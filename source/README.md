# Current construction embedding view

The construction actors can use one current immutable embedding view after an add phase completes. Storage chunks still create saved snapshots, but a joined publication tells each actor which saved root contains every admitted embedding ID. Embeddings with IDs below the published dense count use that root. Newly admitted IDs beyond the count use their insertion root until the next publication. Membership versions and insertion-time references remain unchanged. Centroid reads always use their original root; the embedding override never applies to centroid prefixes. Saved query readers remain independent.

The coordinator publishes only its private latest root after successful append-only writes and flushes. Dense new-ID admission prohibits overwriting earlier embeddings, so the accumulated latest root contains all previously admitted embedding keys without another full-vector scan. The publication API accepts no caller-supplied root. Actors check the admitted count against their current keys and reject shrinking views or prepared-state publication. At the joined actor boundary, publication releases old construction reader handles. Centroid handles reopen their original roots when needed. Publication timing includes validation, actor waits and releasing bounded observation snapshots; it is charged separately.

The default path remains historical-root lookup. The new path is explicitly selected by the diagnostic specification. No routing order, insertion order, balance schedule, split rule, merge rule, reassignment, version increment or saved representation changes. Actual parallel structural mutation and placement scheduling remain deferred. The experiment uses one owner with placement disabled; it does not claim to implement the entire reserve/add/balance/reshard design.

Two fake harness tests verify paired response binding and reject mismatched output or an expanded budget.

These are ARM development-build correctness results, not performance measurements. An earlier test hits the retired-observer cap during balancing; an earlier native smoke hits the snapshot cap. One intermediate build is retained as source-confounded and is not used as proof.

The possible Linux experiment uses the same retained 8,192-vector prefix, two same-binary arms, 256-row storage chunks and one logical balance cut after all rows are registered. This produces 32 appended roots plus genesis. Both arms make exactly two ascending passes over all IDs before balancing. The harness independently computes the expected ID-plus-vector-bit digest from the input prefix. It compares root opens, reader-cache clears, successful encoded storage returns, storage-origin decodes and elapsed probe time. Publication, add, balance, save and final census are separate costs. Provider caches are warm after insertion; a fresh process is not an OS-cold run. Root-open encoded returns are in the LocalStorage counter, while per-reader block decode counters exclude root parsing and provider cache reconstruction. Summed reader spans overlap and are not CPU fractions. The fixed probe is comparable; independently stochastic balance timings are not a causal speed comparison.
