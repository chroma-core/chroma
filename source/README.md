# Attribute the missing neighbors without changing query decisions

The retained depth-five trees have 53/55 leaves, and the existing beam 32 query can select enough leaves for a meaningful navigation-versus-candidate diagnosis. Their saved GT oracle permits about 99.6–99.8% coverage in the best possible 32 leaves, while the actual query returns about 82.6–84.7% recall. That comparison identifies a remaining gap but cannot assign it to navigation, approximate candidate trimming or final FP32 ordering. This package records the actual chosen IDs at those stages on the same saved input; no larger corpus or beam sweep is needed.

The native reader adds one opt-in bounded trace beside the accepted work counters. It copies actual selected leaf IDs, distinct pretrim candidate IDs and retained candidates before exact reranking. The original query consumes the same tuples in the same order and keeps its existing minimum-distance, FP32, sort and tie decisions. The trace performs immutable iterations and creates no alternate scoring path. It does not collect raw score arrays or duplicate every posting row. Default responses remain unchanged when stage tracing is off. `PROTOCOL-CONTRACT.md` defines the ID namespaces, completeness/cap behavior and timing limits.

The external join pins the accepted saved membership report to each original manifest hash and consumes the original hash-verified identity map. It counts GT presence in selected leaves, before trimming, in the retained 200 candidates and in the returned 100. The selected-leaf GT set must equal the pretrim GT set, which checks that the trace and saved membership view agree. Each loss is assigned to leaf selection, candidate trimming or final exact return. This is a diagnosis of these fixed results, not a change to their decisions. The same reused-query/disjointness, FP32-versus-FP64 and global-root-versus-actor-fanout limits remain.

The new local checks pass. The changed saved-reader test verifies seven pretrim IDs, four retained candidates and two returned results with exact stage-off/on result parity, plus rejection before copying an undersized trace cap. Four actual ARM reader processes query the two unchanged 64-row saved fixtures with stage tracing off/on; twelve queries preserve global IDs and distance bits, expose actual chosen IDs and leave every saved file unchanged. The independent retained small GT/leaf set join succeeds for these native outputs. Four wiring tests pass, including a controlled fixture that loses one GT ID in leaf selection, one in trimming and one at final return, invalid/incomplete trace rejection, and fake complete four-cell success/failure. No real-data trace or cloud action occurs locally.

The runtime reuses the accepted harness and existing snapshots, original manifests/maps, frozen sixteen queries, prefix-specific FP64 top 100 and saved GT leaf reports. The two settings remain 100 returned neighbors, rerank factor two, fixed beams 8/32 and uniform tau 2.0. Each arm/setting gets one sixteen-query warm-up and one retained pass: four readers and 128 operations. Each reader has at most ten seconds; all four share forty seconds and the external absolute deadline. There are no retries, index rebuilds, GT recomputation, new data or automatic growth. The parent controls any future binary/transfer/resource admission.

Trace copy time is reported inside the native response; map/report setup and GT joins happen outside the native query and are separately counted. The inherited elapsed fields remain raw trace-enabled records, not latency estimates comparable with the prior run. Existing vector-only cache/storage/decode counters remain distinct from whole-query or physical I/O. Selected leaves are not internal navigation-computation counts. The metadata limit stays 50 MiB observed, and additional trace lists are individually capped at 8,192 IDs; cache/full-query allocations remain explicit exclusions.

The concrete command remains `python3 run-queries.py --spec filled-runtime-spec.json`, with the new exact Linux binary, output and fixed deadline supplied externally. Saved `manifest.json` files are consumed directly and are never rewritten or aliased. Missing or changed saved reports/maps, unknown selected leaves, incomplete traces, invalid stage subsets or budget failures retain a failed result without another attempt.
