# Joined construction phases

Construction now has an opt-in sequence that separates capacity admission, adding vectors, balancing the tree and moving ownership. Storage chunks no longer decide when ownership moves. The ordinary path keeps its existing behavior. This local proof establishes ordering and semantic equivalence; it does not establish construction throughput or readiness for a two-million-vector run.

The coordinator holds routing and structural sequencing. Owner actors hold actual postings and current versions. New registration can run concurrently at distinct owners, while the coordinator computes global routes serially. Balancing continues to use the existing serialized split, merge, neighbor eligibility and immediate cross-owner versioned reassignment path. There is no parallel structural scheduler in this change.

1. **Reserve spare capacity.** Admission treats the entire proposed phase as potentially concentrated at every owner and existing leaf. It checks physical rows, including stale postings, against hard owner and leaf capacities. The caller supplies an additional balancing allowance at least as large as the admitted batch. The soft split threshold is not an admission limit. Rejection leaves the phase ready and performs no vector write or registration.
2. **Add the reserved rows.** One phase can contain multiple bounded storage chunks. Each chunk flushes its immutable vectors, computes routes against the unchanged topology and prepares bounded owner jobs. Each owner receives its rows in input order. Worker threads contact different owner actors concurrently, then all workers join before coordinator locations and traces are committed in global input order. No structural balance or capacity migration occurs inside a chunk.
3. **Publish the current embedding view.** Publication requires every reserved row to finish. It uses the existing append-only current-view mechanism, preserving centroid roots, membership versions and old saved readers. Embedding replacement remains unsupported. This marks the boundary before balancing.
4. **Balance globally.** The existing balance implementation can split leaves and internal nodes, merge, change parents and immediately reassign vectors across owners. Capacity-driven branch movement stays disabled. The existing 100-round cap remains; the phase report exposes its hit count instead of claiming convergence unconditionally.
5. **Move ownership at the boundary.** After balance joins, the explicit reshard operation moves existing branches using the existing placement rule. The tree remains unchanged. A placement threshold is a target, not a guarantee that an indivisible branch fits elsewhere; the existing unavailable-capacity event remains. A subsequent reservation rechecks actual hard capacity. Saving requires the completed ready state.

The parallel-add boundary follows the actual reference implementation. Reference `add` updates a vector version and embedding, navigates and appends to a leaf; it does not split or change centroids. The leaf registration function changes IDs, versions, codes and length. The new test asserts bitwise topology, centroid and centroid-code identity across the entire reference add phase and every owner add chunk. The next balance phase remains separate. This contract covers new dense IDs, FP navigation, FP neighbor eligibility and one replica, using the accepted configuration restrictions. It does not add updates, deletes, concurrent balancing or overlapping phase callers.

Three focused tests pass across the retained terminal runs. The 96-row paired test moves real branches to two owners, constructs an actual cross-owner cutoff tie, runs one-worker and two-worker registration under the same reference balance decision tape, and checks complete saved postings, current versions, codes and vector bits against the reference. Both outstanding requests and actual owner registration spans peak at one versus two. The latter is measured at the owner registration entry and exit, includes vector retrieval waits, and returns to zero after joining; it is not CPU utilization. Its shared observer has constant-size counters and never resets while work is active. The old saved 64-row reader retains its exact results. The order/exhaustion test rejects misplaced operations before mutation, permits a leaf to exceed its soft split threshold before balance, completes two phases and reports one effective owner path despite two configured workers. A dedicated stale-row test has 16 live rows and 17 physical rows: a live-only budget would admit, while the physical budget rejects before mutation. Initial test compilation, the missing observer import compilation and the first stale-row fixture failure remain retained; the corrected stale fixture creates a real versioned reassignment with enough soft-threshold room.

Capacity is expressed in rows, not a memory guarantee. The balancing allowance is conservative admission slack, not a proof that arbitrary repeated reassignment cannot exhaust it. Every actual registration retains existing hard limits, and a failed direct mutation poisons the instance. No rollback or recovery protocol is added. The phase path currently requires a node limit at most 10,000, retains at most 32 reservation descriptions, prepares at most one million route candidates per storage chunk and uses at most eight coordinator registration workers. Existing chunk limits remain at most 8,192 rows. Full current-key scans at publication, reservation metadata scans, central routing/location state, owner posting state, per-row vector copies, provider caches and full saved audits remain costs. Input and reply preparation can consume meaningful memory; row admission does not bound allocator or RSS use.

The native diagnostic retains default compatibility: omitting the new worker option leaves the legacy path and echoed schema unchanged. Enabling it requires the authoritative cell, current-view selection, no fixed-probe mode and no more workers than configured threads. It emits separate reservation, publication, balance and reshard timings plus the phase report. Actual synthetic 64-row native entry checks exercise the legacy path and two completed explicit phases, with complete saved current-membership censuses and exact consumed-spec echoes. The diagnostic has one owner, so two configured workers yield one effective request path. These independently stochastic ARM development-build arms are correctness evidence, not a speed comparison.

No cloud run follows from this package. A future representative comparison must match insertion order, balance cuts, FP policies, owners and physical capacity, and report effective owner overlap separately from configured threads. Parallel balancing needs conflict-safe scheduling for parent edits and cross-owner reassignment; the shared concurrent reference implementation is not a drop-in scheduler for this exclusive coordinator.

## API and source reference

The opt-in API is `enable_construction_phases(workers)`, followed by `reserve_construction_phase(rows, balance_headroom_rows)`, one or more `register_dynamic_batch` calls, `finish_construction_add`, `balance_construction_phase` and `reshard_construction_phase`. `construction_phase_report` reports state and counters. Explicit initial resharding is allowed in the ready state. The state sequence is `Ready → Adding → NeedsBalance → Balancing → NeedsReshard → Resharding → Ready`. Mutation, save and phase-entry checks reject bypasses before changing state.

The new module is `rust/index/benches/hierarchical_index/writer/authoritative_phases.rs`. Minimal hooks are confined to the authoritative owner, dynamic and split modules and focused dynamic tests. The existing diagnostic entry receives an optional `phased_owner_workers` integer, absent or zero for legacy behavior and positive for explicit phases. No parent runner, staged index, publication protocol or production service changes are included.
