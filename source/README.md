# Test whether batched immutable predicates reduce owner balance cost

This paired diagnostic compares the same owner-authoritative construction with individual predicate messages and with at most 64 immutable predicates per message. It asks whether callback reduction materially changes balance elapsed time. It does not assume all of the preceding 16-second balance time comes from predicate messaging. Current-version queries, registration, scrub and placement remain unchanged and separately visible through work counts.

The native command accepts `predicate_batching`, a JSON boolean that defaults to false. True requires the owner treatment. The consumed spec and owner report both echo the policy. The report adds `live_version_requests`, counting actual entries into owner current-version lookup, and retains individual predicate calls, batch callbacks, computed batch rows, total actor callbacks, registrations, split/merge counts and structural wait/hold/context counts. Computed batch rows can exceed live evaluated rows because immutable decisions are calculated before the original live version and duplicate checks; those checks and immediate reassignment remain in their original order. No version is prefetched. The default algorithm remains unchanged.

The controller runs exactly two arms, `disabled` then `enabled`, with the owner treatment in both. Both consume the same retained first 8,192 vectors at 768 dimensions with inner-product distance, explicit full-precision navigation and neighbor predicates, four workers, balance cuts at 4,096/8,192 rows, branching four, split threshold 256 and merge threshold 64. Four owner slots and a 1,024-row movement threshold apply after joined balance. These thresholds exercise construction, not representative ANN quality. Each arm must independently pass the existing scheduler-region, context-overlap, ownership-movement, complete census and exact saved-vector checks. The full-ID exact distance bits must match across arms. The accepted local construction test's saved posting-code verification remains unchanged; this native controller does not independently reimplement that code oracle.

Each arm has at most 30 seconds and both share 60 seconds within the externally supplied absolute deadline. No retry or size increase follows a missed shape gate. Input prefix hashing and the offline build are separately accounted. Saved stores are reported separately from the observed 50 MiB metadata cap. The external operator supplies the exact Linux binary descriptor, resource/window guards and fresh output path; this package grants no lifecycle authority. Child timeouts are not process-group, physical-memory or physical-I/O guarantees.

Independent stochastic schedules can produce different numbers of splits, neighbors, predicates and registrations. Report their work counts before interpreting phase elapsed. Any timing difference is descriptive rather than a fixed-work causal ratio. Summed concurrent context elapsed includes actor waits and nesting; it is not a CPU fraction. The previous accepted reference measurement remains the reference; this package adds no third arm.

The native target builds locally. Both actual synthetic 64-row owner commands pass policy echo, dispatch work, saved census and full-ID exact-distance parity. Three wiring tests cover real reports and shape rejection, fixed runtime bounds, and malformed boolean/reference-policy rejection before input loading. The accepted fixed-input batching test removes exactly 252 callbacks across two predicate modes, and its multi-region saved-code/version/vector/old-reader tests remain separate retained evidence. No local native timing ratio, ANN quality or Linux performance is claimed.

Build with the reused `compile-native.py` recipe against this extracted 940-file archive, the existing target/cache and pinned Rust 1.92 toolchain. It uses offline dependencies, two build jobs, optimization level three and a 20 GiB free-space floor. Fill the exact resulting binary descriptor, authorized absolute deadline and fresh output in `runtime-spec.template.json`, then run `python3 run-pair.py --spec FILLED_SPEC.json`. Source/input/restore/spec/binary hashes remain bound. No global target-cpu change, new infrastructure, corpus transfer or source-index operation is introduced.
