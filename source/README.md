# Compare ordinary construction with one and four local owners

This package asks whether the owner adapter's additional cost comes from extra algorithmic work, computation or local message coordination. It compares the ordinary reference, the current adapter with one owner and no placement call, and the same adapter with four owners and placement only after joined balance. All arms keep four construction threads, the same retained 8,192-vector prefix and individually dispatched predicates. The accepted batching package remains unexecuted. No network latency is measured on this single host.

The native specification adds optional `construction_observation` and `skip_placement` booleans, both false by default. The exact consumed specification is echoed. The three-arm controller explicitly enables observation, disables predicate batching and sets placement off for the reference and one-owner arms. It uses identical full-precision navigation and neighbor predicates, inner-product metric, branching four, split threshold 256, merge threshold 64 and balance cuts at 4,096/8,192 rows. The one-owner arm must record zero moves and one populated owner. Both adapter arms require at least two nonempty scheduler regions, actual overlapping subtree contexts and completed balance. The four-owner arm also requires movement and multiple populated owners. These diagnostic thresholds are not ANN quality settings.

Each phase retains comparable before/add/balance snapshots of shared writer counters: additions, navigation, registration, splits, merges, reassignments, scrub work, balance calls and rounds, neighbor activity, evaluations, version lookups and missing-node retries. Adapter version lookups use actual backend current-entry counts, including scrub calls; `kernel_current_version_requests` separately retains the narrower reference-kernel entry count. The reference uses its current-version entry point. Neither number includes every internal hash-map access inside registration. Counts are cumulative and phase deltas must subtract snapshots; a subsequent phase's before snapshot includes the preceding placement work. Both arms report shape, physical occupancy and completed membership. This permits qualification of different stochastic work rather than assuming equal trees.

The optional message observer retains six fixed operation buckets: current lookup, version mutation, posting access, pure predicate, registration and other. Each bucket stores calls, summed and maximum dispatch-to-service elapsed, callback-service elapsed and caller round-trip elapsed. Queue depth and peak queue depth are bounded-size counters, not an event trace. The field named `queue_ns` begins before the reply-channel/job construction and send, so it includes that small request preparation as well as enqueueing and scheduling delay; it is not pure queue or blocked time. Service elapsed includes descheduling and existing callback observation overhead. Round-trip elapsed includes preparation, queueing, callback work and return scheduling. These overlapping sums are not additive CPU or fractions of wall time. The observer does not change the existing channel, lock, request ordering, replies or lifetime rules. It is enabled only at a joined boundary and is never reset while work is outstanding.

The native report retains message snapshots before add, after add and after balance, and a final report that also includes placement, publication and reporting calls. Observers are off by default. Common balance-call and current-version counters add only a disabled flag check outside the diagnostic. No per-ID event map or unbounded timing log is introduced. The existing structural holder, wait and NPA-context counters remain separately labeled.

The sequential Python controller records user/system CPU seconds and voluntary/involuntary context-switch deltas for each native child with `RUSAGE_CHILDREN`. No other child runs during an arm. These are whole-process values across input, construction, save and audit, not balance-only CPU or directly measured blocked seconds. The controller retains each phase's monotonic elapsed time. Process CPU can exceed wall time across threads. Context switches alone do not establish how long a thread blocks. This package adds no external profiler.

The fixed observer check executes the same 1,024 no-op messages in disabled/enabled/enabled/disabled order, checking identical results and callback counts. It records descriptive overhead samples and validates the six operation buckets and quiescent queue. Four existing owner regressions pass before the final reporting-only counter alignment; the actor-observer helper is unchanged after its passing focused test. The final native target build and three actual synthetic 64-row native entries pass saved-vector/census/exact-distance and new work/message reporting checks. Three Python wiring tests verify actual reports, one-owner and region rejection gates, and the fixed runtime template. Full saved posting-code correctness remains covered by the accepted construction tests, not a new native code oracle. Prior intermediate builds, native entries and their source changes remain retained.

Each real-data arm has at most 30 seconds, and all three share 90 seconds under a separately fixed authorized absolute deadline. There is no retry or row increase if a shape gate fails. Input prefix hashing and the offline build are outside the compute envelope. The observed metadata limit remains 50 MiB; retained saved stores are reported separately. The external operator owns resource guards and shutdown. Child timeouts do not enforce process-group or RSS limits.

Build using the reused `compile-native.py` against the extracted source with the pinned Rust 1.92 toolchain, existing cache, offline dependencies, two jobs, optimization level three and 20 GiB free-space floor. Fill the exact Linux binary descriptor, absolute deadline and fresh output in the template, then invoke `python3 run-pair.py --spec FILLED_SPEC.json`. No cloud or transfer action occurs in this package. The accepted source epochs and staged index remain exact; five source files change in this new epoch. A runtime decision remains external.
