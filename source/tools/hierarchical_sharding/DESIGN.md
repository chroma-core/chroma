# Hierarchical SPANN subtree sharding and horizontal scaling

Distribute one logical hierarchical index by assigning its lower subtrees to different machines. A small shared upper tree routes queries to the relevant subtree owners, while those owners build and compact their branches independently. The primary experiment tests whether the hierarchy can control both the vectors examined and the machines contacted as the collection grows. Independently built indexes with all-shard fanout remain a baseline, not the target architecture.
This is a research implementation plan for the [blog requirements](https://app.notion.com/p/3f958a6d8191802e8ac8f3171fee9b00). The source baseline is `ab03657249240a8732109058286efb8ce31e1faf`. The implementation branch is `codex/hierarchical-spann-sharding`. Production log consumption, updates and deletions under sustained load, distributed ownership changes, and automatic recovery belong to subsequent integration work.
## Target architecture and the pieces
One logical hierarchical index spans the machines. A small upper tree routes a query to lower subtrees, and each subtree has one compaction owner. Remote subtree references are part of the same tree and committed version; placing an unrelated router in front of independent indexes does not satisfy this target.
- The upper tree contains routing centroids and links to remotely owned subtree roots. Coordinators can retain a read-only copy of this small structure.
- A subtree owner builds and compacts its assigned lower branches. A machine can own several subtrees, so moving work between machines does not require changing the logical tree.
- A query worker opens the committed snapshots for its assigned subtrees. It retains their navigation data and loads selected postings and original vectors as needed.
- A coordinator traverses the upper tree, sends work to selected subtree owners, and manages the collection-wide search budget and final result merge.
- A collection manifest binds the upper-tree snapshot, subtree snapshots, ownership mapping, distance metric, dimensions, and global vector identities into one immutable generation. A generation is a named committed version of the whole index.
- A separate benchmark driver measures end-to-end requests and checks results against exact answers over the full indexed corpus.
## Build and publish the distributed tree
1. **Create the shared upper tree.** Use a fixed representative sample to establish the initial spatial partitions. Choose an ownership boundary: the set of subtree roots below which workers own construction. Record the sample, routing parameters, and boundary in the generation.
2. **Assign subtrees to machines.** Use more subtrees than machines and place them using measured population, memory, build time, and query work. A target of 32 subtrees is an initial experiment, not a guarantee of equal sizes. Keep the same boundary and logical subtrees when varying machine count.
3. **Preserve global vector identity.** Route each input vector through the upper tree to its owning subtree. Preserve the original dataset ID independently of physical placement. The modulo-ID mapping used by the baseline is not a spatial ownership rule; the target needs an explicit mapping between subtree-local IDs and collection-wide IDs, with capacity checks.
4. **Build and compact locally.** Give each subtree one writer and a separate immutable block namespace. Insertion, splitting, and balancing below the ownership boundary run locally. Bound concurrent builds on a host and include input partitioning, distribution, balancing, flush, and reopen in the total time to a queryable generation.
5. **Publish a complete generation.** Workers flush and reopen their subtree snapshots before reporting readiness. The publisher validates expected vector coverage, unique ownership, routing references, and snapshot compatibility, then atomically publishes a manifest binding the upper tree to those exact snapshots. Readers stay on the previous complete generation until publication succeeds.
6. **Append through the same upper tree.** Freeze the upper routing structure and ownership boundary within the initial construction epoch, meaning a period in which partition definitions remain fixed. Route new vectors consistently, compact affected subtrees independently, and publish a new generation. The global tree generation is distinct from each subtree snapshot generation. Pin every subtree by its own generation and content hash; affected owners publish new snapshots while unchanged owners retain their older immutable snapshots. Publish the complete new set with one global compare-and-swap operation, and keep the prior global tree queryable.
The initial milestone constrains balancing at the ownership boundary. It does not split a subtree root into new remotely owned roots or reassign vectors across owners during local maintenance. Measure the resulting recall, occupancy, and load skew instead of assuming these constraints preserve unrestricted single-machine behavior. The format must permit a local subtree to grow below its fixed boundary root; reject unsupported boundary changes explicitly.
Cross-boundary splits and reassignment are a subsequent protocol. A root split must publish new child snapshots together with the corresponding upper-tree references. Moving a vector between owners must preserve its global ID and expose neither a missing vector nor unintended duplicates to a reader pinned to one generation. Subtree migration also needs exclusive writer ownership, retry semantics, and protection against a stale owner publishing after the move. These mechanisms remain proposed until implemented and tested.
The persisted collection manifest is the consistency anchor. It prevents a query from combining a new upper tree with incompatible older subtrees. Start with one publisher for the research prototype; multiple publishers require conditional publication or an ownership lease that rejects stale writers.
## Query the distributed tree
1. **Pin a complete generation.** Validate the query and select one manifest for the entire request.
2. **Traverse the shared upper tree.** Score routing nodes and select relevant subtree roots. The target contacts only the owners required by this traversal; exhaustive traversal remains a reference mode.
3. **Continue traversal at subtree owners.** Remote workers return the candidate information required by the chosen search policy. Return to the coordinator when a collection-wide branch-selection decision is necessary.
4. **Enforce a collection-wide budget.** The reference mode preserves the beam, the number of branches retained after a navigation level, across local and remote branches. Giving every subtree a full independent beam is a different policy with a larger aggregate budget. A variant that allocates a fixed budget per selected subtree may reduce coordination, but must be evaluated separately at matched recall.
5. **Rerank and merge candidates.** Resolve duplicate global IDs before counting results, score final candidates with original vectors and the same metric, and retain the global top k. Exact candidate distances do not make approximate navigation exact; measure recall against the complete corpus.
6. **Require complete selected work.** Check request identity, generation, subtree identity, and ownership. Missing or stale responses from any selected subtree fail the request rather than silently reducing recall.
Preserving global branch selection can add network round trips between tree levels. Measure those sequential dependencies, coordinator CPU, queueing, machines contacted, total vectors scored, serialized bytes, physical storage reads, and retained memory. Bytes alone do not determine latency.
The first distributed-tree reader may materialize all navigation metadata for the subtrees it owns. Arbitrary on-demand navigation fragments and cache-aware routing are separate capabilities. The blog must distinguish implemented subtree ownership from proposed finer-grained loading.
## Independent-index baseline
The baseline keeps independently constructed indexes with modulo ownership and searches every shard. Preserve it as a correctness, transport, compaction, and cost comparator. Its measurements do not establish that one tree is distributed by subtree. The following components and workflows describe that baseline.
- A logical shard owns a stable subset of vector IDs and one hierarchical tree. Logical shards remain fixed while experiments change the number of physical machines.
- A compaction worker adds vectors, balances its tree, and writes immutable index blocks. It publishes a shard snapshot only after those blocks are complete.
- A query worker opens one committed shard snapshot and retains only that shard's navigation data. It loads selected posting lists and original vectors for reranking as needed.
- A coordinator sends a query to the required workers and combines their exact reranked candidates into the global nearest results.
- A collection manifest identifies the complete set of shard snapshots, their ownership, dimensions, distance metric, and one collection generation. A generation is a named immutable version of the whole collection.
- A benchmark driver generates requests on a separate machine and records end-to-end response times, failures, and recall against exact reference answers.
### Build and publish the baseline collection
1. **Assign every vector to one stable shard.** Use the original dataset row number as the global ID. With S logical shards, shard s owns IDs for which `id % S == s`. Its tree uses a local ID, and the worker translates it to `s + S * local_id`. This keeps the existing 32-bit tree IDs while allowing 64-bit collection IDs. Reject any shard that exhausts its local ID space.
2. **Prepare each shard's input independently.** Produce little-endian, row-major float32 files in dataset order, recording source revision, dimension, metric, row counts, and checksums. Time source conversion and distribution separately from construction and include them in the total time to a queryable collection. Do not have every worker download or retain the entire corpus.
3. **Build shards concurrently.** Give each shard a separate storage namespace and a single writer. Workers execute insertion, balancing, commit, flush, and reopening checks independently. Bound the number of concurrent shard builds on a host so memory use stays within the measured budget.
4. **Publish completed shard snapshots.** A worker writes a new immutable snapshot manifest after all referenced blocks exist. A failed or retried build cannot overwrite a previously published generation. Reopening must succeed before publication. Small shards up to 100,000 vectors also verify every reachable ID; large shards require a separate streaming integrity audit before headline benchmarks because the current full audit retains all IDs in memory.
5. **Publish the complete collection.** The coordinator checks that every shard belongs to the same intended generation, uses the same configuration, and collectively covers the expected dataset prefix exactly once. It writes the collection manifest atomically. Readers continue using the previous complete generation until the new one is ready.
6. **Compact the next batch independently.** Partition the next dataset suffix using the same ownership rule. Each writer reopens its previous shard snapshot, adds only its new rows, balances, and publishes a new snapshot. Measure time until the entire new collection generation is queryable, including the slowest shard and publication.
The persisted collection manifest anchors reproducibility and read consistency. A reader must use the exact snapshot named by its request; a worker that has another snapshot returns an error. A single publisher is sufficient for the benchmark. Multiple competing publishers require compare-and-swap or a fenced lease before production use.
### Search the baseline collection
1. **Pin one collection generation.** The coordinator validates query dimensions, finite numeric values, result count, search settings, and the chosen manifest before sending work.
2. **Search every logical shard concurrently.** Each worker searches its own hierarchical tree and reranks candidates with original vectors using the same metric. The first milestone uses all shards; it makes no claim that routing eliminates network work.
3. **Require complete responses.** The coordinator checks request identity, generation, shard identity, ID ownership, and finite distances. A timeout, missing shard, or malformed response fails the request. Partial answers must not appear as successful benchmark results.
4. **Merge the nearest candidates.** Each shard returns up to k exact reranked candidates; the coordinator orders their union by distance and then global ID and retains k. This merge is exact relative to the returned candidates. Approximate shard search can still omit true neighbors, so collection recall must be measured against the complete corpus.
5. **Record the whole request cost.** Record end-to-end latency at the driver, worker search time, coordinator work, shards contacted, serialized network bytes, and errors. Keep index payload bytes, physical storage traffic, and retained memory as separate measurements.
Query workers open only their own shard navigation metadata, which reduces per-worker memory when data ownership is spread across machines. Each worker still materializes its entire shard's navigation structure. This milestone does not implement arbitrary navigation fragments loaded on demand, shared caches, or one globally balanced tree spanning machines.
For the independent-index baseline, use 32 logical shards as the initial placement experiment. Assign them evenly across 1, 2, 4, and 8 physical workers, building one shard at a time per worker and running one persistent reader per shard. At 1B vectors this produces approximately 31.25M vectors per tree, reducing the risk that one writer exceeds a machine's memory. Set coordinator concurrency explicitly and record any fanout waves. A separate 8/16/32-shard experiment can determine whether the extra fanout is worth the smaller trees; do not mix that change into the primary machine-count sweep.
## Alternatives considered
A coarse spatial router in front of independently constructed indexes is a possible additional comparator. It can reduce fanout, but it does not by itself provide shared hierarchical navigation or a collection-wide beam across remote branches. The target instead stores upper routing nodes and remote subtree roots as one versioned tree. Evaluate a simpler routing wrapper only when it answers a specific cost or recall question; it is not a substitute for the distributed-subtree milestone.
## Implementation sequence and acceptance gates
1. **Validate the independent-index baseline.** Preserve reproducible build, append, reopen, network query, snapshot, and failure tests. Fix correctness defects needed by both architectures; label baseline results separately.
2. **Represent one tree across ownership boundaries.** Add shared upper routing nodes, remote subtree references, stable global vector identity, and a manifest binding the complete tree. A one-machine deployment of the distributed representation must pass structural integrity and exhaustive-query checks against an equivalent local tree.
3. **Distribute subtree construction and publication.** Build and append subtrees on two machines with the upper tree and ownership boundary fixed. Verify complete coverage, no unintended duplicate ownership, old-generation readability, and rejection of incomplete publication. Explicitly test attempted boundary changes.
4. **Distribute query traversal.** Compare one-machine and multi-machine traversal of the same committed tree under the same global search policy. Results must agree apart from documented numerical or tie behavior. Measure collection-wide beam coordination against any separately defined local-budget variant.
5. **Measure horizontal scaling.** Keep the same upper tree, subtree snapshots, boundary, search policy, cache conditions, and workload while placing subtrees across 1, 2, 4, and 8 machines. Report both fixed-setting recall and cost at matched recall. Measure routing quality, selected subtrees, physical hosts contacted, skew, coordinator cost, and aggregate work.
6. **Test a larger real corpus and extend balancing.** Record the larger-run forecast before execution and gate it on measured resources and exact-reference cost. Add cross-owner reassignment, upper-tree updates, and subtree migration as separately validated capabilities.

## Benchmark questions
The companion benchmark plan (`BENCHMARK.md`) defines the run matrix and result format. The central questions are whether more machines reduce collection publication time, whether they increase query throughput at a chosen tail latency and recall, and whether a larger collection can maintain useful recall within measured per-node resources.
For construction, compare a fixed corpus, shared upper tree, ownership boundary, and subtree layout on 1, 2, 4, and 8 machines. Record upper-tree construction and input routing separately, and include them in end-to-end publication time. Run independent-index builds as a separately labeled baseline. Report total publication time and speedup `T(1) / T(p)`, efficiency `T(1) / (p * T(p))`, per-shard completion times, aggregate compute, and storage traffic. Run both fresh builds and a fixed-size append. Include input preparation, final flush, and manifest publication in separate phase measurements and in the total.
For reads, separate physical placement from tree and search-policy changes. First place the same immutable distributed tree and subtrees on different machine counts. Then vary data size with a fixed amount of data per node. Sweep ownership depth, subtree count, routing selectivity, and global versus allocated subtree budgets as separate experiments. Compare with exhaustive traversal of the same tree and the independent-index baseline. Count distinct hosts as well as selected subtrees, since multiple subtrees may share a host. For each experiment, report fixed-setting recall and the cost to reach 90% and 95% recall where achievable. Use top-100 results, held-out queries, repeated trials, and enough requests for meaningful p95 and p99 estimates.
For failures, interrupt one compactor before publication and one query worker during a load run. Verify that the old collection generation remains readable, incomplete new generations remain unpublished, and failed queries appear in the results. Measure recovery and retry costs explicitly. These are research protocol checks, not evidence of production availability.

## Risks that can invalidate a scale claim
- Fixed ownership boundaries can worsen recall or create oversized subtrees as new data arrives. Measure boundary-sensitive recall, population skew, build stragglers, and hot-query concentration.
- Collection-wide branch selection can introduce sequential network round trips and a coordinator bottleneck. Compare policies at matched recall and report aggregate work.
- Publishing upper-tree references separately from subtree snapshots can create an inconsistent index. Test atomic generation publication and stale-owner rejection before enabling boundary changes.
- All-shard fanout in the independent-index baseline can improve latency while increasing total work. Report aggregate CPU, bytes, and cost as well as per-machine values.
- Changing shard count changes tree construction and search budgets. Keep logical shards fixed for the primary machine-count sweep.
- Each shard independently returning k results multiplies candidate and reranking work. Record aggregate budgets and measure matched recall instead of treating identical per-shard settings as equal work.
- Independent writers can have uneven completion times. The slowest shard determines publication time.
- Process-local materialized postings and block pins can outlive the nominal block-cache budget. Measure resident memory through the entire run and define cache clearing precisely.
- A restarted application can still read from the operating-system file cache. Label that condition separately from a storage-cold or object-storage run.
- Reusing a hundred queries can produce warm-cache behavior without supporting a broad p99 claim. Separate exact-reference query preparation, warm-up, calibration, and timed test requests.
- Incremental append compaction does not establish update, deletion, log replay, or merge-on-read semantics. Keep those claims outside this milestone.
