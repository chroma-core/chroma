# A bounded real-source concurrency pilot

The first pilot runs the instrumented two-file configuration over the same four complete public source files, then compares a four-file configuration only if enough of the fixed node deadline remains. It does not change the canonical row order, decoder, output chunking or UUID equality policy. It is scheduled on the future preparation node only after the 10M read/capacity gate; no pilot runs from this plan now.

The preserved four-file prefix contains 3,281,725 real rows: 1,090,356, 1,066,143, 30,720 and 1,094,506 rows in canonical file order. The small third file is part of the real prefix and remains included; report the imbalance instead of choosing a more favorable set. Confirm these counts against the new metadata plan before execution. Both arms use fresh unique output directories and fetch the same selected dense/UUID columns. Do not seed one arm from the other or use a warmed full-file cache for only one arm.

Each arm uses 100,000-row chunks, 2,048-row decode batches, one file retry, a 16 GiB charged source-request cap, a 16 GiB ingestion-output cap and a seven-minute wall limit. Keep the same full host CPU allocation, runtime, SQLite settings and source hash. The host guard includes both arms, failed attempts, runtime/cache, logs and control files. Stop the pilot after 15 minutes total; do not consume the preparation or preservation reserve. Each arm's actual process-group CPU/RSS and stage receipts must cover the complete interval. Failed arms remain outcomes, not omitted observations.

Compare every canonical vector and UUID chunk's interval, byte count and SHA-256, then verify complete dense global IDs and exact global UUID uniqueness. Equal UUID-index SHA is useful evidence but cannot replace row/lookup semantics because storage-engine layout is not the identity contract. Preserve all source/footer/range receipts and actual requested bytes. Report network wait, conversion, serialization, writes, hashing and SQLite time separately. The request timer includes range hashing, and file-thread spans overlap; do not add concurrent wall times into elapsed time.

The initial two-file arm is the baseline. Adopt four-file ingestion only when its complete elapsed time improves by at least 15%, its full canonical artifacts match, and its peak RSS/request/output headroom remains within the declared limits. One sequential pair is a screening result, not a stable throughput claim: publisher/network/cache effects and ordering are uncontrolled. If the result is marginal, keep two-file ingestion; do not spend the main node budget on an open-ended tuning sweep.

Pilot time and both retained outputs count against the same six-hour node budget and storage guard. Recompute the remaining full 100M preparation plus archive/restore projection after the pilot. If it no longer fits with the 30-minute preservation reserve, do not start bulk 100M on that node. Preserve the pilot and revise the next concrete job; never extend the installed hard stop silently.
