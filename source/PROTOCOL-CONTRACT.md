# Trace the IDs selected by the existing query

The saved reader can expose bounded ID lists that explain where true neighbors leave its existing query path. Start it with `read --checkpoint-dir STORE --profile-query-work --trace-query-stages`. Stage tracing defaults off, requires the existing work profile, and rejects snapshots with more than 8,192 vectors before processing requests. It changes no navigation, score, budget, sort, distance or tie decision.

A successful ordinary-query response adds `query_stage_trace_policy="bounded-query-stages-v1"` and a complete `query_stage_trace` object. `selected_leaf_ids` records the actual navigation output in its existing order. `pretrim_candidate_ids` records distinct local vector IDs after minimum-distance deduplication and before the candidate budget applies; it does not repeat every scored posting copy. `retained_candidate_ids` records the actual candidates after the unchanged approximate trim/sort and before exact reranking. Final mapped IDs and FP32 distance bits remain in the existing response. Candidate IDs in the trace are local to the pinned snapshot, so the external join uses its original local-to-global map rather than assuming a namespace.

Each list has at most 8,192 IDs. The reader checks selected-leaf and distinct-candidate lengths before allocating their trace copies; retained candidates are a subset of that already checked vector. A cap failure returns an error rather than a truncated trace. The response marks complete traces explicitly. This bounds additional ID payload only; it does not turn the existing full candidate/scoring allocations, provider caches or RSS into bounded memory claims.

`copy_elapsed_ns` records the two trace-copy intervals, including vector allocation and iteration. Those intervals sit outside the existing selection/sort timer. Native operation elapsed still includes the copies and optional response construction, so trace-enabled latency is not compared with the previous latency experiment and is not corrected by subtracting this timer. Navigation/scoring/selection/exact-rerank code and FP32 tie behavior remain unchanged.

The controller joins each trace with the frozen top 100 GT, original dense map and accepted saved-leaf GT membership report after the native child completes. It reports selected-leaf, pretrim, retained-candidate and returned GT hit counts and the resulting loss partition. Selected-leaf and pretrim GT sets must agree; disagreement fails as an inconsistency. Retained IDs must be a subset of pretrim IDs and returned global IDs a subset of retained mapped IDs. The loss after exact reranking can include FP32-versus-FP64 ordering/ties rather than an approximate-trim failure. Mapping/report loading and per-query set-join elapsed are reported separately from native query timing.
