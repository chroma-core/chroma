# Temporary deletion benchmark recovery

The reference is the finer leaf scheduler at `14dc9698eb6e400ba6f677575eff7a5659deeed6`; the candidate is temporary per-leaf posting-slot deletion state at `1d659e171b8456d4e0bbd6c77dbf6cbb40674470`. The candidate keeps transfer claims, marks outgoing positions dead, uses live counts for balancing, and scrubs touched surviving leaves after all workers join. Final cleanup is included in balancing time. The separate batched-transfer experiment is excluded.

The recovery owner inspects EC2 before starting work. At recovery there are no active benchmark or build processes and no remote experiment directory; the candidate archive alone exists. The owner starts one locked build, reuses the exact finer-scheduler binary with preserved provenance, and runs sequential Wikipedia comparisons on local NVMe. A first fresh 1M pair commits every 100k vectors; a candidate-first fresh 3M pair commits every 1M. Later runs depend on correctness and usefulness. Each run holds `/mnt/data/chroma-benchmark.lock`. All original checkpoints and the retained 8M source are preserved.

Settings match the established full-precision Wikipedia configuration: 32 insertion and balance threads, L2 metric, branching factor 100, split threshold 2048, merge threshold 512, writer tau 0.5, writer level taus _,_,0.30, 1GiB cache, fixed 100 queries and precomputed neighbors for the exact final corpus. Writer minimum level percentages and replication flags are absent. Benchmark validation is disabled in timed runs. Independent audit binaries check reachable ID coverage, exact-once physical/live posting counts, and sampled embedding bits and codes after reopening the saved format2 index. Audits execute outside timed runs under the same benchmark lock.

The primary sum includes insertion and production preflight, balance including final cleanup, commit preparation and flush, and writer reopen. It excludes dataset loading, benchmark diagnostics, printing, reader-pin cleanup, destruction and benchmark garbage collection; it does not represent all production latency. Raw CLI wall totals and per-process resource samples remain available. Source scan counters count physical ID slots examined and do not directly count copying: the candidate removes source code snapshots and survivor copies but still scans IDs. Cleanup survivor bytes count payload retained/written, not hardware memory traffic. Split-time cleanup is already included in total balance but excluded from the final-cleanup counter.

## Completion

Six runs and separate audits complete. The candidate shows no convincing latency improvement: core indexing changes by +4.2% at 1M, −3.3% at 3M, and +1.6% for saved 8M → 9M. All six saved indexes pass complete ID/topology audits; larger indexes also pass 200 old/new embedding and code samples. Final cleanup is included in balance time. See REPORT.md for method, results, limitations, and recommendation. The shared lock is released, original sources remain, and only the two completed isolated 9M replay copies are pruned after audits.
