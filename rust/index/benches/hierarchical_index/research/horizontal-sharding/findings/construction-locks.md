# Construction locks: sharded and unsharded

Both implementations use locks, but the current sharded implementation adds synchronization and holds some shared locks over more work. Some coordination is necessary to prevent conflicting updates; the particular global locks, ownership directory and sequential owner queues are implementation choices, not inherent requirements of sharding.

This comparison records source inspection on October 19, 2026. “Sharded” means the current full-record construction path, where node records and owner posting lists are managed separately. “Unsharded” means the retained optimized reference used for the matched comparison, under `reference-matched-input-v1/source` in the implementation directory. It does not describe every subsequent change in the separate unsharded-index chat. The owners described here execute in one process; these locks do not establish coordination between independent machines.

The assessments distinguish what the current code relies on from what the intended sharded design requires. They are design judgments, not evidence that a lock can be deleted without changing the operations it protects.

A mutex allows one thread to hold it at a time. A read/write lock allows concurrent readers, but a writer excludes both readers and other writers. A shared bucket lock protects several records assigned to that bucket, so unrelated records can contend for it.

| Lock or serialization mechanism | What it protects in the sharded implementation, why, and whether it is required | What can wait unnecessarily | Unsharded implementation and how it differs |
| --- | --- | --- | --- |
| **Tree-wide structural mutex** | It coordinates edits involving several nodes, including parent changes, splits, merges and root replacement. The general reassignment path also holds it while checking destinations and registering new membership. It covers the whole local logical tree. **Assessment: Structural coordination is required; this broad tree-wide scope is not a sharding requirement.** Concurrent edits to the same parent or root must agree. I would first match the reference by moving expensive preparation outside the lock. Replacing the remaining global mutex with narrower coordination is a separate design decision. | Work on unrelated branches can wait. The ordinary leaf-split path holds it during vector fetching, clustering and replacement publication, as well as structural edits. | The reference also has a tree-wide structural mutex. It allows the same thread to acquire it again inside a helper. However, reference leaf splitting prepares the replacement outside that mutex, then acquires it to attach the children. Internal splitting still uses the global mutex. Reference reassignment coordinates through the destination node and vector-version entry instead. The sharded path's broader scope is a current implementation choice, not a demonstrated sharding requirement. |
| **Tree-wide navigation read/write lock** | Construction navigation takes a read lock. Structural changes take the write lock so navigation does not observe a temporarily detached child while records are replaced. This is separate from the structural mutex above. **Assessment: This is required by the current implementation’s visibility policy, not by sharding itself.** I do not see an established need for tree-wide exclusion in the target architecture. Removing it requires an explicit choice of navigation behavior during structural changes and validation that retries preserve correctness; the current guarantee remains in force until then. | A structural change can stop navigation throughout the tree. A traversal can also delay structural changes, including while it fetches node records. | The reference has no equivalent tree-wide navigation lock. It reads parent-local navigation data and tolerates missing nodes during concurrent edits; insertion can retry when a destination disappears. The sharded lock enforces its stronger requirement for a complete view during traversal. That requirement and its implementation need justification; sharding alone does not require a global navigation lock. |
| **Node mutation locks** | A worker locks a node record while changing its centroid, parent or posting count. It can retain the lock while coordinating a posting update with the owner, keeping the record and posting operation consistent. The record store assigns node IDs to 64 shared mutexes. **Assessment: Coordination of conflicting node and leaf updates is required.** Multiple workers on one owner can change the same leaf. The [decided target](../DESIGN.md#one-edit-lock-per-node) replaces the shared 64-mutex pool with an independent edit lock per resident mutable node. Eviction and reloading must preserve one authoritative lock across overlapping operations. Implementation remains paused; region protection is a separate requirement. | Different nodes can map to the same mutex. Waiting for an owner reply can extend the time that other updates are excluded. | The reference uses a concurrent map whose internal bucket locks protect node updates. Its in-memory leaf contains posting arrays, so a worker can update the leaf directly under that map guard. Unrelated nodes can share a bucket there too. The sharded store uses explicit mutexes around editable records and separately managed postings; those details differ, but protecting conflicting updates to the same leaf is necessary in both. |
| **Vector identity locks** | Each ownership-directory partition assigns vector IDs to 64 shared mutexes. These locks protect multi-step operations involving owner lookup, membership-version changes and ownership transfer. They can remain held through directory and owner replies. **Assessment: This separate lock subsystem is not required by the agreed target design.** It serves the current per-vector directory and membership-version machinery. The target instead requires source revalidation and coordinated posting removal/addition on the affected leaves, plus a cross-machine transfer protocol. Those mechanisms must cover competing transfers before these locks can disappear. | Unrelated vectors can share a mutex. Queued operations elsewhere can prolong the protected operation. | The reference has no separate identity-lock array or per-vector ownership directory. Its version map's bucket lock protects checking and changing a vector's version, alongside the destination node guard during reassignment. The additional sharded locks coordinate the current split between directory and owner state. Subtree routing and explicit posting transfer must preserve membership correctness, but do not inherently require this directory or lock array. |
| **Owner version-map read/write lock** | Each owner has a map of current membership versions. A read/write lock permits direct version reads by workers while the owner executor changes the map. **Assessment: This is not required in the target design and should be removed with the membership-version map and service.** The current shared map needs synchronization while it exists. Necessary structural and placement counters are separate and remain subject to their own coordination rules. | A version update excludes other access to that owner's entire map while the write lock is held. | The reference stores new or changed versions in a concurrent map with bucket locks, rather than one read/write lock for the entire owner's map. Persisted versions use a separate read cache and a mutex for loading that cache. The owner-wide lock serves the current shared-map implementation; its scope is not required for sharding. Our decided target removes membership versions and this version-checking service. |
| **Storage, cache and scheduler mutexes** | Separate mutexes protect cached records, pending writes, memory reservations, reader admission and work queues. A flush mutex prevents concurrent node-store flushes from publishing incompatible saved roots. Some queue operations perform storage work while locked. **Assessment: Some synchronization is required, but this entire collection of mutexes is not a sharding requirement.** Shared mutable caches, memory budgets, work claims and saved-root publication need consistent updates while those components exist. Choose synchronization for each retained component; do not assume one broad lock or storage I/O under that lock is necessary. Reuse the reference’s mechanisms where they satisfy the same requirements. | Workers sharing these structures can wait. Reader admission deliberately limits concurrency to respect memory headroom. A flush can hold its mutex across storage writes; these are not all short bookkeeping locks. | The reference also synchronizes shared maps and lazy loading, but it has no equivalent collection of owner record-store, placement-queue and admission mutexes. Its balance scheduling includes a concurrent set that prevents two workers from balancing the same node. The sharded locks protect its additional bounded stores and queues. Resource limits and consistent storage publication need coordination; this particular collection of stores and locks is not intrinsic to sharding. |
| **One sequential operation queue per owner** | An owner thread processes one queued operation at a time against its posting-list and vector-reference maps. Callers generally wait for a reply. Each ownership-directory partition also processes a sequential queue. These queues provide exclusion even without a mutex around each posting list. **Assessment: The target design removes the constraint of one sequential operation queue per owner.** The [concurrent-owner requirement](../DESIGN.md#concurrent-owner-execution) permits independent jobs to run in parallel while conflicting operations retain explicit coordination. Dispatch and deferred-work queues remain useful; they do not require a single execution thread. The current implementation is still sequential. | Operations on different leaves of the same owner queue behind one another. Configuring many construction workers does not make this owner thread execute several operations simultaneously. | The reference has no equivalent owner executor. Construction workers access shared local state directly using the map and structural synchronization described above. The sharded queue provides a single place to order operations on owner state, but single-machine ownership does not require single-threaded execution. Communication between machines will be necessary; serializing every local leaf operation through one executor is a separate design choice. |

The table describes the main construction mechanisms, with two important configuration exceptions. The optional prepared-split path moves expensive preparation outside the structural mutex and revalidates before applying it. The optional single-owner reassignment path uses a destination-node lock, identity protection and an owner callback without taking the structural mutex. An optional paged metadata store also replaces parts of the resident version-map machinery. These alternatives must be identified when interpreting a benchmark.

The reference has additional narrow synchronization beyond the table. In particular, a short-lived mutex reserves the two leaves participating in a merge, preventing overlapping merges from moving rows in conflicting directions. Atomic counters and concurrent sets also coordinate work. Immutable saved-query readers do not take the sharded writer's live construction navigation lock.

The design requires synchronization on affected leaves, while removing membership-version checks and their service. It does not require the current per-vector directory, owner-wide serial execution or tree-wide navigation exclusion. Resolving how to coordinate structural edits and cross-machine transfers remains part of the architecture discussion. This document explains current code; it introduces no implementation change or benchmark result.
