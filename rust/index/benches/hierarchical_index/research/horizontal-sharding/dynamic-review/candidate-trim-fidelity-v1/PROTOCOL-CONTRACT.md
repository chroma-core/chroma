# Candidate cutoff fidelity diagnostic

This diagnostic explains why ten true neighbors reach the saved query’s candidate set but fall outside the 400 candidates sent to exact reranking. It observes the existing selection and scores a bounded comparison set afterward. It does not choose a new query policy or access reserved evaluation queries.

The reader records each distinct candidate’s approximate distance as exact FP32 bits immediately before the existing cutoff operation. The operation remains the same distance-only partition, exact truncation to 400 and distance-only sort. Boundary ties remain subject to that operation’s existing selection, including signed-zero equality. The trace additionally records cutoff bits and the offered and retained tie counts. These fields are enabled only by the existing stage-trace flag, with the existing 16,384-ID cap. The added copying is charged inside diagnostic selection elapsed; these samples are not comparable to untraced latency.

The focused native test applies the original inline operation and the shared observed helper to identical ordered inputs. It verifies exact selected IDs and score bits with tracing off and on, including repeated ties, signed zeros, empty inputs and no-trim controls. This proves observer neutrality for the same input order. Hash-map iteration and boundary ties can produce different kept sets across separately seeded processes; the runtime reports prior-kept and prior-returned equality rather than silently requiring deterministic cutoff ties. Actual chosen leaf order and complete pretrim candidate sets must match the prior beam-38 result.

## Measurements and interpretation

One reader process runs the 32 calibration queries at FP centroid navigation, per-level beam 38 with tau 2.0, k 100 and rerank factor 4. The shared cache policy remains 256 block-capacity units, 4,096 root entries, one shard and no provider clear after an operation. This first pass is not described as warm steady-state latency. Root opening and FP centroid preload remain separately reported. Existing work counters and bounded vector-block observations remain unchanged; incomplete aggregate evidence is unavailable rather than zero.

For each query with true neighbors excluded by the observed cutoff, a second reader process performs the existing exact selected-ID operation on the union of the 400 kept candidates and the excluded true neighbors. Each request has at most 500 IDs. These exact operations occur after all query decisions, outside query timing, and cannot affect those decisions. Returned exact FP32 bits must match the original query’s final returned vectors. The report compares excluded approximate scores with cutoff/ties and their exact ranks within the kept-plus-excluded set. Full raw exact scores remain available for independent checks. This is not an exhaustive exact ranking of all pretrim candidates. FP64 ground-truth order and FP32 distance order remain distinct.

The query trace requires at most 16,384 score tuples, with eight bytes of score/ID payload per tuple before container and serialization overhead. The targeted exact operation has at most 500 vectors, or 1,536,000 logical FP32 bytes per request, excluding cache and Arrow metadata. The report charges actual requested vector rows and logical bytes, separately from observed encoded storage returns and storage-origin decode counts. Neither is physical disk I/O or network traffic. A local saved reader does not measure physical owner fanout.

Approximation-driven rank reversals, cutoff ties and inconsistent reconstruction are competing explanations. The trace can distinguish their score evidence; no bug, recovered recall, matched quality or speedup is presumed. There is no automatic full-precision posting policy, rerank-budget increase, beam increment or evaluation run.
