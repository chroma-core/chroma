# Chunked durable construction at independent logical cuts

The construction writer accepts a logical insertion cut through bounded durable storage chunks, then balances and redistributes only after the entire cut joins. A 64-row storage chunk does not trigger balancing or capacity placement. This preserves the declared logical schedule while removing the requirement to hold a whole cut or corpus in the native input harness.

The owner adapter reserves physical posting headroom for the entire logical cut before registration. Each chunk validates dense IDs and finite vector shape, stages immutable vector content, joins insertion workers, and releases pending handles before the next chunk. Staging does not publish current membership. Immediate registration and reassignment still use the existing authoritative owners and reference scheduler. A failed insertion or balancing operation cannot publish a saved generation.

The adapter admits a configured row ceiling below the 32-bit ID limit rather than the old 16,384-row fixture ceiling. Its latest 32 phase reports are retained, while cumulative phase counts and add/balance seconds continue across later cuts. The native harness applies the same history limit. Routing, ID directories, owner posting/version state and joined snapshot publication remain resident or whole-state dependencies; this change does not make those structures bounded.

## Split preparation admission

Split preparation uses the existing clustering algorithm. The caller configures maximum physical source rows and an aggregate modeled working-byte budget. Each split reserves the configured maximum before source detach, and releases it on scope exit. Reservation rejects immediately when the aggregate budget is exhausted, including nested operations, rather than waiting while holding structural state. This is a modeled admission boundary, not a hard allocation or RSS ceiling.

The modeled reservation is `rows * (4 * dimension + 256 + 2 * Code1::size(dimension)) + 64 * dimension + 65,536`. It covers vector payload, tuple/group capacity, original/output code payload and clustering distance/label/index/center scratch with an allowance. It excludes allocator bookkeeping, provider/root-index allocations, retained owner postings, global routing, caller publication buffers and existing caches. It can double-count shared payload during nested operations. The native response reports the configured budget, aggregate reserved peak and rejected reservations. Actual allocation is not measured by that model.

At 100,000 rows and 768 dimensions, the reservation is 355,314,688 bytes per admitted split. Four such reservations require 1,421,258,752 bytes, before the excluded state. A cut of 100,000 new rows does not guarantee that every source leaf has at most 100,000 physical rows: prior occupancy and stale copies require headroom. The caller must configure that headroom and the aggregate budget; exhaustion is an explicit failed construction, not an automatic change in balancing cadence. No million-vector performance or capacity result is claimed.

## Native interface

The existing `reference-owner-diagnostic --spec PATH` command accepts `bounded_vectors` (default false), `split_rows` (default 256), `split_working_bytes` (default 16 MiB), `max_owner_physical_rows` (default 1,048,576), `max_audit_nodes` (default 10,000), and `max_audit_rows` (default 1,048,576). The existing `balance_every` controls logical cuts. Storage and input buffers use at most 64 rows. The bounded treatment requires owner construction, at most four insertion/balance workers, and a split threshold within the admitted row limit. The reference arm uses the same chunk joins and logical cuts but retains its ordinary central embedding map.

The command verifies every consumed prefix byte before construction through a bounded buffer, rewinds, and hashes the actual construction pass again before saving. It then rereads bounded input chunks to verify every saved vector bit and exact distances. Small fixtures retain the existing all-ID distance array; larger inputs report its ordered digest instead. The original saved manifest and streamed dense ID map remain create-new. Declared whole-source identity remains externally verified; the native command independently verifies the consumed prefix, not all unused source bytes.

The input decoder temporarily owns encoded bytes and decoded rows together, so its accounted payload is twice a 64-row FP32 chunk, plus one validation query and ordinary container overhead. Durable staging creates a new immutable fork per chunk: one million rows produce 15,625 stage commits and flushes. Root-index growth and repeated provider reads can dominate despite bounded input buffers. Stage count and elapsed time remain in the owner report; root-index bytes are explicitly unavailable through the reader API. Full saved-vector validation can also repeat decoding. These costs remain charged rather than being inferred efficient from bounded input buffers. Native add elapsed includes chunk reads, decoding, hashing, staging and joined worker insertion; decoder elapsed is nested within that interval. Owner add totals cover staging and worker insertion after the caller supplies a chunk. Chunk joins also create fresh worker scopes; no claim of a persistent insertion-worker pool is made.

## Local evidence and scope

The focused tests cover a 641-row logical cut in eleven storage chunks, including a final one-row chunk, followed by 34 further cuts with bounded history. They retain full saved census, vector/code verification and an old reader. Separate negatives reject physical reservation before the first registration and reject insufficient split budgets. Existing missing-first-registration, ownership transfer, split/merge and old-reader proofs remain part of the focused target.

The real native smoke uses 259 synthetic vectors with logical cuts of 193 and 66 rows and storage chunks of 64, 64, 64, 1, 64 and 2 rows. It compares saved reference and bounded-owner exact distance bits and complete current membership, and rejects an incorrect prefix hash before creating the output store. These are correctness and wiring tests, not representative timing measurements or evidence of million-vector readiness.

No cloud operation, corpus download, query policy change, production default change or staged-index mutation belongs to this milestone. Earlier quality and query-cost results describe their immutable saved trees, not this construction epoch.
