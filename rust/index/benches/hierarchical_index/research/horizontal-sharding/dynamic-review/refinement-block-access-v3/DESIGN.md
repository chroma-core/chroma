# Measure exact refinement before changing access order

The experiment tests whether many selected vector IDs cause repeated storage-origin decoding of the same physical block. It preserves the exact candidate set and FP32 results. A successful measurement can justify one grouped/coalesced implementation; a negative result ends this hypothesis. It establishes a local mechanism on retained data, not real-data latency or a state-of-the-art claim.

An optional observation follows the actual vector reader's block lookup. It records each u32 key's resolved block, reader pin hits/misses, provider cache obtains/hits/misses, successful storage callbacks and encoded byte lengths, storage callback errors and aggregate fetch-pipeline errors, and actual storage-origin Arrow decode attempts/successes. Each decode attempt is recorded immediately before the existing from_bytes branches. Per-block maps hold at most256 keys and overflow invalidates the experiment. The observation shares the actual reader pin-map lifetime and is passed explicitly to the observed provider helper; it is not a resettable provider-global counter. Default observations remain absent. Root opening and root decoding happen before each measured operation and are excluded. Cache reconstruction decoding is outside storage callback counts; the retained fixture uses the existing plain Foyer cache.

The existing opt-in pin profile exposes the new maps/counters. Reset happens at the CLI operation boundary, before request futures; snapshot follows the awaited result and existing cleanup. This experiment uses normal successful local operations with no outstanding futures at reset. Generic remote detached-fetch cancellation accounting is not claimed. The measured exact-scoring wall interval ends before response mapping and JSON output; provider obtain and decode nanoseconds are aggregate stage durations which can overlap and must not be summed into wall time. Fetch transfer elapsed and provider memory, physical I/O, network traffic, allocator peaks and RSS decomposition are unmeasured.

Four actual rerank contract tests include a new cold-contention/warm-cache test. A fresh plain provider opens the saved fixture after write/flush. The first concurrent operation verifies per-ID mapping, request partitions and actual decodes without asserting a race-dependent duplicate count. A serial reader sharing the now warm provider verifies16 obtains/hits and zero storage-origin decode attempts, exact output and zero terminal vector pins. A missing-vector operation retains request accounting and ordinary cleanup. The three existing release/clone/error tests remain selected. The Local storage dispatcher returns a missing-file error before invoking a decode callback; callback error count is therefore zero while the aggregate fetch-pipeline error count is one. A separate block-manager unit verifies missing storage error accounting and the256-key overflow latch. No save/recovery failure campaign is introduced.

The sole native controller uses representative-compaction-v3/runtime-attempt1, exact1072-file inventory and no corpus growth. For each of two owners, an independent unprofiled process produces the reference for32 fixed evenly spaced IDs. Fresh default and serial-release processes each execute that same set twice, first with a fresh provider and then a warm repeat. Every complete result/count must match the reference. The controller retains all ten responses, exact block identities, counters, stages and normal terminal cleanup. Fresh process/provider does not mean OS-cold. A meaningful positive mechanism requires default fresh storage-origin decodes at least twice the number of required blocks and at least four extra decodes; no implementation follows merely from nonzero counts.

Build/test scope uses Rust1.92, locked/offline, two jobs, debug0,20GiB floor and1200s per command. Run the four rerank_pin_contract methods, the one refinement_observation_missing_block_and_cardinality blockstore method, then bounded bench build. Retain exact source end hashes/logs/binary; exact binary review precedes native execution.

Native runtime uses Python3.13.5, at most one reader child alive, Tokio/Rayon2threads, each request5s and a300s work alarm. This limits configured concurrency; it is not an OS CPU quota. Terminal waited-child OS maxrss must be at most2GiB; this is observed highwater, not a hard instantaneous memory cap. Output is observed at most50MiB and raw responses at most8MiB. Normal Reader.close owns cleanup; no group signal, process sampling, cloud access or denied-operation retry occurs. Full fixture hashes are outside the measured operations and must match before/after. No optimization or additional run is admitted by this source freeze.
