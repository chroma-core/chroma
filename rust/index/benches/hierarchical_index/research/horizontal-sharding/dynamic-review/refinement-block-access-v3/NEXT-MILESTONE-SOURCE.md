# Reduce repeated query bytes in adapter batches

The next recommended milestone sends a query vector once per adapter batch while preserving every operation. The retained16-query analysis models request bodies decreasing from5.02MB to0.350MB, about93.03%, when identical repeated query arrays are represented once per batch. These are reconstructed component bytes, not recovered complete historical HTTP bodies or measured physical network traffic. A paired actual serializer test can establish the byte difference directly without changing search quality.

The client already groups operations by destination adapter and sends one HTTP body per phase. Each item currently carries a nested query array. The receiving adapter validates the tree, subtree membership, unique subtree IDs and deadline, then dispatches each item unchanged to its pinned Rust child. An opt-in protocol can move the common vector to one batch field and omit item query fields. The adapter must validate and reconstruct an owned immutable per-batch query before starting any child call, preserve exact float values including negative zero, and keep all subtree/snapshot/generation/operation/node/local-ID/budget/order/deadline bindings. An explicit version and reply echo must reject silent fallback. Inline-plus-shared ambiguity, mixed queries, missing vectors and nonfinite or wrong dimensions must reject before dispatch. The default wire format stays unchanged. No cross-request query cache or new service is needed.

The proposed proof combines strict Python contract tests, actual paired serialized body accounting for identical operation lists and a tiny complete coordinator/native-reader trace comparison. The real-data reconstructed16-query workload can supply a separate synthetic serialization replay if its exact inputs and missing historical fields are disclosed. The adapter still writes the query to every Rust child, and every required distance calculation remains. No posting CPU, latency, recall or production-network benefit follows solely from HTTP byte reduction. A realistic latency proof requires an actual representative remote adapter workload and fixed recall/hardware/cache conditions; that is outside the retained local measurement.

Posting scoring is also a concrete subsequent opportunity. The default leaf scorer first loads and filters actual postings, then computes a residual/quantized query for every selected leaf and scores every current code copy. Those distance calculations and per-leaf centroids are essential under the current search policy. It then materializes every physical hit, deduplicates minima in a full map and sorts every unique distance because the selected-leaf wrapper passes an unlimited internal budget; only afterward does it retain the external budget and cutoff ties. The pilot finds53,523,050 unique candidates across1689 calls, median26,136 against budget1000;1674 calls exceed that budget. A tie-inclusive linear boundary selection followed by sorting only retained candidates can remove avoidable full sorting, but stage timing is needed before attributing the260ms posting-stage lower bound to sorting. Current streaming mode already offers bounded candidate storage, while paying per-entry version lookups and clearing all leaf arrays each operation; it is not automatically a CPU win. No scoring implementation or quality retune is activated by this analysis.

The source references are the client batch constructor in subtree_transport.py, adapter dispatch in subtree_server.py, default selected-leaf wrapper in reader/remote.rs, score_leaves in reader/reader.rs and version-aware posting loading in reader/persistance.rs. This proposal remains source-only until the parent chooses the next coherent implementation budget.
