# Reader memory diagnostic

The diagnostic tests whether decoded provider blocks remain resident after reader-owned posting arrays and reader pins are released. A second hypothesis is that keeping two saved generations open adds reader metadata while sharing some provider blocks. This is a bounded correctness diagnostic on one existing eight-row generation and its nine-row successor, not a throughput or query-strategy experiment.

Three fresh native processes use the same query, M=1 and sorted leaf order. They retain posting arrays, release arrays after each operation, or stream postings with the reviewed candidate collector. Each process records an empty-provider baseline, the first generation opening, progressively visited leaves, two repeated all-leaf operations, separate exact reranking, both saved generations open, the older reader dropped, all readers dropped and the provider explicitly cleared. Result IDs, distances and distinct counts must match across policies.

The cache wrapper remains confined to the new benchmark. It wraps the unchanged plain in-memory Foyer builders and records cache gets, obtains, hits, misses and inserts. A separate census reads known keys through the underlying cache and immediately drops returned clones. The census changes access recency and underlying cache telemetry. It does not measure a replacement policy or storage I/O. Census keys represent observed keys; missing keys do not provide an allocation census outside that set.

Block size is the existing rounded Arrow-buffer payload estimate. Root size is serialized metadata size. These values exclude allocator control structures and do not establish unique heap allocations across shared buffers. Reader pins and provider blocks can refer to the same buffers; their byte estimates must not be added as an independent total. Reader metadata and posting counts use the existing length-based payload counters. Candidate map capacity, bitmap and returned output-vector capacity remain separate, and their maxima do not establish the simultaneous whole-operation allocation peak. Provider decode scratch, quantizer scratch and allocator metadata remain unavailable.

The controller samples process RSS through the operating system about every 50 milliseconds, including during work. RSS is a process-level resident-memory observation and includes allocator retention; it cannot identify a particular cache or prove a transient peak. An observed sample above one GiB aborts the diagnostic. This is a sampled abort threshold, not an instantaneous operating-system memory limit.

The controller limits the diagnostic to three processes, thirty phase records per process, sixty seconds per process, three minutes overall and thirty-two MiB of aggregate output. The fixture is limited to sixty-four MiB before launch. Every process owns a fresh session; the controller kills and waits for that session on success or error. Before-and-after content inventories must match. New source, binary and raw evidence remain below sixty-four MiB. No saved index file is written, no cloud node is used and no larger corpus is prepared.

Source and controller review precede the native run. The source freeze is recorded in manifest.json. A compile-time closure inference error and a Python bytecode-cache permission error occur during preparation; neither executes the native diagnostic. The corrected controller uses a task-owned bytecode cache. Runtime results remain pending independent source admission.
