# Split preparation can use a shorter publication interval

The connected writer holds the structural mutex while fetching split inputs, clustering them, and creating posting codes. The optimized reference performs those steps before acquiring the mutex that attaches the replacement children. A bounded, speculative preparation stage is a plausible way to remove this difference, but the existing results do not measure its benefit or identify the initial root's share of lock time.

The retained 100K comparison changes balance cadence and produces different trees and work. The short arm reports 33.522595 seconds of balance and 7.839155 seconds of cumulative outer structural hold; the long arm reports 50.634535 and 35.808955 seconds. Splits are 69 versus 75, peak subtree workers are 22 versus 15, and subtree jobs are 687 versus 39. The long arm has one initial 100K leaf; the short arm first balances 4,096 rows. These observations support investigating large split preparation, but they do not establish that the initial root accounts for the hold increase. Input, search settings, allocator, and optimized matched reference still need their separate runtime comparison.

## What each implementation locks

The connected leaf split acquires the global structural mutex before reserving topology work and entering the exclusive visibility scope. It reserves split memory before detaching the source, removes the source metadata and owner payload, filters current versions in physical row order, resolves immutable handles, and fetches vectors in bounded windows. It then runs two-way clustering, quantizes both output posting lists, installs owner payloads and full node records, and edits the parent or creates a new root. Recursive internal splits and parent centroid recomputation run under the same reentrant mutex. The outer visibility destructor flushes dirty full records before the mutex is released. Self and neighbor reassignment run afterward, outside this outer hold, although those operations can acquire their own structural scopes. These steps are the same for an initial oversized root and a subsequent leaf; the initial root takes the root-creation branch instead of parent replacement. Relevant source: `writer/writer.rs:1031–1201`, `:1813` and `:2159–2320`; input filtering is `reference_owner_adapter.rs:664`, and publication flushing is `live_node_adapter.rs:20–26`.

The optimized reference detaches the leaf from its concurrent node map, obtains resident embedding references, filters versions, clusters, quantizes, and inserts the replacement leaves without an enclosing structural mutex. Its attachment helper then takes the mutex, checks whether the source is still the root, and replaces the current parent or creates a root. Internal-node splitting remains locked. This is narrower locking, not a lock-free reference. Its packed navigation publication and concurrent-detach behavior differ from the connected writer's stronger complete-view policy; copying the unlocked detach literally would violate that policy. Relevant source in the isolated reference: `writer/writer.rs:1369–1513`, `:2052`, `:2287–2306`.

## The smallest safe boundary

A coherent candidate keeps the source visible during preparation and moves only pure preparation outside the global mutex. Under the existing order of structural mutex then visibility scope, it admits the complete split scratch budget and captures an owned source snapshot: node identity, parent, posting owner and ownership epoch, record revision, centroid bits, and the exact ordered physical ID/version/code rows. It also captures immutable full content handles. It then releases all node leases, identity guards, and visibility scopes before vector I/O, clustering, and output quantization. The prepared object owns its reservation until publication or discard; it must include the snapshot and both prepared output lists, not only the vector payload.

Publication reacquires the same structural/visibility order and validates that the source is still the same leaf, its ordered physical rows and centroid match, its owner/epoch is unchanged, its current-version selection is unchanged, and its parent/root relationship remains eligible. Validation must precede detach. A changed source discards preparation and returns to the ordinary scheduler without partially installing children; retries need an explicit bound or existing safe fallback. New child IDs and authoritative membership updates occur only after successful validation. Parent attachment uses the current relationship and preserves recursive internal split admission. All dirty credits remain held through successful flush, and a failure after detach retains the existing poisoned-writer/old-generation contract.

This candidate should initially require the existing joined insertion/balance phases and local reassignment transactions OFF. Under that policy, other reassignment mutations acquire the same structural mutex, allowing final current-version validation and publication to form one exclusion interval. The independent destination-local transaction can mutate versions without this mutex; enabling it would require additional identity-lock/revision validation and is outside this proposed change. A node revision alone is not a proof that every current-version observation is unchanged. No identity guard may survive into clustering, vector I/O, owner callbacks that can mutate, or recursive structural work.

The initial root is a useful correctness case but a weak parallel-speed witness: before its first split there is only one schedulable leaf. Releasing its preparation lock cannot invent independent subtree jobs. Subsequent leaves provide the meaningful overlap case. This distinction prevents treating a shorter measured root hold as a promised reduction in total construction time.

## What current measurements can establish

The actual structural timer includes all outer acquisitions and destructor flushing, counts reentrant nesting once, and samples hold immediately before final unlock. It combines root splits, other leaf splits, internal edits, reassignment, scheduler revalidation, and movement. It has no operation or source-leaf tag, so it cannot separate root hold from later holds. Wait sums overlap across workers and are not wall time or CPU. Legacy `critical_*` spans end before topology destructor flushing and have a different scope. Source: `writer/structural_timing.rs:1–17`, `writer/writer.rs:1037–1041` and `:1191–1200`.

Clustering and posting quantization accumulate separate nanosecond counters in source, but the retained native `before_save.counts` does not expose those durations. Full-record point-miss and flush timers, vector fetch/decode timers, and message caller/queue/service spans overlap one another and structural holds. They cannot be summed or subtracted to derive exclusive preparation wall time. The retained evidence therefore justifies a fixed-work scope test before another construction measurement, rather than a numerical speed projection.

## Proposed next change and decisive fixture

Implement one default-off prepared-leaf split path, retaining the existing publication and recursive parent logic. Use an authored tree with two independently oversized leaves and a small routing cache. Pause preparation after its bounded snapshot, prove a navigation reader and a disjoint leaf's structural work can progress while the source remains visible, then publish the prepared split. Use a recorded clustering decision or compare the exact same prepared groups so randomness does not masquerade as parity. Verify exact current ID/version/code order, full saved-vector bits, current one-copy membership, and old-generation queries.

The same fixture must change source rows or versions between preparation and publication and prove rejection before detach; move its owner or replace its parent and prove the corresponding validation; exhaust scratch/dirty credit before mutation; and inject a post-detach flush failure to retain poisoning and the old snapshot. Include an initial oversized-root case to validate root attachment, without claiming parallel overlap there. Counters should distinguish prepared, published, discarded, and fallback work. No remote execution, production edit, or new admission is part of this readiness note.

The matched optimized reference result should precede selecting this implementation. If that result confirms a substantial residual construction gap, this reference-like split preparation boundary is a higher-value candidate than another cache-size or callback-count adjustment. It targets a concrete extra exclusion interval while preserving the connected writer's stronger visibility contract.
