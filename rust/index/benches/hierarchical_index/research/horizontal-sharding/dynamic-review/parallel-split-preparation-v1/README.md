# One split loads its immutable inputs in parallel

The coordinator prepares one current split at a time. Only the reads that copy that split's vectors run concurrently. Clustering, random-number generation, neighbor discovery, current-version registration, parent edits, merges and root changes keep their serial order. This is parallel input preparation, not parallel structural balance.

An owner captures its ordered live `(ID, version, vector reference)` tuples after the existing scrub. Each worker receives a contiguous part of that sequence and opens independent readers. An embedding reference below the published append-only construction count uses the current embedding root; centroid references retain their own roots. The owner joins every worker, restores the original tuple order, and checks the tuples and current-view binding again before returning the split inputs. No actor command or coordinator mutation can interleave with this command. Later splits capture their own current state after all earlier reassignments.

The ordinary policy is zero workers and retains the existing serial owner-reader implementation. Explicit policies one and two use the same independent-reader helper, so a future paired timing can isolate concurrency from reader lifetime. The native diagnostic accepts `split_preparation_workers` only for the authoritative arm, with a value no greater than its configured thread count. The field is omitted when zero. The production and ordinary reference paths are unchanged.

Each operation uses at most eight workers. Each worker retains at most sixteen root readers and drops that map before opening a seventeenth root. A worker copies a borrowed vector into owned memory before clearing its block pins. No reader or pin map is cloned across workers. The existing per-reader block-observation map has a 256-entry cap; overflow or outstanding observations reject the preparation rather than returning incomplete measurement. All worker jobs join even if a read fails, and the earliest input error is selected after joining. The input row bound is the existing hard leaf-row limit. The helper adds no unbounded cross-operation history.

The complete output vectors still occupy `rows × dimension × 4` logical bytes. The counters report this operation's maximum owned output payload, a conservative extra temporary-vector estimate of `workers × dimension × 4`, the actual peak number of root readers in a worker, and the sum of worker maxima of reader-held decoded payload estimates. Those estimates exclude root-index allocations, map and thread overhead, provider caches, decode allocations before insertion and process memory. Shared Arrow buffers can be counted repeatedly. They are not an allocation or resident-memory bound.

The preparation span starts at the current SplitInput command and ends after tuple revalidation. It includes tuple capture, worker creation, root opening, fetch waits, vector copying, joining and validation. The diagnostic reports its summed elapsed time divided by that cut's serial balance elapsed time. These spans do not overlap other split preparation commands, but the work within them overlaps. The fraction is not CPU utilization. It excludes command enqueue/reply overhead, clustering, neighbor work and structural commit. This measurement can reject a speedup premise if preparation occupies little balance time.

The counters distinguish vector payload copied, root-reader opens, reader-map drops, provider obtains/hits/misses, successful storage-origin encoded block returns and successful storage-origin block decodes. The existing stage LocalStorage observation also includes root reads; the preparation block counters exclude root opening and cache reconstruction. A cache hit can still involve implementation-specific reconstruction. None of these counters measures physical disk I/O or network traffic. Observers run identically in the explicit one- and two-worker helpers; zero retains its original unobserved behavior.

The correctness sequence uses 225 synthetic 32-dimensional vectors across four owners and 25 explicit construction phases. A reference run records its split choices and outer-round order; the legacy, one-worker and two-worker authoritative controls consume the same choices. Assertions cover internal splits, competing parent edits, root growth, merges, root contraction, capacity placement, cross-owner immediate reassignment and subsequent scans observing the updated versions. All controls compare the normalized semantic boundary events and tree shape at each phase. This trace is not every internal predicate event. Full saved posting order, versions, codes, vectors and complete current-membership census match the reference at 192 and 225 rows; a pinned 192-row reader retains its results after the final phase. A separate test rejects changed tuple order, version, root, key or cardinality in the snapshot comparison.

The native entry-point check uses three independent 64-row synthetic constructions to test policy echo, preparation metrics and full saved census. Its stochastic trees differ, so its timings and preparation fractions are descriptive wiring evidence, not a worker-count speedup comparison. ARM local correctness does not establish Linux performance, CPU utilization, deep-tree scaling or a material reduction of the observed serial-balance bottleneck. No remote execution is authorized by this package.
