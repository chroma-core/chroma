# Compare integer scorers in the same reader binary

The reader can select a posting-distance integer kernel without changing quantization, candidate selection or query values. The comparison uses the same binary, hardware, input generations and partition-inclusive policy. It changes only the explicitly requested scorer policy. There is no global target-cpu=native build asymmetry.

The optional read command flag is `--posting-scorer-policy portable` or `--posting-scorer-policy runtime`. Either explicit policy requires `--profile-posting-selection`. Keep `--partition-posting-candidates` identical in both arms. Omitting the scorer flag preserves the existing per-code portable method and adds no scorer response fields. The explicit portable arm uses the new batch interface with the ordinary count_ones integer kernel; the explicit runtime arm uses that same interface and resolves the implementation through CPU detection.

Every ordinary operation response, including an operation error response after successful reader configuration, echoes `posting_scorer_policy` as the requested `portable` or `runtime` string. It also echoes `posting_scorer_implementation` as `portable` or `x86_64-popcnt`. An early invalid command/configuration rejects before the request loop, so no JSON operation echo is promised for such startup failures. Existing posting selection policy/profile fields remain unchanged. There is no new request-body field or cross-query cache.

The runtime policy chooses x86_64-popcnt only when Rust runtime ISA detection reports POPCNT support. That detection occurs when configuring the reader; each posting batch makes one implementation branch, and its inner code loop has no per-code feature detection. Other architectures and unsupported x86_64 CPUs fall back to portable and report that implementation explicitly. A paired Linux performance controller must require runtime implementation x86_64-popcnt before describing its second arm as hardware optimized. A runtime arm that reports portable is an unsupported-hardware/fallback result, not an optimization measurement.

The kernel changes only the exact weighted integer AND/popcount sum across four query bit planes. It processes all padded packed bytes, preserves code order and emits every physical copy. Both arms use the same floating-point correction routine in its existing expression order. Minimum-distance deduplication, first-copy bits on an equal minimum, all cutoff ties and final external-ID ordering remain unchanged. Query residual and bit-plane preprocessing already occur once per leaf; this change does not remove a per-code query allocation.

This contract is for source and local correctness work. ARM macOS can validate fallback, exact integer sums, correction bits and saved posting semantics, but cannot validate x86_64 machine code or execution. Linux compilation/code-generation inspection, detected ISA, native float-bit/candidate parity and paired full-component measurements remain requirements for the continuation task. No cloud lifecycle, transfer, controller or Linux runtime is authorized by this artifact.
