# Shortening construction lock scopes

The next lock change should protect the destination leaf and its membership update instead of serializing every reassignment behind the entire tree. The smallest reference-like candidate is an optional, bounded, nonpaged single-owner first-reassignment transaction. A split can also prepare vectors and clusters outside structural locks, but preserving the current complete-view contract requires a snapshot-and-revalidation protocol; moving the existing detach outside the lock is unsafe. This is a source-based proposal, conditional on the pending cache result, with no implementation or execution admission.

## What the locks protect

The structural mutex serializes changes to the tree's parent/child relationships. A separate complete-view gate keeps construction navigation from seeing a temporarily detached child: readers share the gate, while a structural publisher holds it exclusively. Neither exclusive placement on one owner nor a cached node makes concurrent worker access exclusive. A leaf mutation lease protects that leaf's posting append and length update; identity stripes protect membership transfer across owner actors. Immutable saved readers use pinned root tuples and do not depend on the live construction gate.

The optimized reference also uses a structural mutex. It keeps leaf split vector collection, clustering and code construction outside that mutex, then attaches replacement children under it. Its first reassignment locks the destination leaf and current-version entry together, checks the expected version, bumps it and appends the new row. Its internal split still holds the structural mutex, including child-centroid collection and clustering. Calling the reference fully lock-free would be incorrect.

The retained report does not separate clustering, quantization, owner waits and record access within structural holds, despite source counters for some of those activities.

The same arm has 24,879 outer structural acquisitions, 66 splits, one merge and 24,719 VersionMutation callbacks. Source inspection makes successful reassignment a plausible source of many acquisitions; the counters do not tag every acquisition, so their numerical proximity is not complete attribution. The source and these measurements justify testing a shorter scope, not predicting a speedup. The tree has one internal root and 66 leaves, so this evidence does not measure recursive internal-tree scaling. The pending cache pair may change access costs; this investigation assumes no result from it.

## Recommended coherent first change

Use the existing destination node lease and one owner callback to mirror the reference's first-reassignment transaction in bounded, append-only, single-owner mode. Keep other modes on the existing path until a separate transfer design proves them safe.

1. **Prepare and admit before membership changes.** Fetch the immutable vector and perform global navigation as today. Reserve destination dirty-record credit and pin headroom before acquiring the destination mutation lease, even if that record is already dirty. A concurrent flush can acknowledge an old dirty revision while a writable lease remains; admission must survive that acknowledgement. Reserve queue work and any physical-row capacity before a version bump.
2. **Revalidate the actual destination.** Acquire the existing destination lease, confirm it is still a leaf, and use its authoritative centroid and owner binding. If it disappeared or changed kind, retry navigation without changing the current version. Do not retain a source-navigation read guard or attempt a read-to-write upgrade.
3. **Publish one membership action.** Retain the normal identity guard ordering. In one owner callback, check the expected live version, deletion/overflow rules, destination presence and physical capacity; then quantize/append the row, bump the current version and mark its authoritative version dirty together. Capacity rejection must precede the bump. Do not replace the global lock with separate check/bump/append callbacks that allow another worker to consume the final slot.
4. **Finish destination metadata before release.** Update the leased node length, commit its already-admitted dirty record, release identity/node guards, then run the unchanged recursive balancing. No owner callback may acquire a node, identity or structural lock, call another actor, or perform provider IO. Preserve source invalidation ordering and old saved readers.

This removes the global mutex from a local membership operation; it does not remove necessary local synchronization. The existing full-record node lease also excludes structural removal of that destination. Multiple destination leases must not nest: the store rejects nested mutable leases and different node IDs can collide on a stripe. Restrict the first implementation to the existing one-current-copy policy, release the lease before recursion, and keep the established node-before-identity-before-owner order.

This candidate needs an unconditional held dirty credit because global serialization currently excludes some flush/lease races. Revision-aware flush acknowledgement preserves newer committed changes, but it does not by itself guarantee a previously admitted writable draft can still commit after another flush cleans its entry. Keep failure-before-bump tests for this boundary. A post-bump metadata/publication failure must poison the writer and retain the last valid saved generation; it must never return a successful partial transaction.

Cross-owner reassignment cannot use the same single callback: it removes source current state, installs destination state and advances home authority under an identity guard. It also needs destination capacity reserved across that handoff. Preserve its existing structural protection for this first candidate; a future distributed transfer protocol must replace that protection explicitly.

## Moving split preparation later

A second coherent change can leave the old source attached while preparing a bounded replacement. Capture its ordered physical rows, centroid, parent, posting owner/epoch and record revision under the complete-view read scope and source lease. Reserve split payload and transaction headroom before copying; release every structural, node, identity and owner guard before vector IO, clustering and code construction. Keep prepared tuples and codes within the existing split budget; do not move their memory outside accounting.

Acquire the structural mutex, then the complete-view write scope, then the source lease in that order. Compare its incarnation, centroid, ordered membership/version snapshot, owner binding and current-version filter within this short validation/publication interval. New appends, scrub compaction, parent movement, owner movement or changed eligibility must reject the stale preparation before detach. In the bounded append-only owner path, existing-ID version bumps occur within reassignment's current structural transaction; changing that transaction as recommended above means split publication must instead hold the relevant sorted/deduplicated identity stripes through final validation and attachment, or introduce an equally explicit exclusion. A stale snapshot cannot rely on a global mutex that no longer excludes those bumps.

Only after validation should the publisher detach the source, install children, update current parent/root relationships and flush the complete structural change before releasing the write scope. Final authoritative metadata/current reads can still wait inside that interval; the proposal moves vector collection, clustering and code construction rather than claiming to remove all IO. Keep tree-before-write-gate ordering and never hold a node lease while waiting for a gate that another writer holds while waiting for that node. Allocate publication reservations before detach; recursive ancestor edits must retain their credits through the outer flush. An aborted preparation must leave the source readable and its work queued, with a bounded retry/defer rule rather than a random retry-to-success loop.

This split design is plausible, but exact ordered revalidation can repeat substantial work. Source revision alone does not detect an ID version bump that has not yet caused a leaf scrub. Parent-only changes may cause conservative rejection. Those are implementation costs to measure, not reasons to weaken validation or silently accept a different tree input.

## Smallest discriminating correctness fixture

Reuse the authored full-record fixture with a tiny clean cache, two normally occupied destination leaves and an unrelated structural branch. Keep identities, candidate order and selected leaf decisions fixed; compare against the current transaction, not independently stochastic trees.

- Hold the structural mutex on the unrelated branch and show a valid local first reassignment on a disjoint destination can complete under its destination/identity lease. A move touching that destination must still wait. This proves scope separation, not contention speed.
- Retire the selected destination between navigation and acquisition. Verify Retry leaves version/postings unchanged; fresh navigation selects a replacement and eventually produces exactly one current copy. Separately change the expected version and verify the newer membership wins.
- Compete two destination leaves for the owner's last physical slot. Exactly one action may bump/append; the rejected action must retain its prior live membership. Repeat with colliding node/identity stripes and opposite request order to verify progress without nested lease expansion.
- Flush after a writable draft is admitted but before its commit, while another transaction consumes available dirty capacity. The held credit must still permit commit, or rejection must occur before membership mutation.
- Verify ordered posting/code bytes, current vector bits and a pinned old-generation reader after subsequent split/merge and save. Preserve queue epoch/requeue behavior and all source/destination rows on rejected preparation.

A later split-preparation fixture should pause after preparation, append or reassign one source row, and verify rejection before detach. Its unchanged branch should also prove exact prepared tuple/code parity with a fixed clustering decision tape. Do not conflate those additional split tests with acceptance of the smaller first-reassignment scope change.
