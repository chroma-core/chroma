# Plan only: move scrub validation to physical owners

A shared version-map pointer cannot cross process or machine boundaries. The measured follow-on for physically separate owners is to amortize scrub validation, which accounts for most backend current lookups, instead of turning every read into a transport request. This plan is not implemented or authorized for execution by the current ablation.

A scrub removes rows whose recorded version no longer matches the authoritative current version, preserving the existing swap-removal order and code bytes. A source posting can contain stale rows whose current version belongs to another owner, and a newly registered destination row can temporarily precede installation of its version authority. Therefore source-owner absence alone cannot certify staleness during a transfer. A fixed snapshot of versions cannot replace live validation across immediate reassignment.

The smallest candidate is a bounded scrub transaction over at most 64 row identities. Outside any owner callback, a coordinator obtains the source row identities and leaf revision, acquires the existing per-ID transfer locks in a consistent global order, and rechecks owner identities. It groups authoritative version requests by current owner and asks each owner to read its actual map. It then asks the source owner to validate the leaf revision and apply the ordered swap removals before releasing those ID locks. Any changed leaf identity or revision requires a fresh attempt under the same supported construction protocol, rather than applying stale flags. The request carries exact leaf/row/version identities, and the reply reports actual validated rows and removed code spans. At most the relevant owner groups and one source callback replace up to 64 individual current calls; the actual number depends on ownership diversity.

Lock ordering is a prerequisite, not a detail to infer. Existing registration takes structural/node state and the per-ID lock before owner calls. A scrub must not hold a conflicting node or actor lock while waiting for an ID lock whose holder needs that same node or actor. Owner callbacks must never acquire transfer locks or synchronously call another owner. A concrete integration must prove its structural/leaf revision protocol, sorted ID-lock ordering, atomic ownership publication and progress against actual registration, split and placement paths before this transaction is sound. No timeout or recovery protocol is supplied by this plan.

NPA eligibility keeps per-row live version checks and immediate global reassignment. Prevalidating a whole NPA batch can miss version changes caused by an earlier row and is outside the first scrub-only cut. An eventual owner-local predicate result would need a version-bound token rechecked at versioned registration, with explicit ordering and evaluated-ID semantics; it cannot reuse the current direct pointer as a distributed cache.

A future fixed-decision test must compare exact scrub order, current versions and code bytes; force transfer between source removal and destination installation; exercise source-owner changes and concurrent leaf replacement; and verify saved current membership with no central mutable version mirror. The runtime decision should depend on the current ablation's actual work-qualified result. No implementation, transport, cloud run or larger fixture follows automatically from this plan.
