# Major performance opportunities and comparison rules

The selected first milestone removes repeated global parent admission from appends; its paired run now verifies exact work elimination. The next query opportunity is reducing exact-refinement data movement while preserving the existing candidate set and exact distances. This recommendation is conditional on stage counters confirming that refinement dominates on our retained real-data workload. The supplied 40M Wikipedia diagnostic reports 712.7 ms refinement within 810.9 ms cold latency, versus 29.7 ms warm latency; those numbers are external session evidence, not independently reproduced FineWeb results. They motivate a hypothesis rather than a comparative claim.

## Ranked opportunities

1. **Read refinement candidates by block once, with bounded concurrency.** Resolve exact candidate IDs to persisted blocks, group them, fetch/decode each required block once and emit the same owned distances. Preserve candidate membership, version visibility, output order/ties and FP32 arithmetic. Measure unique required blocks, fetches, encoded bytes, decodes, held-block highwater, stage latency and end-to-end latency. This directly targets the cold/warm gap without first changing recall. A one-block-at-a-time implementation can save references while losing latency; compare bounded batches rather than assuming serial release is faster.
2. **Build and maintain partitions in bulk.** Admit the immutable parent once per batch, avoid checking every old version for every new vector, and avoid repeatedly materializing posting arrays during construction. Our current per-addition loop is O(N × added rows), and the supplied 40M build reports 779.92M loaded posting entries for 40M final rows. Separate this amplification from useful scoring, balancing and final output. SPFresh supports the principle of local partition maintenance, but its dynamic benchmark is not a bulk-build result.
3. **Reduce the amount requiring full-precision refinement.** After the exact-fetch path is efficient, evaluate stronger quantized scoring or bound-guided refinement at matched recall. One-bit or four-bit code size is only one component: authoritative vectors, factors, IDs, codebooks, records and retained copies remain charged. This requires a quality experiment and cannot inherit a paper's recall guarantee for our metric, data or implementation.
4. **Reduce routing and network work as owner count grows.** Replace flat all-owner root scoring with a bounded hierarchy and consistent global candidate reduction. This is material to the 100B model, but changing a frontier changes recall. It should follow a held-out quality protocol rather than silently lowering the beam.

## Acceptance for the next coherent milestone

The completed counted-parent milestone has independent acceptance in `poc-counted-parent-write-v1/independent-complete-runtime-review.json`. Any next query milestone should implement one source-frozen block-aware refinement path only if retained real-data counters confirm repeated or fragmented fetches. Use the same saved tree, exact candidate lists, fixed queries, metric and precision for both implementations. Run correctness and instrumented stage tests first, then a bounded representative retained real-data replay large enough to expose multiple blocks; the98-row fixture is a correctness gate, not performance evidence. Declare the precise cache state. A fresh process is provider-cold but does not clear the operating-system page cache. Record warmups, repeated paired order, per-query latency and raw counters, thread count, concurrency, CPU/SSD/RAM and binary/source hashes. Set dataset, query-count, time, disk and memory budgets before execution; no automatic corpus growth or cloud allocation follows from this review.

Exact-output parity is mandatory for this first optimization. Measure end-to-end time and refinement time separately so a kernel gain cannot stand in for system improvement. Report bootstrap, source verification and oracle work separately; do not remove them from one timed path alone. A useful target is a substantial reduction in refinement fetch/decode amplification with no end-to-end regression, not a guaranteed speedup chosen before a baseline. If fetches are already unique and decode is not dominant, stop that implementation hypothesis and choose bulk maintenance from the measured evidence.

## Standard for a competitive claim

A defensible claim names the exact dimension improved: build wall time and core-hours, peak RAM, index bytes, update amplification, end-to-end query latency or throughput at matched recall. Match dataset bytes/hash and split, dimension/type, metric/normalization, k, recall definition and tie policy, held-out queries, thread/concurrency and cache state. Include full vector/refinement storage, quantizer factors and IDs, authoritative record copies, build scratch and replication. State mean and tail separately; report repeated raw runs and parameter-selection cost. Freeze baseline versions and disclose any index training, CPU SIMD or accelerator difference. A Pareto improvement over our own baseline is a valid major result. It is not industry SOTA without credible contemporary baselines under these same conditions. No source surveyed here establishes that our current POC is SOTA.
