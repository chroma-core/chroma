# Posting-array retention check

The hypothesis is that visited leaves accumulate owned posting arrays even after raw block pins are released. A retained, admitted native reader opens a real eight-vector, two-leaf snapshot. Each leaf contains four live vectors. Scoring the leaves separately retains one then two leaves: 116 then 232 bytes of posting payload, or 132 then 264 bytes including leaf centroids. A later root-description request retains both arrays. Posting and vector block pins are zero after every response. The full requests, responses, snapshot path and reader hash are retained in `raw.json`.

The optional policy releases owned posting arrays after each completed operation, including error responses. The worker constructs its response before releasing arrays. Its default behavior retains arrays. The existing reader helper preserves topology and quantized navigation centroids, and later scoring reloads live-version-filtered postings. The storage provider cache is unchanged. This policy targets retained arrays between operations; it does not bound the posting arrays simultaneously materialized for one selected-leaf request, the candidate vector, transient decoding, provider caches, process RSS or concurrent readers. The reported byte counts describe array payload rather than allocation overhead.

The focused replay recipe compares every logical operation-response field between the default and optional policy. Only elapsed time and memory instrumentation are excluded. It includes reload, exact reranking and a malformed request. Native compilation completes in 5.18 seconds using the existing offline target cache; independent source/native admission passes for the bounded replay. Nine operations per mode preserve every logical response field. The optional mode retains zero materialized posting arrays after each success and error response, reloads released leaves correctly, and preserves exact selected-ID reranking. Both readers exit with status zero under a five-second watchdog and verified cleanup. Full raw records are retained in `parity-runtime.json`. This check is a correctness and memory-accounting fixture, not a latency or query-strategy benchmark.
