# Compare cache partitions without changing query decisions

This runtime asks whether the existing cache shard count causes avoidable repeated vector fetches on the two previously affected cells. It reuses the exact accepted Linux Code4 binary; there is no build, source deployment, new quantizer, corpus or tree. The four cells are reference four-bit with64 and one shard, followed by owner one-bit with64 and one shard. Every cell keeps256 weighted block units,4096 root-cache entries and clear_after_operation=false. The shard parameter applies to both caches, so root partitioning changes too, although root capacity and saved inputs remain the same.

The frozen template pins the binary bytes/hash and all saved manifests, maps, query vectors, prefix GT and saved leaf reports. A compact decision file binds every warm-up and retained response to its prior ordered IDs, FP32 distance bits, numerical work counts and selected-leaf order, plus unordered pretrim/retained candidate sets. It also pins four-bit code and FP-source centroid digests. Cache policy echoes must match. No response with changed numerical work or decisions is accepted. Existing stage joins remain outside query timing. Vector observer requests can include warm-up centroid loads in addition to the200 exact-rerank gets, so the counters are partition-checked rather than incorrectly equated to rerank work.

Each cell has ten seconds and the four share forty seconds under a separate absolute deadline. Each uses the same sixteen warm-up requests and sixteen retained requests, per-level beam32/k100/rerank2 and four configured construction/runtime threads as the prior readers. Actual selected leaves and evaluations remain checked through the fixed decision digests. There is no automatic retry, seed search, size increase or policy sweep. Missing binary/input bindings, child failure, timeouts, incomplete observations, changed cache echoes or changed decisions stop the run and preserve partial metadata.

Attribution is decided separately for each tree. A64-shard baseline with zero retained storage callbacks is inconclusive because its fresh randomized hash assignment does not reproduce the prior misses; the one-shard cell still runs as prespecified, and the baseline is not retried. If the baseline has callbacks and one shard has none, the result is consistent with mitigation by changing cache partitioning. If one shard still fetches, report that it did not eliminate fetches. None of these outcomes reconstructs the original hash seed or proves a latency ratio. Encoded storage returns are successful vector-root payload bytes, not physical I/O or whole-query traffic. Capacity targets are soft weighted targets rather than process-memory bounds; no blocks are pinned across query boundaries.

Three local test methods pass using actual retained responses and GT/leaf/map metadata with every child process intercepted. They cover four-cell success, inconclusive completion without retries, child exit7, changed numerical decisions, changed policy echo, wrong binary and expired deadline rejection, plus set-order-insensitive candidate digests. No AWS, network, watchdog, corpus or native process executes in these tests. Two wrong-working-directory test setup attempts and the failed overly strict warm-up request-count guard are preserved. The last is corrected from equality to a lower bound because actual warm-up centroid reads are separate from exact reranking. Accepted underlying cache-mechanism tests and native source suites are not repeated.

Run `python3 run-cache.py --spec FILLED_SPEC.json` only after external admission supplies a fixed absolute deadline. The binary descriptor stays exact; the filled spec cannot substitute another binary. The package contains no lifecycle code, controller or rebuild tool. Original saved manifests/maps remain unchanged. The resulting metadata is bounded to50MiB after the run; direct child timeouts do not prove termination of arbitrary detached descendants. Existing bounded retrieval must collect only the declared output files, not saved stores.
