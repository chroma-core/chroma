# Repeated vector fetches have a cache-capacity explanation to test

The retained run performs real repeated storage returns and decodes across queries. It does not show duplicate fetches within one query. Code4 reference fetches four recurring blocks46 times across sixteen retained queries; one-bit owner fetches three recurring blocks27 times. Every query-block pair has at most one pin miss, provider obtain, storage callback and decode. All six cells clear reader pins once, begin with no pins and peak at sixteen blocks. Pin release exposes whether the provider retained a block; it does not itself clear that provider cache.

The configured capacity can be stranded in separate hash buckets. The tiny reader’s default block cache has256 weighted units divided among64 shards, so each shard gets four units. A block’s weight is its decoded payload rounded up to MiB, with a minimum of one. The observed sixteen-block pin peak is about25.6MB; blocks of that scale commonly weigh two units. A few such blocks sharing one shard can exceed four units while most of the global cache remains unused. The existing Foyer plain-cache constructor uses randomized hashing and independent shard capacities. It performs synchronous in-memory insertion and lookup, so delayed background admission is not the source path here.

A fixed local mechanism test reproduces that exact capacity pattern in the actual Foyer plain-cache wrapper. Four distinct keys deliberately share a hash and each has weight two. Their demand is eight units against256 global units. After priming,64 shards produce32 misses in32 repeated obtains; one shard at the same total capacity produces zero. Returned values and order remain exact. This proves shard fragmentation can cause repeated obtains despite global headroom. It does not reconstruct the historical UUID bucket assignments, which were not recorded. The retained observer also omits individual decoded block weights, other cache occupants and eviction reasons, so whole-cache pressure cannot be excluded solely from those logs.

No production or default behavior changes are justified by the incomplete historical attribution. The only source delta is this cfg(test) mechanism case. There is no pin-all cache, added residency, changed generation visibility, query change or cloud action. The existing explicit cache policy can already reduce shard count without raising total weighted capacity. That is a bounded candidate mitigation, not a demonstrated fix for the old processes or a general cache recommendation.

The smallest proposed attribution uses the accepted native binary and exact retained request files, with no rebuild or new quality sweep. It compares64 versus one shard at the same256-unit block/4096-entry root targets for the two observed problematic cells: reference four-bit and owner one-bit. Four children have ten seconds each and forty seconds shared; original snapshots, queries, policies, results and downstream work stay fixed. The root cache shares this shard parameter too, so its partitioning changes, although its capacity target and saved root inputs do not. A fresh64-shard process can choose a nonconflicting hash assignment; if the misses do not recur, report the result as inconclusive rather than retrying. Compare actual per-block misses/returns/decodes and exact numerical outputs, not a latency ratio. Weighted targets remain soft targets rather than RSS bounds. This proposal does not authorize execution.
