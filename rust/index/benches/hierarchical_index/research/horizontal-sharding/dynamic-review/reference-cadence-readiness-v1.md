# Reference-like balancing cadence readiness

A 100K first insertion batch is the next small policy comparison if epoch 12 remains correct and destination-local reassignment does not already remove most balancing cost. It asks whether repeated balancing of changing small trees creates unnecessary work. It changes the construction trajectory, so it is not a fixed-work speed comparison. Moving split preparation outside the structural lock is a larger correctness change and should follow only if the remaining lock occupancy justifies it. If epoch 12 exposes a correctness failure, repair that first; if it leaves very little balance cost, reassess priority rather than automatically running either experiment.

## What the reference does

The exact retained optimized reference groups the first million insertions into 100K logical batches when the requested checkpoint exceeds 100K, then balances after each batch. Later million-vector checkpoints use one checkpoint-sized insertion batch. Each insertion batch routes against one stable tree with 32 workers, joins their per-leaf changes, regroups them, and flushes postings before balance starts. The harness loads the complete checkpoint input separately. Its writer keeps shared resident vectors and does not impose the connected engine's explicit split-byte reservation. This is not evidence that split scratch or input residency is free.

These facts come from commit `bec6e7213b37ca97066545535bc82d4252f9c0dc`, benchmark `rust/index/benches/hierarchical_spann_profile_quantized.rs:1251–1299` and writer `rust/index/benches/hierarchical_index/writer/writer.rs:608–659`. The retained primary reproduction is `dynamic-review/fast-reference-reproduction-primary.txt`. It specifies Wikipedia 1024D, Euclidean distance, 32 insertion/32 balance workers, branch 100, split 2048, merge 512, FP navigation/NPA, tau 0.5, level taus `[_,_,0.30]`, RNG factor 0, and checkpoint snapshots outside the timed construction. Those settings and data do not establish comparability to the present 768D retained prefix.

## What the connected diagnostic does

The accepted epoch 11 byte-cache arm uses 25 logical insertion/balance cuts, including the final partial cut: 100K rows, `balance_every=4096`, staging at most 8192 rows, 64-row stable windows, and 32 workers. The diagnostic currently calls `add_phase` once per staging chunk, and the writer joins and flushes each bounded worker window before continuing. Increasing the logical cut does not require buffering 100K input vectors or 100K leaf deltas. Staging and stable-window limits can remain unchanged while the routing topology stays unchanged throughout the larger insertion interval. Immediate current-version and posting visibility remains required.

This preserves the reference's stable-tree routing idea but not its full-batch regrouping or packed navigation initialization. Epoch 11 records 1568 stable windows and 37023 owner registration calls. With one initial root, larger cuts may make bounded windows group more rows into that leaf, but the first root split is correspondingly larger. Neither fewer callbacks nor less NPA work is guaranteed. Existing buffered-window counters distinguish collection, flushes, actual registration calls and flush-length distribution; their elapsed sums overlap across workers.

## The concrete admission blocker and minimal change

The existing binary already accepts a larger `balance_every`. Its configured `split_rows=8192` rejects the first 100K root before detach. The smallest coherent candidate changes only reviewed specification limits: set `balance_every=100000`, `split_rows=100000`, and an explicit aggregate split reservation budget. Keep 8192-row staging, its 128 MiB working admission, 64-row/1 MiB stable worker windows, 32 workers, decoded cache, queue policy and all construction/placement/visibility settings fixed. No new clustering algorithm, delayed membership publication or split lock redesign is needed for this first 100K workload.

At 768D, the current model charges 112 bytes per Code1 code and a 24-byte temporary ordinal tuple. Its wide split admission is `rows * (3072 + 256 + 224 + 8 + 24) + 49152 + 65536`. A 100K configured split therefore reserves **358514688 bytes**, including the bounded ordinal-to-full-ID table. The source reserves this configured maximum for every active split, even a smaller descendant. Five nested levels across 32 workers conservatively total **57362350080 bytes (53.423 GiB)**. The current 8 GiB budget cannot admit that modeled extreme. A declared **64 GiB aggregate split reservation** covers it without allocating 64 GiB up front; it is an admission budget, not an RSS prediction or hard allocation limit. One 100K root alone reserves about 342 MiB. Payload vectors alone are 307200000 bytes.

This arithmetic follows `owner_vector_store.rs:51–67,102–106`, its existing 32-by-five admission fixture, and `writer.rs:22,1043–1068`. The split reservation remains alive during NPA/recursive balance. Structural serialization can reduce simultaneous clustering, but does not justify counting only one live reservation. Allocator capacity, provider/cache/root indexes, actor postings, thread stacks, caller-retained arrays and RSS remain separate. The 384 MiB decoded cache is another separately accounted payload. Host/RSS/output admission must be reviewed independently; no remote resource estimate or execution is approved here.

For the first 100K batch, the initial root contains exactly 100K appended rows. Each balance operation scrubs before checking the split condition (`writer.rs:642–674`), and admitted single-copy append-only membership bounds its current rows by the input count. The 100K current-row bound is not a universal physical-row bound: stale duplicates or concurrent appends after scrub can increase a descendant payload. The configured 100K physical cap remains fail-closed before detach; an admission rejection yields an inconclusive bounded candidate rather than an automatic cap increase. Physical stale copies, dirty work and any unfinished balance still require actual checks. A later 100K cut into an already populated leaf needs at least the retained occupancy plus the incoming cut, or another justified row bound; this note does not authorize later million-scale cadence. Balanced publication must still pass the existing one-leaf copy limit and pending-work integrity gates.

## Actual parallel work and decision evidence

The first unsplit root supplies one eligible subtree job regardless of a requested 32 workers. The owner dirty scheduler groups eligible tickets by existing frontier region, runs nonempty groups concurrently, and joins one claimed page before the next (`writer.rs:739–756`). New leaves permit more jobs in later rounds. The historical reference also cannot obtain 32 independent tree partitions from an initial single leaf. Do not report 32 configured workers as 32-core utilization or promise that a larger first batch improves parallelism. Epoch 11's byte-cache arm reports peak 32 subtree workers, 735 actual jobs and one simultaneous owner callback; these are aggregate observations, not first-root concurrency.

The available comparison records add/balance/placement/save/census times; actual splits, merges, reassignments and NPA evaluations; stable-window grouping; queue reads/commits; mutex outer hold/wait; full-node point-read/miss/flush elapsed; vector requests, cache returns and complete provider decode/byte counters; owner operation queue/service/caller spans; subtree jobs and peak workers; sampled/process RSS; split peak reservation/rejections; and final shape, pending work, membership/vector bits and old saved generations where exercised. Use before-save counters for construction. Mutex hold includes topology flush; callback, split/NPA, gate and worker spans overlap and cannot be added into wall time. Existing joined progress lines preserve coarse cumulative work if the root split times out, but do not provide a separate clustering-only phase line.

The smallest future correctness gate is a fixed-order insertion interval crossing several staging chunks, with a final partial chunk, no intermediate balance, and an initial root larger than 8192 rows. Verify pre-detach row/byte rejection below admission, successful balance at admitted capacity, exact membership/vector/code binding and saved old/current generations. Compare worker-window registration order and stored bits under a fixed tree, not independently stochastic final trees. No tests, builds, source edits, benchmark or cloud action occur in this assessment. After epoch 12 interpretation, prefer one admitted 100K-cadence comparison over split-preparation refactoring if repeated balance/NPA work remains consequential; otherwise select the next question from actual residual costs.
