# Bounded immutable vectors during construction

The construction kernel fetches full vectors through immutable content handles instead of retaining every vector in its central embedding map. Owners still hold the live posting and current-version authority. An immutable handle identifies persisted bytes and stays valid after membership versions or placement change; it never replaces a live version check. This opt-in local prototype preserves the existing global reference scheduler, navigation, structural locks, and reassignment rules.

The wrapper accepts unique dense append-only IDs. Before routing a batch of at most 64 rows, it forks and flushes an immutable embedding root. Staging creates content handles but no current authority. Successful first posting registration installs its handle and current version together in the destination owner, then publishes the directory entry while holding the existing per-ID transfer lock. If the first target disappears, the pending version advances locally with the reference mask; authority stays absent until registration succeeds. Replacement and application deletion reject before mutation. Internal stale-row removal, version bumps, transfer, split, NPA, and merge remain supported.

A fetch resolves the current owner's immutable handle under the existing ID lock, releases all ID and actor guards, and then reads storage. The owner cache releases its own lock before misses. A fetch admits at most 16 handles, each owner retains at most 32 cached vectors, and at most four fetch slots are active with at most two per owner. Each slot owns at most one reader at a time and copies the vector before dropping its pins. Exact dimension and content-bit hashes are checked; missing registered bytes or handles fail explicitly. The original later live-version checks remain in place, so a transfer during a fetch preserves immutable bytes without freezing membership authority.

The kernel retains at most 256 full-vector tuples for one split and at most 64 vectors for one neighbor-predicate window. The split capacity is checked before detaching its source leaf. The input window, staging writer, cache, split tuples, recursive caller arrays, and provider roots/blocks have different lifetimes. The reported cache limit is not a total RSS limit. Global topology, u32 identities, per-ID directories and locks, owner handle metadata, and joined posting/version publication still grow with the index. Caller-owned input and recursive temporary arrays are disclosed rather than counted as cache payload.

Publication forks the latest flushed embedding root, writes the saved centroids in their distinct prefix, and publishes the ordinary five-root format. It does not clone a full embedding map or issue new embedding-set calls during save. This is logical embedding-root reuse, not zero storage write traffic: a provider may rewrite a block that combines centroids and inherited data. The joined posting/version snapshot remains a full copy. Existing immutable readers continue to reference their original roots.

## Local correctness evidence

The main fixture constructs 1,024 vectors of 32 dimensions in 16 batches of 64, using two owners and up to four reference construction workers. It exceeds the 32-vector owner caches and root-handle reuse, moves branches, then exercises split, neighbor reassignment, and merge. The final phase explicitly sets split/merge thresholds to 64/24 in both construction paths so merge is covered without increasing the input. An independently constructed reference tree and the owner tree each pass complete current-membership and exact vector-bit checks. Every saved owner posting ID, version, and code is checked against its owner state and an independent Code1 reconstruction. A reader pinned at 512 rows preserves its exact outputs after later construction and saves.

A separate fixed-decision check feeds the same five ordered ID/version/vector-bit tuples through an existing recorded reference split and replays its exact decision with fetched vectors. It proves tuple and decision fidelity, not identical full independently stochastic trees. The full-build tests deliberately do not claim topology parity or ANN quality.

The transfer test pauses an actual vector fetch after authority resolution, completes a versioned cross-owner registration while the fetch is paused, then verifies the original immutable bits and new current owner/version. Opposing ID fetch orders complete within a timeout. Invalid owner, missing handle or bytes, replacement, and application deletion are rejected. Capacity and integrity failures mark the phase unusable and prevent save. The deterministic first-registration retry test checks that no authoritative posting, current entry, directory entry, or owner handle appears before success, and that the ordinary reference-kernel path and bounded path both finish at version 2 with identical posting and code bytes.

Passing stderr intentionally contains caught negative panics. The original frozen slice and its reviewer-found retry defect remain preserved; the repair changes only that retry and its focused test hooks. No native query package or accepted saved input is modified. The wrapper keeps its existing 32-add-phase limit, so this opt-in 64-row append path admits at most 2,048 rows without a separate capacity change; the local fixture uses 16 phases. It is not a ready larger-scale construction path.

## Adverse access result and accounting

The no-provider-cache fixtures expose repeated I/O work rather than hiding it behind an unbounded test cache. The first no-cache run performs 8,282 decodes and returns 114,434,084 encoded bytes for 131,072 staged logical vector bytes. Its result remains retained. The later fixed fixture with explicit merge performs 6,424 decodes and 88,029,872 encoded bytes. These are independently stochastic workloads, not before/after performance measurements. Encoded storage-origin returns are neither physical disk bytes nor network bytes.

The current miss path opens and drops a reader per uncached vector. This is demonstrably inefficient and is the next access-design target; this milestone does not claim an efficient storage path or a throughput improvement. The explicit no-cache provider retains no block/root cache entries, but root decoding and reader pin payload are still transient work. The largest observed single-reader pinned payload in the retained fixture is 16,320 bytes, separate from the two-owner cache's 8,192-byte limit. Four simultaneous fetch slots and two slots per owner are observed; these are I/O contexts, not CPU parallelism.

The retained fixture reports staging and joined-publication elapsed separately. It stages 131,072 logical vector bytes and uses two publication forks with zero logical embedding-set bytes during publication. Provider mutation buffers, root metadata, actual encoded write traffic, allocator overhead, recursive temporary payload and process RSS are not fully measured. There is no 2M or 100B readiness, cross-host execution, remote-owner latency, quality, or performance claim.

## Scope and files

The new module owns immutable staging, content verification, bounded cache/fetch admission, and access accounting (`writer/owner_vector_store.rs`). Minimal writer integration selects owned fetches, preserves ordered tuples and live checks, and forks the vector root during publication (`writer/mod.rs`, `writer/writer.rs`, `writer/persistence.rs`, and `writer/reference_owner_adapter.rs`). All other accepted source files, the staged Git index, old source archives, and query experiments remain unchanged. This package contains source and local test evidence only; it starts no cloud operation and adds no remote runtime.
