## Memory scope and limits

Each chunk holds at most8ordered IDs and their768D centroids:24608payload bytes. Its32-byte header binds generation, parent, ordinal, dimension and exact row count. The decoded scoring cache admits at most49216payload bytes. One caller pins at most one24608-byte chunk while scoring; returned Arcs can alias cache data. Before eviction, two cached chunks and an incoming decoded chunk can overlap, and the observed peak is73824decoded payload bytes. An encoded return of up to24640bytes overlaps decoding, giving a conservative98464-byte decoded-plus-encoded upper model, outside node records, frontiers and allocation overhead. The one-chunk construction buffer has24608payload bytes plus header. The accounted parent-wave-plus-current-chunk peak is31264bytes, a conservative live-record upper accounting rather than total allocation. Frontier size peaks at128scores; it remains separate. Fixed query arrays, the two resident authority maps, Vec/BTreeMap/Arc headers, capacity slack, file-system cache and allocator/RSS are not included in the scoring-cache cap.

The immutable file generation is fixed at7; filenames derive from generation/parent/ordinal and require no whole-tree resident chunk directory. Exact ID order, dimensionality, finite FP values, extent and header binding are checked. Cache generation is fixed for the lifetime of the object. Source-child completeness is validated when authoring immutable chunks. The negative test proves root-leaf distance parity and fail-closed behavior for missing roots, missing source children at authoring, absent chunk files and wrong-generation headers. It does not promise to discover a subsequently corrupted unselected authoritative record during every packed query; such records belong to the immutable generation contract.

This result answers the first local question: exact scoring can avoid all-child node materialization while preserving the global mixed-frontier result. It does not justify enabling a production packed policy. Connected publication must still maintain child-centroid freshness through updates, split/merge/root changes and owner placement, under the complete-view gate, while preserving old saved generations.
