# Incremental admission boundary

The current authority must run its complete current deployment-validation path on each independent call. This path does not independently decode and re-audit every lower block payload: its report explicitly requires a lower reader open, and writer provenance binds the saved lower content. A recorded digest, read-only mode or unchanged size and timestamp does not enforce immutability. A new counterexample changes a canonical vector while preserving file size and modification time; the next deployment-validation call rejects that canonical-input mutation. No serialized caller receipt or trust flag can authorize skipping that audit. Recovery, restart, missing retained objects or invalidated storage versions require a complete audit.

## Current call path and cost

Complete deployment validation resolves and hashes pinned lower manifests, checks all five persisted block-family identities and the bound strict-copy audit, validates complete global ownership, hashes canonical inputs, inventories sealed lower outputs, and recomputes actual input/canonical value correspondence. Ownership-page validation audits every page and then reads the same pages again to compare owner-local offsets with flat maps. Trie validation separately audits its descriptors and pages and compares complete flat maps. The publication path then hashes shared model/canonical artifacts again and fsyncs shared objects, pages, trie metadata and their directory ancestry. Parent append/replacement checks inside the publication lock perform additional complete ownership work. These costs remain proportional to complete retained state.

A real sixteen-row diagnostic observes 33,927 returned Python read bytes across 59 opens during the complete current deployment-validation path, including 256 bytes from the 128-byte flat-page payload. Shared-object durability observes another 9,728 returned read bytes and 418 fsync calls, including directory ancestry. These counters cover Python Path.open streams and fsync calls, not Rust/provider reads, mmap, disk traffic, RSS or latency. The exact fixture, repeated pass, per-path counters and same-size mutation counterexample are retained under validation-cost-v1. Values depend on this exact bounded fixture.

## First sound reduction

The first reduction reuses owned page bytes within one validation call. The page audit returns its typed root receipt together with the exact immutable byte strings it has just hashed, checked for dense disjoint ownership and bounded by the 100,000-row cap. The same call compares those owned bytes with each saved flat-map offset. It neither rereads mutable page paths for that comparison nor accepts an older receipt from the caller. Every later call audits actual page bytes again. Default standalone audit behavior, the full flat-map oracle, trie audit, content audit and all durability fsyncs remain unchanged. This removes one repeated page read, not complete-state validation or durability.

## Changed-object manifest required before cross-call reuse

A future manifest must bind the exact committed parent deployment and candidate, all parent/new posting, authoritative-version, raw-vector, leaf and internal block roots, ID-map roots and owner-local prefixes, canonical vector interpretation and bits, flat-page and trie roots, and a reserved contiguous new-global-ID interval. Changed posting/version keys and logical tombstones require semantic coverage; retained physical files do not expose key deletion. Changed leaves require reachability, length, current-version and unique-live-ID proofs. Reassignment and topology replacement require complete preserved global-ID/value sets or a separately reviewed ownership-transfer proof. Unknown, omitted or extra changes fail closed. File inventory differences alone do not provide these proofs.

Unchanged objects can avoid cross-call payload rereads only after an actual storage authority guarantees their immutable identity and retention. Such an authority must bind object version and durability to the fully audited committed parent, pin every reused object through publication, and invalidate reuse on recovery or retention failure. The current local mutable filesystem provides no such enforcement. A later integration must use the existing complete deployment CAS; index and ownership roots cannot publish independently. This work introduces no second pointer, activation flag or production trust service.


## Frozen same-call implementation

The source candidate adds `audit_with_page_bytes` to the page module and consumes its owned owner-local byte strings only inside `validate_ownership_pages`. The ordinary `audit` still returns the same typed receipt and retains no extra payload copy. The two corrected component tests pass in 0.004 seconds. They verify receipt equivalence, empty-owner bytes, owned-byte stability and actual-file revalidation on a later call. One initial fixture attempts to mutate a read-only page and receives PermissionError; that failed result is preserved. The corrected fixture explicitly changes permissions on its owned page before corruption, and it does not treat read-only mode as a trust guarantee. Source and exact test deltas are retained in validation-pages-v1 through validation-pages-v3. The admitted tiny native method passes in 0.278 seconds. On the exact same fixture, the independent reference algorithm and same-call implementation return equal receipts, while ownership-page payload reads decrease from 256 to 128 bytes. The complete current deployment-validation path passes before corruption. A later same-size page mutation with restored modification time rejects both page and deployment validation, rejects reader construction before a backend starts, and rejects publication before probing or changing the pointer. Raw per-path counters, the exact parent record and failure assertions are retained under validation-pages-v3. Independent native runtime reconciliation passes; its receipt is `validation-pages-v3/independent-native-runtime-review.json`.

## Existing storage integration hooks

The repository provides copy-on-write identities, but the inspected APIs do not expose the immutable-version and retention authority needed for cross-call admission. Block forks create a new UUID (`rust/blockstore/src/arrow/provider.rs:479`), and root forks accept a new root identity. Block and root flushes use default put options (`provider.rs:631`, `provider.rs:819`); the storage default is Upsert (`rust/storage/src/lib.rs:507`). Local storage ignores the options and writes the key path again (`rust/storage/src/local.rs:74`). Its identity-confirmation hook is unimplemented. This is a source-contract observation, not a statement that production permissions allow overwrites.

The S3 client supports conditional create and ETag checks, but the blockfile flush call does not request conditional creation or retain the returned ETag. The generic get options expose no object-version ID (`rust/storage/src/lib.rs:545`). S3 reads fetch the current key (`rust/storage/src/s3.rs:317`), and identity confirmation compares a current HEAD ETag (`s3.rs:167`); neither call pins retention through publication. Root readers cache by UUID and fetch storage keys without a version precondition (`provider.rs:738`). Collection version files and garbage-collection file enumeration identify roots and referenced blocks, but the inspected Python deployment boundary receives no storage pin bound to their durable immutable versions. Independent source findings are retained in `immutable-provider-hook-inventory.json`.

A future integration should extend those existing blockfile/storage and collection-commit interfaces, rather than add an independent trust service. It needs a committed parent identity, a durable immutable version/content identity for every reused root and child object, a retention guard acknowledged by existing garbage collection, and recovery invalidation if any guard is lost. Changed-object coverage must include logical version/tombstone changes, not just new UUID files. Until those guarantees exist, this prototype retains the complete current validation path and skips no cross-call payload or durability work.

## Next independent memory seam

The next candidate is bounded selected-leaf scoring. The current remote scoring call loads up to thirty-two selected leaves concurrently, retains their arrays, appends every candidate to a result vector, then builds a complete distinct-ID map before taking M and preserving boundary ties. Releasing arrays after the operation does not bound those simultaneous allocations. A correctness-first optional path can process one selected leaf at a time, preserve authoritative-version filtering, and release its arrays after scoring. It must keep the minimum approximate distance per live ID across leaves; pruning each leaf before duplicate resolution is not accepted.

The candidate collector can retain a global distance cutoff at the Mth distinct ID and every tie at that cutoff. A later duplicate can improve its distance and become eligible again. Exact distinct-scanned accounting still requires bounded state: for admitted contiguous local IDs, a checked bitmap uses one bit per local row; its allocation must fit an explicit budget before scoring. Candidate/tie count and owned-byte caps must fail the complete request when exceeded, never drop a required tie or silently reduce M. A raw posting-list limit must be checked before copying arrays, including stale physical entries; provider Arrow decoding and caches remain independently bounded or explicitly outside the owned-array claim. The smallest tests compare all candidate distances/ties/counts with the complete current oracle, include duplicate copies with different approximate distances, stale/deleted versions, later-improving duplicates, repeated leaf visits and budget failure after partial processing. This is a design, not an enabled path or query-strategy experiment.
