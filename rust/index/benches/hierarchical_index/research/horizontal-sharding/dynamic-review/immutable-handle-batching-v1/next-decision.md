# Decision after the paired 100K run

The next decision depends on whether fewer handle messages reduce balance time at comparable recorded work. The baseline takes 85.015 seconds in balance, but its counters do not identify one exclusive cause. The paired run uses independent stochastic trees, so compare phase work and overlapping spans before attributing an elapsed difference to batching. Keep the one-owner sequence; transport remains deferred.

The strongest remaining serialization hypothesis is durable work-queue maintenance, followed by scalar current-version dispatch. A global structural mutex is important, but its 13.673 seconds of cumulative outer hold cannot by itself explain 85.015 seconds of balance. Near-one-core process usage also does not prove that all 32 workers are waiting for that mutex.

1. **A single home queue serializes frequent durable commits.** The baseline records 211,079 work marks, 29,632 flag-page reads and 29,874 queue commits, despite only 109 claimed pages and 746 scheduled leaf jobs. A cache miss at its one-page flag cache calls a synchronous fork/write/flush while holding the home lock; `mark` also holds the global admission lock. Alternating node IDs across 64-slot pages can therefore make eligibility bookkeeping perform far more durable publications than structural topology, which records only 69 commits. This is a consequential scheduling/storage boundary, not evidence that the queue consumes a known fraction of balance time. Its elapsed time is not separately measured. If the paired run still has tens of thousands of queue commits and near-one-core balance after handle dispatch falls, inspect one fixed queue-event tape before considering a bounded coalescing/transaction change. Preserve newer-event acknowledgement and pre-detach admission; do not replace durable work state with an unbounded resident map. Source: `owner_work_queue.rs`, `load`/`flush_home` at lines 35–39 and `mark` at line 43.
The active one-page queue cache is an explicit benchmark setting, not the queue default. The epoch 4 result records `spec.full_records.queue_cache_pages_per_home = 1`, and its runtime queue report confirms `cache_page_cap_per_home = 1`. The accepted diagnostic passes that field directly into the queue constructor (`reference_owner_diagnostic.rs:136`). The queue's default is four pages (`owner_work_queue.rs:14`), and constructor admission accepts one through 64 pages (`owner_work_queue.rs:30`). The same existing configuration can therefore select bounded four or eight pages without an engine change; that would be a separately declared future treatment, not a change to the current pair. Each flag page encodes 193 u32 words, or 772 bytes, so four/eight pages encode 3,088/6,176 bytes per home; decoded structs, cache containers and provider buffers add separate memory.

This is a fixture-specific cache-cliff hypothesis. Seventy distinct live nodes require at least two 64-slot flag pages, while the benchmark admits only one cached page. Node IDs can be sparse, and retired nodes/events can touch additional pages, so the live-node count does not prove the exact page working set or that four pages retain it. A four/eight-page result on this small tree would not predict large-tree behavior: a larger active event set can again exceed either fixed cap, and synchronous eviction commits remain. Wait for the current paired result before selecting any cache treatment or queue change.

2. **Live per-row eligibility still crosses a serial home and owner boundary.** The baseline has 1,612,410 Current callbacks and 2,821,898 home location messages. Neighbor-point adjustment checks each row's current version after pure predicate batching; reassignment checks validity again before navigation/registration. These immediate checks remain necessary across recursive mutations. Handle batching changes neither their semantics nor every location caller. If Other handle callbacks fall but Current/home dispatch and their caller spans remain high, the next candidate is an owner-local ordered live-prefix transaction that stops before the first action and reacquires the suffix afterward, rather than a stale version window or a shared-pointer shortcut. Existing prefix evidence includes substantial discarded suffix/predicate overwork, so this is a hypothesis requiring fixed-decision evidence, not automatic enablement. Source: `reference_owner_adapter.rs` current/resolve/fetch methods, and `writer.rs` FP neighbor adjustment and reassignment.
3. **Structural transactions and available work limit useful parallelism.** Split holds the structural mutex and complete-view write scope through detach, vector collection, clustering, installation, parent repair and topology flush. It releases both before neighbor adjustment. Reassignment separately serializes destination revalidation, membership bump and append under the same mutex. The queue claims at most 64 jobs and groups them by a global partition frontier; recursive balance stays within each spawned job. A depth-one tree and skew can provide fewer independent active regions than configured workers. If structural hold/wait or visibility wait rises relative to work, investigate preparing immutable split inputs before the structural interval with source revalidation, or a bounded transaction decomposition. Do not assume independent subtree beams or remove global eligibility. Source: `writer.rs` split at lines 1031–1192, reassignment registration at line 1714, and dirty scheduling at line 740.

Use the existing epoch 7 receipts, not another instrumentation build. For each arm retain add/balance time and user/system CPU; phase splits, reassignment attempts and self/neighbor evaluations; before-save home scalar/batch/messages; owner operation calls/queue/service/caller totals; vector logical gets, reader opens, copied bytes and decode count/time; queue marks/flag reads/commits/claims/scheduled jobs; actual structural acquisitions/hold/wait; visibility read/write waits; node reads/miss elapsed/evictions/commits; and actual peak stable windows/subtree jobs/fetch workers. Count differences before save separately from save/query/audit. Queue commits and elapsed balance are already observable, but queue-specific elapsed attribution is unavailable. A large commit count alone does not establish dominance.

All timing sums need their existing scopes. Owner caller includes dispatch, service and reply scheduling; queue time is nested within caller. Current callbacks, home activity, storage misses, structural hold and visibility wait overlap each other and concurrent threads. Full-record miss elapsed includes provider access/cache admission; flush elapsed nests its gate wait. Reentrant structural holds are counted once and include mutation flush, while legacy critical hold omits that flush. Cumulative waits are not CPU or disjoint wall buckets. Stable insertion collect/flush sums overlap 32 workers and can exceed insertion wall. The baseline's 0.381-second vector decode sum is not evidence that decoding dominates balance.

The work-count warning remains material: the 98,304-row phase has two splits, 1,653 reassignments and 28,771 evaluations yet takes 7.48 seconds, while the 77,824-row phase has four splits, 3,250 reassignments and 55,969 evaluations in 5.45 seconds. No per-vector slope, matched-work speedup or 100B forecast follows from counts alone. Evidence: `100k-owner32-epoch4-phase-work.json` and the epoch 4 `closed-native-metadata/result.json`. This note makes no source, test or cloud changes.
