# Reader memory diagnostic results

All three read-only policies return identical complete candidate sets and distinct counts on the saved eight-row generation and its nine-row successor. The diagnostic completes thirty-six phase boundaries across three native processes. All process exits are zero, a separate process inventory finds no diagnostic executable, and before/after hashes of the complete fixture match. These are L2 results on a tiny real saved index, not a performance or capacity measurement.

The provider retains decoded blocks independently of reader-owned posting arrays. After the first saved generation is scored, all policies retain five cached blocks with 2,496 estimated Arrow-buffer bytes and five roots with 420 serialized metadata bytes. The retained-array policy also holds 232 posting payload bytes and 48 centroid bytes. Array release and streaming hold zero posting and centroid arrays between operations, while their provider census stays unchanged. The block census reaches five entries after the first leaf and remains there while two more leaves are visited; several leaves share decoded blocks. Repeated scoring produces cache hits rather than additional misses on this fixture; these counters do not measure storage I/O or decoder invocations.

Opening and scoring the successor while the earlier reader remains open raises the provider census to nine blocks with 4,608 estimated buffer bytes and ten roots with 840 serialized bytes. Each reader holds 164 estimated tree-metadata payload bytes. Dropping the older reader and then every reader leaves those nine blocks and ten roots cached. Explicit provider clearing reduces both censuses to zero. The provider's cache lifetime therefore extends beyond the readers; dropping a generation is not a provider-cache reclamation policy.

Sampled maximum RSS is 12,369,920 bytes for retained arrays, 12,288,000 for array release and 12,255,232 for streaming. These small differences cannot attribute heap use to a reader policy. The samples include live diagnostic JSON, cache-census work, shared buffer aliases and allocator retention. Temporary provider decoding, allocator metadata and simultaneous candidate/output allocation peaks remain unmeasured. The raw reader pin tuple covers posting and vector readers; it is not a separate scalar-reader pin measurement. The per-mode raw samples and actual sample spacing are retained in results.json and runtime/*.rss.json.

The census reads known keys through the plain in-memory cache and changes recency. It immediately drops returned clones. The sizes are per-object payload estimates and can alias other objects; reader and provider estimates must not be summed as an independent total. The default block cache has 256 MiB-ceiling weighted units and the root cache has 4,096 entry units. This fixture visits far fewer objects than either capacity and cannot establish replacement behavior or derive a larger-index working set.

The next implementation candidate is an explicit optional provider-capacity configuration with the existing cache implementation and a clear lifetime contract. A custom replacement algorithm or generation garbage collector is not justified by this fixture. Any configuration change needs its own admitted tiny repeated-leaf trace comparison and explicit reload counters. Current defaults remain unchanged.
