# Bounded selected-posting scoring

The optional scoring operation visits one selected leaf at a time and computes the same approximate distances without copying posting IDs, versions or codes into retained leaf arrays. It reads the actual persisted posting borrowed from the existing blockfile provider. Provider decoding occurs before this operation can inspect physical lengths; provider Arrow blocks, caches, allocator overhead and RSS are outside the owned-array claim.

The operation validates actual ID/version/code lengths and checked byte arithmetic before allocating residual scoring or candidate state for that leaf. It enforces separate maximum physical entries per leaf, aggregate physical entries across the request, aggregate physical posting payload bytes and distinct candidate count. Stale and deleted copies count toward physical budgets. A decoded provider block may contain additional rows or overhead beyond the selected posting. No tree-declared or previously filtered leaf length substitutes for actual persisted lengths.

Every physical ID is checked against the pinned contiguous local-ID range. The operation reads the authoritative published version, rejects missing or out-of-u8 versions, skips deleted or stale copies, and scores every current copy. Every current distance must be finite, including duplicates that would lose. A request-wide map stores each live ID's minimum distance. This first implementation retains all distinct minima under an explicit count limit, not only M entries; it makes no M-bounded candidate-memory claim. The final result keeps the M nearest distinct IDs and every distance tie at that boundary. External IDs remain resolved by the existing pinned mapper before its final stable cutoff.

Exclusive mutable access prevents simultaneous operations from borrowing the same reader while posting and scalar pins are cleared. Previously materialized arrays are discarded, including allocated empty vectors. All borrowed posting and centroid lifetimes end before moving to the next leaf or clearing final pins. An error discards the entire candidate map and emits no partial result. The outer worker also clears pins on error, and the Python adapter requires the exact requested limits and structured metrics rather than accepting an older worker that ignores the optional request field.

Metrics separate physical input rows and payload, current scored copies, largest borrowed leaf, zero copied posting-array bytes, candidate entry count, actual HashMap capacity, capacity-times-key/value payload bytes, and residual-vector capacity. HashMap control bytes, bucket padding, output buffers, quantizer scratch and selected-leaf ID validation have separate overhead; capacity payload is not total allocator memory. The 100,000 local-row and candidate limits remain. All full startup/publication oracles remain. Default requests have no streaming policy or new response fields.

Two Rust tests pass in 0.01 seconds. The persisted case contains ten physical copies: eight initial IDs, a replacement of ID zero, deletion of ID one and an additional current copy of ID two. Eight current copies reduce to seven unique live IDs. At M=1, six tied IDs are retained and agree with the existing complete oracle. Borrowed posting payload is 290 bytes, candidate capacity is seven entries and 56 key/value payload bytes, and residual-vector capacity is sixteen bytes. Budget errors and duplicate selected leaves fail the whole operation and clear pins; a subsequent valid operation succeeds. A separate collector test checks later improving duplicates, losing nonfinite duplicates and cutoff ties. Two Python argument/protocol tests pass in 0.016 seconds. Native compilation finishes in 2.37 seconds. These are test durations, not latency measurements.
