# Observe preparation without changing scoring

The opt-in reader flag is `--profile-posting-preparation`. Its default is false. It requires `--profile-posting-selection`; the existing profile rejects streaming limits, so this observes only ordinary selected-posting preparation. Keep `--posting-scorer-policy runtime` and `--partition-posting-candidates` identical in off/on arms. The scorer still echoes its requested policy and detected implementation. No request body, query value, candidate budget, ordering, generation, leaf, local/global ID or scorer arithmetic changes.

Each ordinary response after configuration echoes `posting_preparation_policy: "posting-preparation-v1"` when enabled. For a selected-leaf scoring operation, `posting_preparation_profile` contains `valid`, `quiescent`, `overflow`, `joined_load_ns`, `request_profile_ns`, `leaves` and `scalar`. Operation errors retain a partial profile with `valid:false` if observation began. Pre-observation admission errors carry an invalid profile and reason. Non-score operations echo the policy but have no preparation profile. Missing policy/profile or a false validity flag must stop a measurement; it cannot be treated as zero work. Omitting the flag emits none of these new response fields.

The response also identifies `posting_preparation_provider.kind` as `plain-memory-foyer` and echoes its effective policy. `posting_preparation_reader_open_ns` measures the one-time reader open, including its metadata/root work, outside the request observer. That constant repeats as response metadata and must be charged once per reader, not once per response. Provider/configuration creation and manifest parsing are outside that open timer. Generic library observations describe provider obtains and storage-origin Arrow decodes; they do not claim hybrid persistent-cache reconstruction coverage.

Each observed request receives a fresh scalar observer handle and requires exclusive ownership of the scalar reader pin map. Older observer callbacks retain their older handle. The request joins or drops its loader futures before snapshot and checks both the preparation handle and scalar observer handle for outstanding references. It disables updates before reading the final snapshot. Outstanding references, map overflow, admission failure or an operation error make the measurement invalid. The observer changes no lock scope, lookup order, 64-ID batch, 16-future limit, 32-leaf limit, filter predicate, code copy, borrow lifetime or pin-clear/error behavior.

The observer retains at most 256 leaf reports and 256 scalar block identities. It records per-batch block cardinality in a bounded histogram, not a list of all IDs or an unbounded event log. The existing per-ID point map is disabled for this mode. The batch block map is reset only under the existing whole-leaf version lock after the prior batch's futures complete. `scheduled_point_gets` counts scheduled batch positions; actual point accesses are the scalar observer's reader requests. The final scalar batch map is only the last batch, not complete request locality. The cumulative per-block access map and per-leaf batch-cardinality histogram provide the request accounting. Overflow means incomplete data and invalidates the report.

Per-leaf reports contain start/finish and lock enqueue/acquire/release timestamps relative to the request start, posting-fetch/allocation/version-loop/lookup/filter-copy/centroid/install elapsed spans, physical/current/stale/deleted/missing/invalid counts, copied code bytes and output capacities. ID/version capacities are element counts; code capacity is bytes. Cached leaves report a bypass and zero new version work. Error spans are partial; their release timestamp is captured while the scope drops after the version guard. `joined_load_ns` is the existing successful joined-load stage timer. `request_profile_ns` additionally includes scoring and selection, but excludes final profile serialization. Observer overhead is included; compare off/on externally and do not subtract nested timers to invent exclusive CPU.

The minimal later protocol uses the same pinned owner27 and exact 16 requests in their existing sequence, in two separately launched off/on readers using one binary. Match source generation, scorer implementation, partition policy, provider policy, query values and all request fields exactly. Preserve each arm's first-use versus already-loaded behavior; do not evict postings or warm one arm differently. Compare complete normalized ID/distance-bit/count/tie outputs before interpreting profiles. Report paired arm order and observer overhead separately. A fresh process is not OS-cold storage. Summed lock waits and asynchronous decode/obtain spans can overlap and are not latency fractions or exclusive CPU.
