# Measure selected-posting preparation before changing it

This milestone adds observation to the actual scalar-version path without optimizing retrieval, changing cache policy, moving the version lock, changing asynchronous result order or changing pin cleanup. The hypothesis is that first-use posting preparation contains consequential version lookup, shared-lock or filter/copy work. Source inspection cannot determine which component matters. This epoch provides source and local correctness only; the continuation owns measurement controllers and any Linux/cloud lifecycle.

The public benchmark opt-in flag and off/on procedure are specified in PROTOCOL-CONTRACT.md. The selected-leaf scoring wrapper owns a fresh request-local preparation report and installs a fresh scalar observer handle only with exclusive scalar pin-map ownership. The regular scorer passes no preparation observer. Future/provider callbacks inherit the request's handle through the actual get_block/get_observed path. Previous callbacks cannot update a fresh request handle. Final report validity requires no outstanding request/scalar observer handles, no bounded-map overflow and a successful operation. These observations do not establish cancellation or panic cleanup guarantees.

The loader retains the same 64-position batches, 16 lookup futures, 32 leaf futures, whole-leaf version lock, filter predicates, owned code copies, centroid retrieval and installation check. It preserves the existing error return before scalar clear and the existing completion order. The report records per-leaf timestamps and aggregate durations, capacities, physical/live/stale/deleted/missing/invalid rows and copied code bytes. Partial error reports are invalid. Each batch's block-cardinality histogram derives from actual key-to-block resolution while holding the existing version lock; cumulative request counters come from actual pin/provider/storage/decode boundaries. No vector ID inventory is collected in preparation mode.

Observation is bounded by admission of at most 256 selected leaves, at most 256 block identities, one at-most-256-entry current-batch block map and at most 65 batch-cardinality histogram entries per leaf. Actual batches contain no more than 64 points. Leaf reports are bounded and duplicate insertion marks overflow. Scalar block/point observer overflow invalidates the request rather than certifying incomplete counts. Reports include a baseline of existing scalar pins; they do not assume reader opening leaves no pins. The last batch map is not an all-batch event history. Observer snapshot copies are bounded but add work inside the version lock; off/on timing must disclose this overhead.

Provider hits mean obtain returned a decoded block handle. Storage callback counters and Arrow decode counters describe storage-origin decoding, not hybrid cache reconstruction. The CLI uses the existing plain-memory Foyer provider and reports its effective policy. Root opening is separately timed and excluded from the request counters; other startup metadata is explicitly outside that timer. Held payload is the existing Block::get_size estimate, not provider residency, unique allocated bytes, physical I/O, RSS or a preallocation bound.

The local correctness plan contains two bounded report-unit tests, one saved-posting off/on bitwise parity test with cached-leaf zero-version work and invalid admissions, one block-observer cap/disable/old-handle isolation test, then benchmark cargo check. The saved fixture uses the existing real persisted two-reader fixture and runtime scorer plus partition-inclusive selection. It compares every retained ID and f32 distance bit, including its cutoff ties. No performance result, x86 execution result, complete fixed16 experiment or native CLI run is claimed by these tests. Tests require independent source admission first.

Only six existing source files and one new preparation module change. The isolated patch compares captured pre-edit bytes, preserving the accepted scorer. The full source archive extends the accepted 916-file hardware closure with the new module; all 18 SQL dependencies retain their pre-pinned hashes. No source file outside this owned change set differs from the accepted hardware manifest.
