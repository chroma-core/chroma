# Validate changed subtrees without rescanning retained owners

Publication can validate only changed owners when the unchanged bytes remain tied to a previously audited, durably retained storage version. The current local and generic object-storage interfaces cannot establish that prerequisite. This design therefore proposes a new integration contract and keeps the complete current validation path as the only active admission path. It changes no validator, storage behavior, default, test or runtime.

## The current cost

Preparation and validation contain separate whole-corpus costs. Removing one validator pass does not remove full canonical copying, owner cloning, record auditing or metadata serialization. The measured sixteen-row validation inventory establishes repeated Python reads, not total native/provider I/O. The accepted same-call map optimization removes 384 returned bytes from 109322, while retaining every other path read. That reduction does not address proportional publication. The representative 98-row multi-block fixture has not yet been profiled for validation cost; its correctness and saved-root inventories are retained separately.

## Why current hashes cannot authorize reuse

The storage interface has conditional-put modes, but both block and root flush use the default Upsert mode and discard the returned ETag. Local storage ignores put options and rewrites named paths; its `confirm_same` is unsupported. S3 `confirm_same` compares a current HEAD ETag. Get options contain priority, consistency and parallelism fields, with no explicit retained version ID. UUID keys, hashes, directory inventories, chmod 0400 and an ETag checked at one instant cannot prove that another process cannot replace or delete a dependency before publication or before an old reader fetches it. This is an observation about available interfaces, not a claim that production operators permit overwrites or garbage collection.

The missing authority must cover the whole reused dependency closure, not only five root UUIDs. Every referenced block, ownership node/page, canonical value object, identity/record map and relevant model object needs an exact retained version identity. Lease expiry, provider restart, recovery, garbage-collection handoff or namespace replacement must invalidate the admission capability before reuse. Pin lifetime covers publication and the actual retained-reader contract; it must not expire while an admitted reader may lazily fetch a dependency. A fresh hash/stat comparison cannot substitute for that contract.

Existing garbage collection already reasons about collection versions and referenced block closures. `compute_versions_to_delete` retains a configured minimum of versions and applies an age cutoff; `compute_unused_between_versions` reads roots and computes referenced-file differences against a kept version. Those mechanisms are the appropriate lifecycle integration point. A minimum-version or age policy is not an acquired validation/read lease: concurrent registrations can age a parent out, and no audited API here atomically pins the full closure for this validation operation. The proposed capability should reuse that version/GC authority rather than create an independent retention service. It still needs immutable-byte enforcement or a proved writer-wide write-once contract, exact version reads, an explicit lifetime and recovery invalidation. This inspection does not establish production policy settings or every server-side guarantee.

## The smallest useful interface

Start with topology replacement, where the record segment, global user/offset mapping and canonical values do not change. This avoids inventing incremental record semantics or a new appendable canonical format inside the first milestone. The proposed operation consumes one internally captured committed parent, a storage-authority-issued retained snapshot pin, and a complete candidate with an explicit replacement set. It returns eligibility for the existing collection proposal only. It creates no independent pointer or service.

The captured parent binds tenant/database/collection, collection version and log position, job/session, exact registered bundle artifact, deployment fence and canonical configuration. The provider issues a non-forgeable typed handle only after it establishes exact immutable versions and retention for the audited closure. An ordinary JSON receipt, caller flag or public dataclass cannot manufacture this handle. The audit certificate binds that handle and closure digest to the actual complete parent proof. Persistence and recovery of certificates require an authority-controlled protocol; deserializing an old certificate alone restores no trust. No such provider handle exists in the current code.

The candidate declares removed/replaced parent owner IDs, new owner IDs and all exact saved five-root references, map/count/revision descriptors, model boundaries and page/trie roots. Each unchanged owner must preserve its exact payload identity: snapshot/map artifacts, all five saved root versions and their reachable dependencies, generation/count/ownership revision, vector interpretation and committed boundary-centroid content. Its routing-slot index can change when a sibling splits; validate that the candidate slot resolves to the identical committed centroid and boundary hash. The enclosing model object may change, so equality of the whole model artifact or the whole subtree descriptor is neither required nor sufficient. Physical paths are locations, not immutable version authority. Physical placement changes are separately verified transfers with exact imported content/version pinning and the same collection proposal. Every changed owner receives a full native saved-index audit: all reachable live postings, authoritative versions/tombstones, one current copy per local ID, complete map coverage, exact canonical vector bits and actual saved root identity. A file inventory delta is diagnostic evidence only; it cannot reveal logical deletion or a version change inside a retained block.

Global single ownership composes from the already proved parent and an exact affected-set proof. Read the removed owners' pinned maps, reject duplicate old IDs, and compare the union of all replacement IDs to that exact union. Validate every replacement local offset and require disjoint complete output coverage. No replacement can claim an ID from an unchanged owner. Exact reuse of unchanged owner payload identities and unchanged canonical/record/identity versions carries their prior proof. Changed routing-slot metadata is independently checked against the candidate model and identical per-owner committed boundary content; it does not authorize a different centroid or saved payload. The ownership trie updates only affected owner paths and authenticates exact reused child descriptors/counts; the full page/flat-map oracle runs separately for differential acceptance. A multi-set fingerprint or count alone does not prove this equality.

The new namespace keeps the exact old mapping, identity source, canonical and record-file references. Its changed owner-map references and parent namespace chain bind the complete candidate. A reusable namespace proof separates invariant user/offset/vector identity from current collection version and owner placement. It must not weaken collection dimension/schema/configuration checks. The existing construction receipt is provenance; it is not the new reuse authority.

Before registration, recheck current collection/session and parent version/fence after all preparation and audits. The existing collection version check remains the final publication fence. Publish the complete vector/namespace/record references together through the existing registration input. A stale parent, missing retained version, expired pin, failed audit or unacknowledged required write prevents eligibility; an ambiguous registration acknowledgement remains pending/unknown. Cleanup and operation outcome remain separate. No old log offset is blindly replayed.

## Boundaries this first interface does not remove

The first interface targets complete changed-owner validation, not changed-block or changed-row validation. A one-row addition can still require auditing its full destination owner. Per-owner live-posting/version/vector certificates would be a later, deeper proof and are not implied by a physical copy-on-write block list.

Append remains a separate architectural step because its canonical file, namespace table/identity source and shared record roots change. Proportional append requires authenticated appendable canonical and namespace pages plus a record-writer change proof binding actual materializer raw/log/user/offset/vector correspondence, all changed record maps and hidden-key/deletion coverage. Global IDs remain u64 and current record offsets u32; this proposal does not widen the record namespace. The current full-copy/full-audit append path stays active.

Flat saved maps, complete JSON owner descriptors and the 100000-row prototype cap remain. Even a payload-proportional validator may still visit O(owner count) metadata unless the enclosing bundle gains authenticated hierarchical descriptors. Current full-directory transfer mirrors and retained historical files can dominate copy/durability costs. Report these separately rather than claiming that a changed-owner validator makes publication proportional overall.

## One coherent acceptance milestone

Reuse the existing representative fixture, with no new rows or builds merely to populate data. Its append bundle has owner a with 48 rows and owner b with 50 rows. The retained split replaces a with split-a/split-b, 24 rows each, and preserves b's payload. Its b centroid_index changes from 1 to 0 while its boundary hash, ownership revision, generation, count, map, saved snapshot and roots stay unchanged. The new routing slot must resolve to the same committed centroid; the whole descriptor/model object is not byte-identical. The parent bundle SHA is `5767b33ac518fdb3e64787600cb55db6efbef7d48198af43ceb85c939334e75a`; the candidate bundle SHA is `1cd178970ec4c809347ccf8122a1afcf2e54a74ba28ffdfc6b4603de73831112`. These identities come from retained artifacts, not a newly executed validation.

1. Establish an actual immutable-provider/retention contract before enabling payload reuse. Until then, verify fail-closed fallback on the real mutable local backend. A deliberately immutable in-memory test provider may prove the composition algorithm, but its results must remain component evidence and cannot establish durable local, S3 or production authority.
2. Bootstrap the exact parent with the full current validation and actual record/native audits. Account for bootstrap bytes/objects separately; do not subtract this cost from a single-operation benchmark or call bootstrap free. Bind every reused dependency to the provider handle and exact collection context.
3. Validate the existing split transition through the new contract, compare its complete result/eligibility with the full oracle, and prove all 98 IDs/users/offsets/vector bits plus the single-copy saved roots. Expected proportional work is the 48-row old affected set, 48 replacement rows and changed metadata/objects. The unchanged 50-row owner and unchanged record/identity/canonical objects have zero payload reads only on the genuinely pinned provider path. Current local fallback continues to read them.
4. Exercise adversarial cases in private copies: same-size restored-mtime corruption of an unchanged map/block/canonical/record object; missing or replaced retained version; changed pin/provider epoch; wrong owner/root/map/value/version/posting; hidden duplicate or missing replacement ID; undeclared changed owner; modified unchanged payload descriptor or changed slot resolving to a different centroid; stale collection/session before preparation and during final audit; partial candidate write and retained orphan. Immutable-provider mutation must reject at the provider or invalidate the pin; mutable local storage must fall back and detect corruption. No case may obtain a reusable receipt from a caller-supplied label.
5. Retain the full existing oracle as a separate validation mode and compare outputs, complete proposal references, old pinned-reader results and no-eligibility failures. Distinguish native semantic audit from Python provenance checks. Preserve all input hashes, raw object-read/byte counters and terminal normal cleanup. Do not publish through a second local pointer.
6. Report bytes and unique object versions by category: bootstrap, changed owner native audit, removed-owner map proof, unchanged-owner reuse, metadata/path traversal, complete oracle, fallback, copied bytes and durability calls. Python returned-byte instrumentation does not cover native/provider reads; counters must be at the provider interface for those claims. Fsync calls are distinct from bytes and do not imply object-store writes. No latency or RSS claim is required.

The proposed fixture budget remains at most 128 rows, two initial owners, 32 dimensions and the retained approximately 1.78 MB input closure. Private counterexamples use copies, with a declared 16 MiB aggregate evidence/copy ceiling and finite per-child deadlines proposed in the source-review freeze. Stop on any mismatch, missing provider capability or exhausted budget; do not enlarge the corpus, run cloud operations or compare query strategies. Exact executable/controller/source admission precedes any future runtime.

## Decision and prerequisites

Do not activate cross-call or cross-publication reuse on the current mutable local storage. The next implementation decision is whether to add and prove the missing retained immutable-version contract in the existing provider/garbage-collection/publication lifecycle. This is a cohesive storage-and-validation integration, not another cache flag. If production already enforces an equivalent guarantee, its concrete authority, version-read API and recovery/retention behavior must be identified and connected first. Until that evidence exists, implement only a fail-closed contract/component and keep full validation/durability as the fallback; do not report zero unchanged-owner reads for the real publication path. This design is submitted for independent review before implementation or runtime.
