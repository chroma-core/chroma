# Configured durable staging grain

The durable staging grain controls how many new vector rows share one immutable commit and flush. It is independent of the logical insertion/balance cut and does not change the bounded fetch/cache limits. The compatibility default remains 64 rows. A caller can explicitly admit a larger grain through both a row limit and a modeled working-byte budget; the native diagnostic records both settings in its complete spec.

The native spec adds `staging_rows` (default 64) and `staging_working_bytes` (default 1 MiB). Before creating output or reading a construction chunk, it checks the configured maximum against the modeled admission. Owner staging repeats the row/byte check before writing a new root or publishing current authority. Initial prefix verification and final saved-vector validation still use 64-row buffers; construction reads use the declared staging grain. Fetch batches remain at most 16 handles, owner caches retain at most 32 vectors and reader-pin admission remains unchanged.

The model is `rows * (16 * dimension + 256) + 65,536`. Four FP32 payload equivalents cover caller decoded rows, encoded-input overlap, writer copies/block construction and an allowance; the per-row term also budgets handle/container metadata. This is a conservative declared model, not a measurement or hard bound on every allocation. Root-index state, older forked blocks, provider caches, allocator overhead, owner postings, routing and publication coexistence remain outside it. Native decoding owns encoded and decoded input together and reports that separate payload peak; the input byte buffer drops before writer staging begins.

At 8,192 rows and 768 dimensions, one decoded payload is 25,165,824 bytes (24 MiB), and the staging model admits 102,825,984 bytes under an explicit 128 MiB budget. The test checks that arithmetic without allocating a real corpus. A maximum grain is not a minimum buffer allocation: partial chunks allocate only actual rows. The model includes no claim about RSS or total machine memory.

The number of vector-root publications is the sum of the ceiling of each logical cut divided by the staging grain. One million rows in a single cut require 15,625 publications at 64 rows or 123 at 8,192 rows. Ten cuts of 100,000 rows require 15,630 or 130 publications, respectively. These are operation counts rather than a throughput forecast. Forked root-index growth, encoded writes and storage latency still require representative measurement.

## Fixed local evidence

The fixed comparison uses 513 synthetic 32-dimensional vectors and identical logical cuts of 257 and 256 rows. A seeded two-leaf topology has one occupied leaf and one empty leaf; it performs no random split or merge. Each variant performs 513 registrations and one actual ownership move. Both retain identical sorted per-ID codes and current versions, verify every persisted FP32 vector bit and complete current membership, and preserve an older saved reader.

The 64-row grain performs nine stage publications and the 256-row grain performs three. Both stage 65,664 logical vector bytes. Observed stage elapsed is 14.680377 ms and 7.629041 ms in this single local order. Those intervals include writer open/fork/set/commit/flush, but they do not establish a causal elapsed improvement or physical I/O reduction. Logical payload bytes are separate from encoded writes and disk traffic.

Negative tests reject an undersized configured working budget before creating a root or owner authority, reject a chunk above its admitted row limit, and reject extent arithmetic overflow. The initial test run preserves eight passing methods; only the fixed fixture needs repair. Its earlier single-leaf/no-internal save and oversized-posting save failures remain in raw logs. A fixture-only empty-input mistake and an incorrect exact move-count assertion also remain. This milestone does not repair those persistence paths or claim general large-posting support.

The native smoke runs two owner constructions on identical 259-row synthetic input, with grains 64 and 256 and logical cuts 193 and 66. It checks the declared chunk count, complete saved census, exact FP distance bits and published original manifest. Independent clustering remains stochastic, so that native result supplies no exact tree or timing comparison. An invalid staging budget must fail before creating output. No real corpus, cloud operation or query policy change belongs to this package.

## Next connected boundary

The next substantial source seam is incremental owner publication, not further grain tuning. The current owner save rebuilds all nodes and clones every owner's current map into a fresh joined writer. Existing persistence can fork previous immutable roots and apply dirty sets, but it clears its own dirty marks before all flushes complete. Authoritative dirty marks and the previous published root must remain intact until successful completion.

A coherent publication slice would add owner-local dirty current IDs, reuse kernel dirty node/tombstone marks, copy only changed postings and metadata into an ephemeral publication writer, and keep the previous five published roots. It must fork posting/version/node roots from the prior generation while using the newest staged vector root. Successful publication must rebase the staging store onto the flushed vector root containing the complete centroid prefix; otherwise later staging roots lose unchanged centroids. This updates the next immutable base, not existing content handles or old readers.

The decisive test uses several generations with append, actual owner movement, later split/merge, an unchanged region and an old reader. It checks complete current/code/vector census, exact centroid visibility, reused old object hashes and bounded changed-payload copying. A controlled flush failure must preserve authoritative dirty marks and the prior published roots or poison publication explicitly. Vector deletion remains rejected by the append-only contract; structural tombstones and metadata-only placement need separate accounting. This is a design handoff only, not an implemented publication claim.
