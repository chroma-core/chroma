# Candidate selection reduces sorting work under an explicit tie distribution

The opt-in selected-leaf scorer selects the requested cutoff before sorting retained candidates. Let U be the number of unique scored IDs, M the requested candidate budget and T the number retained after including every cutoff tie. Full sorting processes U rows; the new path performs partition/retention over U and sorts T. The structural cost is linear selection plus sorting T, while scoring, minimum-distance deduplication, the full candidate map and Vec capacity remain unchanged. In the worst case T equals U. This is not a new memory bound or a reduction in posting reads, vector refinement, recall policy or candidate network volume.

The retained16-query trace records 1689 score operations, median U of 26,136, maximum 159,497 and fixed M of 1000; 1674 calls exceed M. It does not retain the full pretrim distances. The exact optimized reader helper is therefore measured on generated arrays at recorded quantiles, with seven paired AB/BA samples and identical-ID/distance-bit output checks. Generation, cloning and deduplication are outside the timed kernel, and clone time is retained separately. Ratios are per-size synthetic-kernel results, not weighted real-query speedups.

For generated spread scores at U of 12,031 through 159,497, median kernel time improves by 4.22–8.31×. At the observed median U of 26,136, full sort takes 718,834 ns and partition takes 122,292 ns (5.88×), sorting 1000 retained rows. Generated 32-group tie-heavy scores improve by 1.93–2.21× while retaining 1128–4984 rows across these sizes. The all-ties control is 1.85–2.11× slower and retains all U. Empty inputs produce only timer-scale observations and carry no performance conclusion. No adaptive tie-density choice is activated.

A full-query speedup requires the fraction of real query time spent in this selection kernel. That fraction is unmeasured: the historical 260 ms posting-stage lower bound also contains posting materialization, version checks, quantization and distance computation. If a future representative measurement assigns a fraction f of total time to selection and measures kernel speedup s, the idealized whole-query speedup is 1/((1−f)+f/s), before overhead or overlap. With s = 5.88 and assumed f = 0.1 it is about 1.09×; with assumed f = 0.5 it is about 1.71×. These are arithmetic scenarios, not observations. All-ties inputs can reduce performance instead.

Four real saved-index query triplets independently preserve the complete trace across the retained c8 baseline, new full-sort path and partition path, including IDs, distances, global-ID ordering, selected leaves/candidates and budgets. Eight focused tests pass. The local native binary is a development build and supplies correctness/stage diagnostics only. The optimized standalone executable imports the same source helper and its compiler flags/hash are retained. The accepted baseline 100B model is unchanged. At 100B, the gain remains conditional on the number of candidates scored per retained owner and tie density; root fanout, raw scoring, global ID namespaces, record scans and affected-owner maintenance still require their own accounting.

The query-sharing byte result composes with this selection policy because the adapter reconstructs identical per-reader payloads before the pinned policy is applied. The byte experiment measures actual local requests at 14,461→12,783 bytes and reconstructed 768-dimensional bodies at 5,014,171.875→344,657.125 bytes per query. Those are separate baselines from the kernel experiment. Their percentages must not be multiplied into an end-to-end speedup: HTTP serialization CPU, physical network conditions and real selection-time share are unmeasured. No combined rerun is needed to establish interface compatibility, and no joint latency claim is made.
