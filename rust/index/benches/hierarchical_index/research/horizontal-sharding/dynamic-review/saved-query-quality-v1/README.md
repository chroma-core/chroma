# Measure recall and scoring work on the same tiny saved trees

This package prepares an exploratory saved-query comparison for the already retained reference and combined-owner checkpoints. It builds only the instrumented reader binary; it does not rebuild either index, change its manifest/map, recompute GT or increase the corpus. The exact source prefix, sixteen reused query vectors and FP64 top 100 file are the accepted saved-locality inputs. Their hashes and original generation 1 manifest/map descriptors are frozen in `runtime-spec.template.json`.

The two prespecified settings keep 100 returned neighbors and exact rerank factor of two fixed while setting the leaf beam minimum and maximum to 8 or 32. The existing uniform navigation policy keeps tau 2.0. Each arm/setting gets a fresh reader process, one complete sixteen-query warm-up pass and one retained warm pass in the same order. This creates four reader children and 128 operations: 64 warm-up and 64 retained queries. There is no tuning loop, broad sweep, retry or automatic growth. Each reader has at most 10 seconds and all four share 40 seconds under a fresh external absolute deadline. Build time is separately bounded by the reused offline recipe. The parent owns runtime/resource approval; no cloud execution occurs in this package.

The result retains every measured global ID and native FP32 distance bit, recall@100 against the frozen exact GT, actual scored posting-copy and distinct-ID counts before trimming, actual exact reranks and returned counts. Selected leaves are a proxy for navigation work; no internal-node/centroid evaluation count is claimed. Per-query native operation elapsed excludes reader opening and output serialization/transport but includes the existing mapping, clearing and memory accounting. Whole-process wall/CPU includes reader opening, warm-up, measured queries and exit and is reported separately. Timings use the same observation policy in both arms and are descriptive; one warm pass over 16 reused queries is not statistical latency evidence or a scale projection.

The existing vector access observer reports vector-block pin/provider/cache/storage-origin decode work, not whole-query storage or physical I/O. The process uses the default plain memory provider and retains loaded posting payloads. Reader block pins clear after each operation while provider cache remains warm. Root opening and initial metadata loads are outside that observer. Full warm-up coverage does not establish OS-cold behavior, remote execution or actor fanout. The input is one saved global root per arm, independently constructed with different shapes/work; no tree parity claim follows.

Local correctness is complete. The changed saved-reader test checks stale/deleted filtering, 39 scored loaded copies, seven distinct candidates, a four-candidate trim, four exact gets/distances and two returned results. A first compile failure puts the get counter in the nonmutable eager wrapper; its log and source remain under `attempt1`. The corrected counter sits at the actual lazy fetch boundary. The test passes, and the native target builds. Four actual ARM reader processes query both unchanged 64-row saved fixtures with profiling off/on; twelve queries preserve returned IDs/distances, report 64 scored/reranked rows and exact final FP32 bits, and leave all saved files unchanged. Three wiring tests pass, including fake four-child success and first-child failure without running AWS/network or a real-data query.

The scientific limits remain explicit. The cohort is reused exploratory test data with unproven corpus/query disjointness. Recall uses a frozen FP64 reference, while the reader retains its FP32 approximate and exact arithmetic and existing tie behavior. Saved-query timings are single-process warm observations, not ANN latency-at-scale, cross-host execution or a 100B claim. Immutable saved inputs remain an experiment assumption; the controller pins metadata/maps and relies on the accepted retained checkpoint payloads rather than implementing a production immutability contract. No new infrastructure or transport is added.

After the external operator supplies the exact new Linux binary, fixed deadline and output path, the command is `python3 run-queries.py --spec filled-runtime-spec.json`. The accepted original manifests are named `manifest.json`; requests pin generation 1 directly, and the controller never creates or rewrites a `manifest-1.json` alias. The recorded saved paths must exist unchanged on the retained driver. If a binding, shape, response or budget fails, the result remains failed without retry.
