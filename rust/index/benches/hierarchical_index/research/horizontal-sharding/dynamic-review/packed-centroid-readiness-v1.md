# Packed centroid access is a plausible later mechanism question

Navigation still copies and sometimes decodes routing centroids after the384MiB vector cache removes most immutable-vector reads. The optimized reference scores an internal node's children from one shared contiguous centroid array. A bounded equivalent is worth a fixed-tree mechanism test, but retained counters do not isolate navigation's share of node traffic. The matched reference and prepared-split comparisons remain ahead of this work; no speed claim or new execution follows from this note.

## The concrete difference

The connected construction path holds its complete-view read scope while traversing the global mixed internal/leaf frontier. Each fetch wave requests at most8node records. For each requested ID, the authoritative store checks dirty state or its root-and-ID clean cache; a miss opens a provider reader, reads a node64 record, decodes its FP centroid, child IDs and quantized centroid code, and clears reader pins. FullAccess then clones the NodeRecord, including its centroid and internal child vector, into a fresh Arc even on a clean-cache or dirty-state hit. The traversal reads the root, reads expanded parents, fetches each child to score its centroid, and fetches the selected IDs again to distinguish leaves from internals. The initial root can therefore be fetched twice; selected records are fetched again after scoring. Clean cache hits can avoid provider decoding but not this FullAccess clone. FP scoring does not need the stored quantized centroid code. Source: active `writer/writer.rs:439–456`, `writer/owner_node_access.rs:46–56,96–107`, and `topology_access.rs:34–59`.

These costs are routing metadata costs, not whole-posting fetches. Full authoritative leaf records contain metadata and FP/quantized centroids; posting ID/version/code rows live in the separate owner actor. Other construction consumers also read full records, so the store's point-read total is not a navigation-only count. The node_get adapter separately creates an owned tree representation for mutation/read callers; it must not be confused with FullAccess's wave clone. The older live-only node_centroid helper clones a centroid too, but the current full-record navigation uses FullAccess rather than that fallback. Source: active `writer/owner_node_access.rs:59–93` and `writer/live_node_adapter.rs:28`.

The optimized reference stores ordered child IDs and contiguous FP centroids together in an immutable ChildNavigation payload shared by Arc. An expanded internal node clones the small navigation Arc, releases its map guard, and scores borrowed centroid slices without a lookup or centroid copy for each child. It still resolves selected candidates against live node metadata; packed scoring removes the all-child lookup, not every lookup. A missing-at-publication centroid has a special fallback lookup. Child and centroid publication, parent edits and centroid propagation update this payload under the reference's structural mutex. Batch initialization refreshes parents when needed; stable batches reuse the payload. Source: isolated reference `common.rs:8–84` and `writer/writer.rs:256–286,292–385,796–946`.

Both paths call the same configured FP distance function for scoring. The useful comparison is identical ordered centroid bits, candidates and distance bits, rather than a new quantizer or reduced beam. The reference permits concurrent missing nodes and fallback behavior; the connected writer promises a complete view and must continue rejecting unknown missing records. Copying the reference's missing-row fallback literally would weaken that promise.

## What remains after vector caching

The decoded-vector cache is keyed by immutable vector content handles and stores document FP arrays. The node store has separate node64 roots, a different codec, live revisions and its own8entry/32KiB clean cache. A warm document cache cannot satisfy these centroid records or prevent their clone/decode work. The provider block cache can retain encoded/decoded block data below the node store, but a node-store miss still runs its record decoder and creates owned centroid/code arrays. Provider cache hits are not proof of zero node work or zero physical IO.

Retained before_save evidence shows substantial node traffic with the384MiB document cache enabled. Epoch11's byte arm reports658581full-record point reads,588124evictions and5.837seconds of cumulative point-miss elapsed over153140navigations; its document cache records864196hits of955088gets. Epoch13short reports959774point reads,873233evictions and11.843seconds of point-miss elapsed over154696navigations. Epoch13long reports292416reads and1.048seconds over145311navigations. These runs have different trees, schedules, dirty-record residence and work. The variation is a warning against predicting cost from cache size or navigation count alone. Point-miss spans include provider open/get/decode and cache admission, overlap concurrent callers, and include non-navigation consumers; they are neither CPU nor an additive fraction of balance time.

Existing retained fields include navigates and missing-node counts, full-record point reads/evictions/cache caps/miss and flush spans, and visibility wait counters. The generic traversal returns fetch waves, requested/returned record bytes, distance evaluations and frontier/pin peaks, but the full-record construction caller retains only distance/level/count totals in internal stats, not the whole per-navigation work object. Current native diagnostic counts do not expose all those internal duration/distance fields. The older live-only topology report has navigation wave/byte counters; that report cannot substitute for full-record measurements. A fixed fixture can count its access calls directly without a production UUID ledger or another benchmark instrumentation cycle.

## One bounded fixed-tree fixture

Use one authored768D tree with a mixed leaf/internal frontier and more than128child records, then one fixed32-query tape containing equal-distance ties. Replay the same ordered centroid bits through current point-wave navigation and a reference-like packed scorer. Require identical ordered selected node IDs and every returned distance's to_bits value, with unchanged global beam/tau policy and tie input order. Count actual full-record fetches/decodes, centroid-copy bytes, distance evaluations, cache/pin peaks and packed-payload preparation bytes separately. Repeat the identical tape after explicit eviction, without timing assertions or cache-parameter sweeps.

A full100-child parent payload is307200centroid bytes at768D before IDs/types/version metadata. It does not fit the current4KiB node-record admission or32KiB node cache. A bounded prototype therefore needs separately admitted immutable scoring chunks, for example at most8ordered children per chunk, rather than appending a whole packed tree to the resident node map. The descriptor must bind parent revision, ordered child identities and centroid revisions to one coherent live visibility epoch or immutable saved generation. The cache must charge actual packed payload and bound concurrent pins/dirty preparation; root indexes/provider buffers and frontier scores stay separately reported. Dirty authoritative child records remain the source of truth; a packed array is a disposable or durable versioned scoring view, not a second mutable authority.

Use the same fixture through a child-centroid update, a leaf split and a merge/root contraction. Publish affected child lists and scoring chunks in the existing exclusive visibility scope; refresh a parent's scoring entry whenever a child's centroid changes, including propagated internal centroids. Test a paused update so readers see a complete old or complete new view, never a cached stale centroid paired with current children. Preserve an opened old saved reader across the mutations and re-run its fixed queries unchanged. Include root-leaf distance and unknown-missing-record rejection. Physical owner placement changes must not change logical child identity or silently retain stale versioned chunks; actual multi-owner execution remains outside this fixture.

The smallest useful next artifact is that local fixed-tree read-path prototype and its accounting, after the higher-priority reference/split results. A production hook audit and durable packed codec may be necessary before adopting it; this note does not authorize either. Current evidence establishes a source-level avoidable-copy/read mechanism, but is insufficient to rank its wall-time importance against the pending split result or justify a larger performance experiment.
