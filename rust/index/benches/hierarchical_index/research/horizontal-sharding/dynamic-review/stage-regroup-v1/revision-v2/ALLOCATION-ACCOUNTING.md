# Joined-stage allocation admission

The stage budget covers retained collection and regroup data for one durable stage. It does not cover the whole writer or total process memory. The policy admits at most 8,192 rows and charges `rows * (4 * dimension + 4 * code_size + 8192) + 65536` bytes before collection. The original 1,024-byte metadata allowance does not have a conservative derivation for the overlapping tree and reservation allocations, so this revision raises the charged metadata allowance while keeping the caller's configured budget unchanged. A policy whose budget is too small now fails admission.

The centroid charge covers one retained centroid allocation for every input row. A window creates at most one destination entry per input row; all worker-window entries together therefore number at most the stage row count. Regrouping moves entries and their shared centroid references into the destination map. It does not duplicate centroid arrays. When destinations repeat across windows, the redundant arrays disappear as those entries are consumed. The short-lived source-centroid clone and conversion during collection belong to the separately admitted active worker-window scratch; they overlap the stage charge rather than disappearing from the memory model.

The four code-sized charges cover the retained per-row code buffer, a conservative full-stage equivalent of transient quantizer output, the new rows' copied posting code bytes, and another code-sized overlap allowance. Regrouping moves code-buffer pointers rather than cloning code buffers. Each input row has exactly one code buffer throughout collection and regrouping. Quantization runs on at most the admitted active workers, so charging a full stage of transient quantizer output is conservative. The actor's existing posting buffers and reallocation of old posting contents remain resident-owner storage, outside this stage delta policy; the stage budget does not assert that appending to an existing large posting has bounded total allocation.

The 8,192-byte per-row metadata allowance charges simultaneously live containers rather than only logical fields. The supported 64-bit layout checks constrain a destination entry to 48 bytes, a row tuple to 32 bytes, a prepared handle tuple to 96 bytes, an immutable handle to 64 bytes, a reservation token to 32 bytes, and a tree header to 24 bytes. The following buckets deliberately use pessimistic node-per-entry accounting instead of relying on average tree occupancy.

| Charged bytes per row | Simultaneously live data |
| ---: | --- |
| 2,048 | Worker-window and destination tree nodes. Each tree entry is allowed a complete 1,024-byte node allocation, including key/value slots and child pointers. There are at most `rows` entries in each set of trees. A destination key is 4 bytes and its value is at most 48 bytes; the supported standard-library tree node's 11 slots, up to 12 child pointers, and node header fit within this charge. |
| 2,048 | Pending-home reservation trees and their construction overlap. A home entry contains a 4-byte key and a 24-byte vector header. A complete node fits within 512 bytes. Four node-per-identity equivalents cover retained reservations, the current batch's grouping and reservation-construction overlap, and message copies. Every batch contains at most 64 identities. |
| 1,024 | Row tuple capacity and prepared tuples. Worker vectors and destination vectors overlap during `append`; geometric spare capacity and the current source/destination reallocation overlap are charged here. Prepared tuples replace the source row vector but may coexist with its allocation during collection. Each contains an ID, code-vector header, and full immutable handle. Code backing arrays are charged separately. |
| 1,024 | Identity lists and ordering/lock work: the outer dirty-version list, registration IDs, sorted duplicate-check copy, authority lock-key temporary, resulting lock references and guard vector, plus current reservation-batch identity and key copies. Every item count is bounded by the current destination or 64-row subrequest; no stage-indexed global map is introduced. |
| 1,024 | Nested worker/window vector headers, map headers, reservation-vector spare capacity, shared-centroid allocation headers, transaction flag/reference headers, and actor-message ownership scaffolding. At most one registration transaction and one write lease are active, while all remaining worker/group deltas stay charged. |
| 1,024 | Explicit metadata and capacity headroom beyond the preceding conservative payload buckets. This is not an allocator-overhead or RSS guarantee. |

The fixed 65,536-byte charge covers the at-most-32 worker/join handles, current-stage framing, and constant-sized transaction scaffolding. Container layout is checked by a focused test. The standard library does not promise a stable tree layout or allocation strategy; these are an admission model for the pinned toolchain and supported target, not a portable allocator proof. Changing the toolchain, target, container implementation, or allocation strategy requires reviewing these assumptions. Allocator bookkeeping, fragmentation, thread stacks, provider buffers, caller FP input, durable staging buffers, node-store pin/dirty budgets, owner resident records and existing postings are separately scoped and are not hidden inside the stage budget.

At 8,192 rows, 768 dimensions, and 112 code bytes, the revised charge is 96,010,240 bytes. The local fixture admits 256 rows with a 4 MiB delta budget and a separate 1 MiB active-worker-window budget per worker. No runtime benchmark budget or policy is changed by this local revision.

# Hook admission

The optional observer maintains an auxiliary construction view through insertion and mutation callbacks. Ordinary insertion calls its start, navigation, and registered-row callbacks. Joined regrouping calls the existing navigation and destination-selection helpers directly and performs a direct owner append; it does not invoke those insertion callbacks. Consequently the hook cannot mutate routing through a regroup callback, but admitting it would leave its auxiliary view incomplete before a later balancing callback. The policy therefore rejects an installed hook both when enabled and immediately before a public insertion phase starts. The second check catches a hook installed after policy admission. Both checks precede durable staging or membership changes. This is a compatibility restriction, not a new callback implementation.
