# Optional collector integration

The reader selects the candidate collector only when a selected-leaf scoring request explicitly supplies both streaming limits and candidate working-set limits. The Python deployment reader forwards a pinned copy of each policy. The worker echoes the exact candidate policy, and the adapter rejects missing or changed echoes rather than silently using an older worker. Default requests retain the complete distinct-minimum map and their existing response fields.

The bitmap tracks every distinct current live local ID, including IDs discarded from the retained candidate state. Before inserting a new unique ID, the streaming loop checks the existing total-unique limit independently of the collector's retained-entry limit. Current-version filtering, every-copy finite-distance checks, physical input counts, global beam, global M and external-ID tie resolution are unchanged. The collector's construction parameters and bitmap-byte requirement are validated before scanning; bitmap allocation occurs only after a nonempty physical posting passes its input caps. An entirely empty operation allocates no bitmap and reports zero candidate state.

Candidate entry, staging, final cutoff-tie, output-entry and bitmap limits fail the complete operation. The collector latches errors and exposes no partial result. The streaming operation discards it and clears all reader pins on failure. Exact distinct-scanned and physical-work counts remain separate from retained and wire candidate counts. For the optional policy, top-level candidate peak entries include the declared insertion staging allowance; the nested working-set metrics identify that meaning explicitly.

Output-vector capacity and HashMap capacity are recorded separately. Their allocations can overlap while results are assembled. BTree node allocations, hash control bytes, provider Arrow decoding/cache, quantizer scratch, allocator overhead and RSS remain outside payload counters. Standard BTree allocation exhaustion can abort the process; it is not converted to a structured configured-limit error. No total-memory or unconditional M-bound claim is made, because all cutoff ties must fit or the complete request fails.

The persisted Rust test passes in 0.01 seconds against ten physical copies, eight current copies and seven distinct live IDs. The collector returns exactly the same six M=1 cutoff ties as the complete oracle and retains the correct seven-ID distinct count. It additionally rejects a cutoff-tie limit, output limit and the original streaming total-unique limit, with zero pins after errors. Four strict Python policy tests pass in 0.011 seconds. The source/native reader is frozen before any CLI replay; replay requires its separate independent admission.
