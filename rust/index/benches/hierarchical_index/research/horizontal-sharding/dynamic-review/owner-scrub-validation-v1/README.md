# Batch scrub validation at authoritative owners

The same-process ablation removes current-version messages and records substantially less system CPU and fewer context switches, even with more version and predicate work. Its independent schedules do not establish a fixed-work timing ratio. The distributed-applicable next cut is to reduce message count while still asking the actual authoritative owners for versions. This package implements that cut for scrubbing only; it does not use the direct read pointer or prevalidate NPA eligibility.

A scrub reads the source posting's ordered ID/version rows, marks rows whose version differs from current authority, then removes their IDs, versions and code bytes with the existing swap-removal algorithm. The new opt-in validator processes at most 64 rows at a time. Outside every actor callback it sorts and deduplicates the relevant IDs, acquires their existing transfer locks, resolves the current owner directory and groups requests by owner. Each owner callback reads its own current-version map and returns only the requested versions. The coordinator converts those replies into ordered validity flags and releases the ID locks before processing the next batch. A missing directory entry remains invalid, matching the accepted path. No version map or mutable authority mirror is copied centrally.

The original full source-row snapshot, validity-flag vector and swap/code loop remain unchanged. A tail row brought forward by a swap carries its original validity flag. Duplicate IDs acquire one conflict lock per batch but retain a separate result for each physical row/version. The temporary row snapshot and flags remain proportional to this one leaf's physical rows, as in the accepted path; this change does not claim a whole-operation 64-row memory bound. ID-lock sets and each owner request/reply contain at most 64 rows. With P rows and O owners, the current-validation callback upper bound is `ceil(P/64) * min(O,64)`, plus the same source snapshot and application callbacks. The actual request distribution determines the saving.

The source leaf stays stable because the kernel retains its mutable node guard throughout the complete backend scrub call. Registration acquires target-node access before its per-ID lock; after taking that ID lock it performs only owner/directory work and releases the lock before recursive balance. A take removes the global node before taking owner payload. Leaf installation uses fresh IDs or IDs already removed from the node map. The opt-in path explicitly rejects installation over a live leaf before changing owner data, closing the otherwise premature owner-write boundary. Parent edits and take operations wait on the same source node access. Placement occurs only after workers join. No new global structural lock or revision system is introduced.

Sorted ID locks prevent two multi-ID validation batches from acquiring the same lock set in opposite order. A transfer already holds the corresponding per-ID lock across source removal, destination installation and directory update, so a batch cannot inspect the transfer gap. Owner callbacks never acquire node or per-ID locks and never synchronously wait for another actor. They take only their local version-map read guard and return bounded values. Consequently an actor cannot wait on a coordinator-held lock while the coordinator waits for that actor. The live-node install guard and joined placement are part of this supported POC contract, not a recovery protocol.

NPA still performs each live current-version check, evaluated-ID decision and immediate reassignment at its original point. Validation flags are used only by the current scrub, not by later operations or NPA. Concurrent mutations can occur between completed validation batches, just as versions can change between checks in the accepted scrub. This is not a cross-call version cache, lease or delayed mutation publication. The default policy remains the accepted individual-read path, and the native CLI does not enable this new policy.

The fixed 130-row fixture spans two owners, stale rows, a missing owner entry and a short tail. An independent original-slot permutation oracle verifies exact ID/version/code-byte removal order. Current-owner callbacks decrease from 129 to five across three batches, with zero direct-pointer reads. A separate duplicate-ID test checks per-row version results, empty input and rejection above the 64-row request cap. This is exact work removal, not timing evidence.

The concurrency tests pause an actual versioned registration inside its source-removal/destination-install gap and prove the batch waits before validating. Another test calls the actual kernel scrub, attempts concurrent source-node removal while its guard is held, then restores and saves the node with a complete eight-row census. A live-leaf overwrite is rejected before owner mutation. The multi-region construction enables batched scrub while disabling direct reads and predicate batching; it passes saved current membership, every vector bit, independently recomputed posting codes, exact full-ID reference distances and pinned old-reader checks. Its observed tree has depth four, 48 nodes, 43 splits and 19 merges. It validates 23,661 physical rows through 737 owner calls in 735 batches; those are this run's work counts, not a stochastic timing comparison.

Twelve focused tests and a native benchmark-target compile check pass. The private-test-entry and test-only missing-Clone compile failures remain preserved, each with zero tests executed. Intermediate passing evidence before the live-install guard remains separately retained. Passing negative tests deliberately print caught wrong-owner, request-cap and live-install panics. No source archive or staged index is overwritten. No cloud run, new corpus, timing gain, ANN quality, cross-host transport or production recovery claim is made. The actor request boundary demonstrates owner-local grouped validation; a physical transport implementation would still need to preserve the coordinator's lock/phase contract and exact request binding.
