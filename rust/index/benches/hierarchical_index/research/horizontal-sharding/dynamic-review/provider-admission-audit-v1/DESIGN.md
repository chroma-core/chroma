# Provider admission: allocation and reference boundaries

A buffer limit must be enforced before the allocation it claims to bound. The current provider cannot impose that contract through its storage callback: storage has already allocated the encoded object before the callback runs. The present streaming limit correctly bounds selected-leaf owned arrays after provider decoding; it does not bound the transport buffer or Arrow decoding. This document proposes hooks and focused proofs only. No production storage, decoder or reader behavior changes.

## Current allocation path

| Stage | Actual behavior | A check here can establish | It cannot establish |
| --- | --- | --- | --- |
| Local encoded read | Local storage calls fs::read and returns Arc<Vec<u8>>. | A check in the current caller can reject the returned object. | It cannot prevent the already allocated file buffer. |
| S3 encoded read | One GET reads Content-Length, allocates that complete Vec, then read_exact fills it. Parallel reads also allocate the complete output buffer. | The same GET header can support a future pre-allocation encoded-size check. | A separate HEAD or a callback check does not bound the existing allocation. SDK/network buffering remains separate. |
| Storage dispatch and request sharing | get/fetch return complete byte vectors. GetOptions has priority, consistency and parallelism fields, with no byte budget. Admission-controlled request sharing keys the batch by object keys. | New request-count limits can limit concurrent fetch work. | Request-count admission does not reserve encoded bytes or keep them charged through decoded references. A new byte policy must not silently join a differently admitted shared fetch. Shared requests need compatible admission identity and explicit reservation ownership. |
| Block decoding | BlockManager receives the complete encoded Arc. Exclusive Vec ownership becomes zero-copy Bytes; a shared Arc falls back to copying the bytes. Arrow reads the footer/schema and record batch. | A future checked IPC preflight can reject unsupported layouts before the decoder. | Block.get_size is measured after decoding. A size check there is not a decoding allocation bound. |
| Root decoding | RootManager separately reads complete bytes and creates a FileReader before constructing the sparse index. | A root-specific encoded and metadata preflight can reject before that decoder path. | A block-only limit leaves this allocation path uncovered. |
| Reader references | BlockfileReader stores each fetched Block in loaded_blocks and returns references whose validity depends on that map retaining its blocks. | Explicitly ending all returned borrows permits a safe clear. | Evicting the provider cache or limiting fetch futures does not release these reader references. |

The existing Arrow writer uses aligned, uncompressed IPC options. The pinned lock uses Arrow IPC 55.1.0 without compression dependencies; this audit does not claim compressed decoding is enabled in the current build. Arrow still allocates schema and reader metadata, and the owned-byte path does not prove a whole-decoder allocation bound. A future format-admission contract must retain rejection of unsupported compression and explicitly budget any compression feature if enabled. It must validate supported schema shapes before the relevant allocations. Encoded bytes alone do not establish a whole-operation bound on decoded arrays, schema metadata or allocator overhead. The persisted maximum-block-size setting describes block construction; the read callback does not enforce it against actual encoded bytes before allocation.

The shared-Arc fallback is another distinct allocation. A future reservation must charge the copy before calling Block::from_bytes, rather than assuming every read transfers its original Vec without copying. Root sparse-index copies and root metadata require their own accounting. Retained cache targets remain separate from active transport, decode and reader-reference reservations.

## Reference lifetime and concurrent work

Streaming scoring already scopes one posting and its centroid at a time and clears each authoritative scalar-version block after copying the scalar value. It ends the leaf borrows before clearing all three reader block maps. This provides a useful local operation boundary; it does not constrain startup metadata reads or provider cache retention.

Selected-ID reranking uses buffer_unordered(32), but completed futures leave fetched blocks in the vector reader's loaded_blocks map until the complete operation ends. The value 32 therefore limits concurrent futures, not the number of retained blocks over the operation. The general selected-leaf path has the same distinction. Reader startup also materializes leaf and internal-node ranges, whose range path joins block futures and retains blocks while building owned tree metadata. The existing range stream still uses the same retaining get_block path and has no safe per-block completion callback.

A narrow future rerank implementation can use exclusive reader access, copy each exact distance inside a lexical vector-borrow scope and clear that vector-reader map before the next fetch. That would bound the additional vector-reader block count for that operation, not the bytes in an individual block, the root metadata or other readers. A real proof needs several persisted vector blocks; the retained eight-row fixture has too few blocks to establish this count bound. No new rerank mode or schema is added in this audit.

## Required integration hooks

The storage hook needs optional encoded-object size and in-flight byte reservation requirements in the existing get/fetch contract. Local reads must open one file, check its metadata before reserving, and read through a bounded reader that rejects a later growth beyond the limit. S3 must validate the same response's signed Content-Length before converting it to usize, check the admitted limit before its destination allocation and enforce the limit while consuming the body. Unknown lengths must use bounded reads or fail closed under the option. Every backend must implement or explicitly reject the option. Current defaults remain unchanged.

The provider hook needs a separate decoded-layout admission contract for both blocks and roots. It must check integer arithmetic, footer/schema byte lengths, bounded schema traversal depth, record batches, encoded buffer ranges and supported decompression before allocating the admitted decoded structures. The preflight parser itself needs a budget; calling an allocating metadata parser and inspecting its result afterward is too late. The required copy path must reserve its additional bytes first. Post-decode counters can verify a result, but cannot replace those checks.

The lifetime hook must hold reservations until the actual admitted allocation is no longer referenced. Returning a token when a fetch callback completes is too early if a cache or reader retains the decoded object. The current Arc<Vec<u8>>, Block, RootReader and borrowed-value interfaces do not carry such lifetime tokens. A safe design must bind guards to the owned allocations and their clones, with explicit treatment of shared buffers, caches and active readers. This requires storage and blockstore API work rather than a benchmark-wrapper cache.

## Smallest future proof before activation

1. An actual local-provider test creates a tiny encoded object just over a small configured byte limit. It instruments allocation order and proves rejection before the full-object Vec and before decoder entry. A same-length malformed footer and a source that grows after metadata inspection reject under bounded read, rather than relying on stat as an immutability guarantee.
2. A supported tiny IPC fixture and an oversized declared decompression or schema fixture demonstrate pre-decoder rejection. Unsupported compressed layouts fail closed under the option. The root-file decoder has its own oversized-input case.
3. A forced error after reservation and a cancelled fetch release the in-flight permits. A subsequent normal fetch succeeds. Shared consumers with different policies do not inherit an unadmitted fetch or release a guard while another consumer retains the object.
4. A tiny real index deliberately persists its eight vector rows across several small blocks. Exclusive serial reranking matches the existing complete exact-ID/distance oracle, measures its additional active block count and leaves no vector pins on success, late error and retry. An old-generation reader remains valid; no provider-wide clear is triggered merely by dropping another reader.
5. Every test distinguishes encoded destination capacity, decoded payload, extra copies, active references and retained cache entries. Counters do not establish process RSS or allocator-failure handling. The existing full validation and 100,000-row cap remain in place.

## Decision and next integration work

A complete pre-decode byte-admission implementation requires production storage, shared-fetch, decoder and allocation-lifetime interfaces. Adding only a callback length check or a cache target would misstate that guarantee. This epoch therefore stops at the concrete source-bound design and leaves current defaults and full validation intact. The next implementation priority is the existing compactor task and saved-publication lifecycle, rather than another local cache or a falsely bounded decoder wrapper. A narrow serial-rerank count proof can be considered separately when that specific interface is authorized and reviewed.
