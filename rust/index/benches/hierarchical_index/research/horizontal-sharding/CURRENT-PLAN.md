## Development principles

Optimize for the pace of useful learning. An experiment succeeds when it gives enough trustworthy information to choose the next action. It does not need to resolve every uncertainty or produce publication-quality measurements. Match the strength of each conclusion to its evidence, record the limits, and move forward once further precision would not change the decision.

- **Start with a decision.** Maintain a ranked list of problems and experiments. Choose the most promising question relative to development time and cost. Read existing findings and inspect the code first; state what result would change the next action before adding instrumentation or launching a run.
- **Exercise the behavior with the smallest sufficient workload.** Choose size from the tree shape, concurrency or working set needed to expose the problem. A tiny test that misses the behavior is uninformative. Use larger benchmarks, including millions of vectors, when they answer the question more efficiently and are within the active authorization. Stop at the decision or resource limit; avoid automatic size sweeps and linear extrapolation from shallow trees.
- **Measure enough to distinguish the leading explanations.** Add only the counters, timings or profiles needed for the current question. Approximate measurements are sufficient when their uncertainty does not affect the next decision. Complete metric coverage and perfectly precise attribution are not prerequisites for progress. Keep measured findings separate from hypotheses, and avoid adding overlapping worker durations as if they were separate parts of elapsed time.
- **Keep the experiment loop ready to run.** Maintain a runnable benchmark harness, reuse retained inputs and working tools, and use incremental builds. Run focused correctness tests for the behavior changed; use broader checks at architectural or correctness milestones, or when a concrete risk warrants them. Consolidate required review around coherent changes. Reuse supported execution controls rather than building new machinery for each experiment.
- **Use enough repetitions to make the decision.** One representative profile and one matched comparison can be enough to select the next experiment. Repeat or refine only when noise, changed work or another uncertainty could change that choice. Evidence sufficient to prioritize a hypothesis may still be insufficient to claim a causal speedup.
- **Follow the fast unsharded implementation by default.** Deviate for a structural requirement, measured benefit or explicit hypothesis worth testing. Implement the agreed architecture; a one-machine configuration must exercise it. Intermediate implementations need a concrete reason and a clear role in reaching that architecture.
- **Reassess slow progress.** If preparation, tooling, review or coordination consumes disproportionate time, identify what is actually blocking the decision and simplify the approach. Once the experiment is informative enough, execute it and interpret the result instead of expanding its scope. Preserve correctness, sandbox identity, spending limits and required shutdown controls while reducing avoidable process overhead.

### Reduce benchmark launch time

Changing the vector count for an existing binary should be a configuration change. Aim for one command and tens of seconds to launch a run when machines, binaries and inputs are ready, excluding necessary input preparation. This is a workflow target, not a measured capability. Record preparation and launch time separately from benchmark execution so avoidable overhead is visible.

- **Use one parameterized runner.** Accept vector count, batch size, worker count, owner capacity and profiling mode as arguments. Give each run a fresh output directory and immutable configuration record. Avoid copying and editing the harness for each experiment.
- **Keep machines running during an active sequence of authorized experiments.** Start the machines and install independent local and remote absolute shutdown guards once per bounded development session. Subsequent runs may share that open session only when they fit within its fixed deadline and budget. Stop promptly when the sequence finishes or work shifts to substantial coding. Never reuse a closed window or silently extend a deadline; a later session requires fresh guards. This guidance does not extend the current experiment's stopping condition.
- **Reuse verified inputs and binaries.** Retain commonly used input sizes, binary hashes and provenance. Perform lightweight checks before reuse, and reserve rebuilding, transferring or preparing data for actual changes. Preserve fresh identity and resource checks required by the execution controls.
- **Review the changes that matter.** An unchanged binary and reviewed runner need configuration validation and existing admission checks. Repeat implementation review or correctness tests when code changes or new evidence creates a concrete reason, rather than because another benchmark starts. Normal tool approval controls continue to apply.
- **Keep one operator responsible through completion.** Let the same operator prepare, launch, collect and close the run. Batch independent checks and avoid unnecessary handoffs, repeated status polling and coordination pauses. Run independent read-only input and binary checks on the two hosts concurrently. A fresh 3M input check takes about 70 seconds per host in epoch21; serializing those checks adds avoidable startup delay. Do not launch duplicate checks or overlapping writers.

Short idle periods can be worth their cost when another experiment is imminent. At the recorded rate of $4.032 per machine-hour, keeping both task machines running for ten minutes costs about $1.34. Account for that time within the existing spending limit; stop the machines during long coding or planning intervals. Keeping machines available removes startup overhead, while the reusable runner removes repeated scripting and review work.

## Future optimization: buffer new full vectors before saving

### Routing-memory arithmetic to validate

For a compact routing-only representation, assume N vectors, an average of 2,000 vectors per leaf, average internal fanout 100, 768-dimensional centroids stored at four bits per component (384 bytes), three f32 scoring values (12 bytes), and one 64-bit child ID (8 bytes). The estimated core routing bytes are `(N / 2000) × (100 / 99) × (384 + 12 + 8)`. This gives approximately 20.404 billion bytes, or 20.4 decimal GB, for routing metadata representing 100 billion vectors. A 512 decimal GB budget corresponds arithmetically to about 2.5093 trillion represented vectors.

The roughly 2.5 trillion figure is an arithmetic upper bound for this routing metadata model, not a claim that one machine stores those vectors or their postings, and not measured capacity or throughput. It assumes each child centroid appears once in compact parent arrays, with no retained full-precision copy. It excludes maps and directories, allocations, caches, temporary copies, retained generations and workload headroom. Those costs reduce practical capacity. Average occupancy is an assumption, not a guarantee or necessarily a conservative choice. Validate the complete actual layout and resident memory alongside the routing-cache experiment before using the estimate for provisioning. This dedicated-budget thought experiment establishes neither multi-index fleet capacity nor aggregate memory fit or throughput when many indexes share reader machines.

## Future experiment: adapt centroid precision to reader demand

Compare loading 1-bit centroids for fast initial readiness with loading 4-bit centroids for cheaper repeated queries at matched recall. The hypothesis is that reduced loading cost benefits indexes receiving few queries between load and eviction, while better navigation precision amortizes over sustained use. A large concurrent burst may favor 4-bit centroids immediately: wider beams consume additional resources when demand is already high. Treat this as an unmeasured saved-reader experiment; the current 4-bit centroid baseline and 1-bit posting codes remain unchanged.

Compare three strategies on the same immutable tree and fixed held-out queries: load 4-bit centroids immediately; retain 1-bit centroids and compensate with search work; or start at 1 bit and upgrade asynchronously to 4 bits. Queries retain full-precision query vectors. Tune navigation beam and reranking work separately to reach comparable measured recall; reranking cannot recover a neighbor whose branch navigation never visits. Choose query counts, arrival rates and concurrency that distinguish short use after a cold load from sustained reuse, with explicit memory, runtime and cost bounds rather than an automatic sweep.

First measure the fraction of cold-load bytes and time attributable to centroids. Reducing their packed coordinates from 4 bits to 1 bit does not reduce IDs, links, scoring metadata, posting codes or full vectors. Account for producing and storing both representations, loading and switching costs, temporary memory while both are resident, and interference between background loading and foreground queries. Both representations must describe the same immutable generation; switch coherent routing records while preserving in-flight readers.

Measure time to the first answer at the selected recall, subsequent query latency and tails, throughput, CPU work, bytes read and transferred, peak memory, and total serving cost over the queries completed before eviction. Estimate the upgrade break-even point from additional loading cost divided by per-query savings in a consistent cost unit, and assess latency separately. Compare a simple query-count trigger with a policy based on expected remaining demand before eviction. Consider keeping the frequently used upper tree at 4 bits and upgrading hot subtrees or routing blocks first as a later variant, linked to the reader-caching experiment below.

Adopt adaptive precision only if its loading and query savings justify its total cost and memory at matched recall; otherwise retain immediate 4-bit loading. Record workloads where the strategy loses, and stop on generation mixing, incorrect results or resource limits. This entry schedules no implementation or benchmark and does not change the active construction work.

## Future experiment: popularity-guided reader caching across indexes

Compare full routing-tree caching, demand-loaded routing and popularity-guided selective prefetch/cache placement for immutable saved readers. The hypothesis is that concentrating a bounded cache on frequently used data can reduce network rounds and query latency without reserving space for every routing tree. This is our proposed adaptation; it has no measured benefit for this index and changes neither the current baseline nor writer ownership.

Beehive proactively replicates objects using measured popularity and a target lookup-hop cost, with smoothed estimates and hysteresis to limit churn. Its model assumes similar replication costs and infrequent updates. See Ramasubramanian and Sirer, NSDI 2004, [Beehive: O(1) Lookup Performance for Power-Law Query Distributions in Peer-to-Peer Overlays](https://www.usenix.org/conference/nsdi-04/beehive-o1-lookup-performance-power-law-query-distributions-peer-peer-overlays) and the [full paper, sections 2.1–2.3](https://www.cs.cornell.edu/people/egs/714-spring05/beehive-nsdi.pdf). Its exact-key distributed-hash-table result does not imply constant-time approximate nearest-neighbor search. Its replication/update protocol is separate from our exclusive-membership transfers and provides no validation of our 70%/80% vector-budget thresholds.

Preserve the same candidate-selection rules, query cohort, recall requirements and compatible immutable generations across cache strategies. Cache misses must fetch required routing data rather than silently prune candidates. Read-only generation caching can retain copies without granting mutation authority; the experiment does not adopt mutable indexed-vector replication. Account for popularity measurement, prefetch and cache-maintenance work as well as query work.

For the future multi-index reader fleet, vary neither policy nor workload automatically: first choose a bounded workload that exercises shared-budget pressure, a specified popularity distribution across indexes and routing records within each index, and index loading/unloading. Include many small indexes where representative, record actual index sizes and traffic skew, and compare whole small routing trees with selected records as cache units. Test both cold loads and warm reuse; if the workload fits entirely or never changes residency, report the limits on conclusions about admission, eviction and unload costs. Initial single-index results cannot establish this fleet behavior.

Before execution, define reader placement and request routing, aggregate memory budgets, admission/eviction rules, safe unload/reclamation and immutable-generation pinning for in-flight queries. Choose the smallest fixture that reaches the named cache/working-set condition, then set runtime, cost and memory bounds. These reader-fleet mechanisms are future obligations, not requirements for the current single-index construction experiments or multi-index writer orchestration.

Measure bytes fetched and prefetched, total and per-worker memory across routing/postings/full vectors/request state, network rounds, cold load time, index load/unload costs, query latency and tails, cache hit rates and cache churn. Include generation overlap and memory retained by in-flight queries after unload. Compare under the same aggregate budget and quality/candidate-selection contract. Stop on incorrect results, generation mixing, unsafe reclamation or the agreed resource/time bound; otherwise retain a policy only when complete serving costs and latency justify it, recording adverse results. This entry does not launch implementation or benchmarks.

## Future experiment: use cached routing to order live balancing searches

Test whether a routing snapshot taken at the start of balancing can reduce waiting for searches on other shards. This is separate from saved-reader routing and stable insertion-phase routing: balancing changes the tree, so the snapshot is a potentially stale guide. Preserve live global cross-shard neighbor eligibility as the baseline. This is an unmeasured future experiment; it adds no implementation or execution to the two-machine correctness milestone.

Navigate the cached tree with full-precision construction centroids using the vector being reassigned, or the search vector appropriate to the operation. Group candidate leaves by shard and initially rank shards by their closest cached candidate distance. Contact a few promising shards concurrently and ask each to search its current tree for live candidates. Combine those results and broaden to additional shards in later waves. Local search may begin immediately to overlap network delay without automatically preferring its result.

Fixed placement during balancing does not keep routing current. Splits, merges, root and ownership metadata changes, and reassignment can retire cached IDs or change useful destinations. Retry or redirect retired routes as necessary. Revalidate the live source and destination and coordinate the actual transfer. These checks protect membership correctness; they cannot discover a better destination on an unsearched shard.

Distinguish ordering requests with broadening or fallback from skipping shards through approximate early stopping. Cached centroid distances are hints, not distance lower bounds. Changing request order alone need not reduce total requests or reproduce live global beam selection. Wider cached candidate sets, selective refresh of changed regions, wave size and early-stop rules are alternatives to evaluate, not adopted settings. Unchanged neighbor selection is not guaranteed.

Compare against live global navigation using complete balancing and build cost, communication rounds and bytes, cache preparation and refresh cost, peak memory, stale-route and retry rates, destination differences, resulting clustering, and held-out recall at matched query work. Charge snapshot construction across complete add/balance cycles. Keep ordering-only and early-stopping results separate so any latency saving can be distinguished from reduced search work or changed quality.

## Future scaling hypothesis: coordination during balancing

Larger indexes may spend a smaller fraction of balancing time coordinating centroid updates if more balancing stays within independent subtrees and fewer local changes require updates to shared ancestors. This remains an unmeasured hypothesis. More independent subtrees may reduce conflicts, while larger existing subtrees may only increase local computation. If local changes continue to require global publication permission, that shared bottleneck may persist or worsen as worker count grows.

Include this question in a future bounded scale comparison; it need not be a separate experiment. Measure shared-ancestor updates and publication attempts per million inserted vectors, discarded preparation and retries, publication wait and hold times, conflicts by ancestor, and the number of independent subtrees active during balancing. Record subtree sizes, tree depth, insertion batch size, worker count, balancing elapsed time and CPU consumption. Separate index-size effects from worker-count and batch-size effects. Distinguish fewer conflicts and less coordination work from coordination merely becoming a smaller fraction of longer local computation. The current 3M results do not establish behavior at substantially larger scales.
