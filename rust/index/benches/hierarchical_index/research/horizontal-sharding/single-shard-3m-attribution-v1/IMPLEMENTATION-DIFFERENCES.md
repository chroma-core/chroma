# What can explain a construction-time difference

Both benchmark arms construct one local tree with the same vector order, settings, clustering routine, posting representation and insertion batches. The candidate adds concurrent resident records and a different balancing schedule. The comparison measures those implementation choices as well as the owner interface; it does not measure network communication or physical distribution. This map describes source mechanisms before interpreting runtime evidence.

The owner interface calls the writer directly and reads its current root when reporting ownership. It adds no per-vector routing directory, sequential executor or remote request on the measured path ([owner interface](/private/tmp/chroma-hierarchical-spann-sharding/single-shard/rust/index/benches/hierarchical_index/owner.rs:58)). No substantial local timing difference should be labeled unavoidable sharding overhead merely because it occurs in the candidate.

| Mechanism | Candidate versus reference | Evidence that can distinguish explanations |
|---|---|---|
| A worker reads or changes a resident node. | The reference keeps node values directly in a concurrent map and accesses them through map guards. The candidate uses that map to find a shared record handle, releases the map guard, then acquires the record’s own read/write lock. Every lookup clones and later releases the handle. Retirement empties the old record before unlinking it. These changes prevent a long node operation from retaining a map-bucket lock, but introduce handle and lock work on the read path. | Compare stable insertion CPU with navigation work by level. CPU samples in record access, reference counting or lock operations can support an explanation; inlining can charge those instructions to callers. Equal distance counts alone do not equalize all lookup work. Sources: [candidate lookup](/private/tmp/chroma-hierarchical-spann-sharding/single-shard/rust/index/benches/hierarchical_index/writer/node_store.rs:35), [reference node map](/private/tmp/chroma-hierarchical-spann-sharding/matched-reference/rust/index/benches/hierarchical_index/writer/mod.rs:46). |
| Workers receive balancing jobs. | The reference snapshots eligible leaves, starts at most one worker per initial leaf and joins before discovering new work. The candidate starts the configured pool, admits leaf/internal follow-ups into a producer-aware queue and wakes waiting workers. It still uses joined outer rounds for transfer retries and residual work. Queue waiting therefore includes periods when only a few jobs exist. | Compare per-cycle CPU, tree shape, NPA work, retries, queue waits and active-job maxima. Worker elapsed time includes waiting. Sources: [reference round dispatch](/private/tmp/chroma-hierarchical-spann-sharding/matched-reference/rust/index/benches/hierarchical_index/writer/writer.rs:1180), [candidate dispatch](/private/tmp/chroma-hierarchical-spann-sharding/single-shard/rust/index/benches/hierarchical_index/writer/writer.rs:1295), [candidate queue](/private/tmp/chroma-hierarchical-spann-sharding/single-shard/rust/index/benches/hierarchical_index/writer/scheduler.rs:51). |
| A split or merge changes routing. | The reference uses its structural mutex, including recursive internal splitting and its clustering preparation. The candidate prepares internal replacements outside a region reservation, revalidates child identities/centroids and ancestry, then publishes under an overlapping-subtree reservation. Parent edits include the next ancestor because its cached centroid row changes. A shallow tree can therefore reserve the root for every short publication. | Inspect internal jobs, structural wait/hold counters and CPU samples. Leaf split-size samples and leaf k-means timers omit internal clustering. Sources: [reference internal split](/private/tmp/chroma-hierarchical-spann-sharding/matched-reference/rust/index/benches/hierarchical_index/writer/writer.rs:2128), [candidate internal split](/private/tmp/chroma-hierarchical-spann-sharding/single-shard/rust/index/benches/hierarchical_index/writer/writer.rs:2278), [candidate region scope](/private/tmp/chroma-hierarchical-spann-sharding/single-shard/rust/index/benches/hierarchical_index/writer/writer.rs:2635). |
| Navigation encounters a retired node. | The candidate restarts up to four times when its captured root or selected node disappears, then retains live destinations. The reference skips missing nodes without restarting the traversal. Both use full-precision construction navigation and packed parent scoring payloads. Different visibility and retry behavior can change candidate destinations and later clustering work. | Compare navigation retries, missing nodes, per-level scored candidates and NPA evaluations. More navigation work is not automatically slower execution of the same work. Sources: [candidate traversal retry](/private/tmp/chroma-hierarchical-spann-sharding/single-shard/rust/index/benches/hierarchical_index/writer/writer.rs:729), [reference traversal](/private/tmp/chroma-hierarchical-spann-sharding/matched-reference/rust/index/benches/hierarchical_index/writer/writer.rs:724). |
| Reassignment or a split creates more work. | Both arms claim affected leaves, recheck current source membership, append accepted rows and physically remove them from the source. The candidate also schedules changed sources/destinations immediately. Explicit scheduling of replacement leaves occurs after the split’s neighbor-reassignment work; transfer-triggered scheduling can expose eligible leaves earlier. Thus “immediate” means ready follow-ups enter the current queue, not that every new child necessarily starts at its first publication. | Compare transferred rows, source rows scanned, NPA evaluations and deferred groups. A transfer retry counts a group, not unique rows or messages. Sources: [candidate transfer](/private/tmp/chroma-hierarchical-spann-sharding/single-shard/rust/index/benches/hierarchical_index/writer/writer.rs:1988), [reference transfer](/private/tmp/chroma-hierarchical-spann-sharding/matched-reference/rust/index/benches/hierarchical_index/writer/writer.rs:1842), [replacement scheduling](/private/tmp/chroma-hierarchical-spann-sharding/single-shard/rust/index/benches/hierarchical_index/writer/writer.rs:1548). |
| Insertion groups posting updates. | Both arms collect worker buffers across the complete insertion batch, combine them by destination leaf and append once per leaf after collection workers join. They use the same coordinate/ID preflight, vector storage and one-bit quantization. The candidate’s record access mechanism still applies to navigation, leaf reads and the final append. | Separate preflight, collection and append wall time, process CPU, quantization and navigation work. Sources: [candidate batching](/private/tmp/chroma-hierarchical-spann-sharding/single-shard/rust/index/benches/hierarchical_index/writer/writer.rs:559), [reference batching](/private/tmp/chroma-hierarchical-spann-sharding/matched-reference/rust/index/benches/hierarchical_index/writer/writer.rs:554). |

Per-node synchronization and coherent structural publication protect concurrent work in this implementation. Their exact data structures and scheduling policies are implementation choices that can also apply to an unsharded writer. Immediate jobs are an agreed design feature, not a communication requirement. Retirement handling addresses concurrent routing visibility. The one-owner experiment contains no ownership transfers between machines, replicated upper-tree service or cross-machine coordination whose cost could justify a generic distributed overhead allowance.

Clustering convergence and scheduling remain uncontrolled sources of different work. Sum of split input rows is a useful workload proxy, not a count of clustering iterations. Timers nested inside concurrent jobs overlap and cannot be summed into a wall-time decomposition. Interpret sampled CPU shares with their phase windows, unknown stacks and sample counts; interpret waits separately. Runtime conclusions belong in the experiment report after the measured evidence arrives.
