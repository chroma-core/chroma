# A bounded device-side filter for exact references

The next optional reference engine reduces scores on the GPU before transferring candidates to the CPU. The tested full-score engine remains the fallback. This proposal requires separate code, numerical review and a new measured runtime gate; it does not change the completed pilot's contract.

The current engine transfers every approximate score to the CPU. At one billion vectors and 11,000 queries, FP32 scores alone total 44 TB before candidate vectors, IDs and checks. The completed OS-cache-cleared 1M/200-query run takes 13.786 seconds overall while synchronized scoring takes 0.188 seconds. Kernel time alone therefore cannot predict larger reference throughput.

## The interval rule

For each vector block, compute a conservative upper bound on every vector's Euclidean norm on the CPU while validating its finite float32 inputs and range. For each query, combine its upward-rounded norm with that block maximum in the existing dimension-dependent error formula. This produces one scalar distance-error bound E for the whole block. A shared bound can retain more candidates than per-vector bounds, but cannot exclude a candidate that those bounds retain.

Let s be the approximate float32 distance. Form lower and upper endpoints in float64 on the GPU as nextafter(float64(s)-E, negative infinity) and nextafter(float64(s)+E, positive infinity). Converting a finite float32 score to float64 is exact. Transfer E as float64 without narrowing; calculate it using the independently tested CPU bound. The GPU must support the same finite float64 subtraction and nextafter semantics in the deployed runtime. This uses temporary float64 endpoint arrays for one bounded block, rather than a full-corpus float64 score matrix.

For each query, update the running k smallest upper endpoints using all current-block upper endpoints before filtering any row. Selection must use exact float64 values and comparisons; approximate top-k selection or a narrowed threshold is outside this contract. Maintain the k smallest upper endpoints seen across all processed blocks. Their kth value T is an upper bound on the true global kth distance among that processed prefix. When fewer than k vectors have been processed, use positive infinity and retain the entire prefix. Select every current-block candidate with lower endpoint less than or equal to T. T can only decrease as blocks arrive. A candidate excluded now cannot enter the final top-k; retaining extra earlier candidates is safe. Equality stays inclusive so cutoff ties survive.

Transfer only selected local indices and approximate scores after the device filter. Resolve stable global IDs from the immutable block range and rerank their original float32 vector/query values with the established float64 CPU scorer. Merge by distance and global ID. Never cap retained candidates or silently change precision. All-tied data can require transferring the entire corpus for every query; spill bounded batches or fail with an explicit resource-limit report instead of dropping candidates.

## Gates before a new GPU run

Test the device selection against the existing CPU interval helper for every block and query on small fixtures. Include a processed prefix smaller than k, all cutoff ties, signed nonunit values, near ties, one query, multiple queries, and block boundaries. Deliberately rounded FP16/TF32 scorers must fail the adversarial arithmetic probe. Reject subnormal inputs, possible overflow, nonfinite outputs and any unsupported arithmetic setting before accepting results.

Test CPU-versus-device endpoint construction around cancellation, signed zero and adjacent representable cutoffs, including nextafter and exact float64 selection. Apply the existing overflow gate to the certified block-max norm before every kernel. Retain the three complete full-score check queries across every corpus row. These queries bypass filtering and validate rejected rows as well as retained rows. Compare their error envelopes against independent float64 scoring, and compare complete top-k IDs and distances with the preserved 1M references for all integration queries. Report endpoint construction, selection, synchronization, candidate transfer, vector reread, rerank and whole-run time separately. Record peak device and host memory, retained counts, source reads and all input/runtime hashes.

A faster implementation can exploit the uniform E to avoid materializing both endpoint arrays, but its rounding and threshold proof needs independent review before adoption. The explicit float64 endpoint version is the initial correctness target. No GPU launch or 100M run follows from this note alone; the next execution waits for the measured storage, ingestion and numerical gates.

Independent review confirms the threshold direction, inclusive cutoff ties and uniform-bound proof. The review requires all current-block upper endpoints to update the threshold, exact float64 selection, complete unfiltered check queries, and explicit endpoint-rounding conformance. Implementation remains deferred; the existing tested engine is unchanged.

## Admission and batching

The optional implementation fixes the initial hardware gate at 32 queries and 32,768 source rows per score batch. It uploads each source block once, then handles query batches; endpoint construction and running thresholds currently process one query at a time. The full 11,000-query pool is never scored as one matrix. A pure planning helper includes visible source/query/score/state buffers, doubles the estimated allocations and reserves another 2 GiB for workspace. Its 11,000-query, k=100 estimate is 2,506,824,704 bytes; admission requires this to fit within half the available device memory. Query batches above 256 reject. Vendor workspace is not formally bounded by this estimate, so measured peak memory and explicit failure reporting remain hardware gates.

Memory fit does not establish useful throughput. The current per-query interval/top-k calls can spend time in kernel launches and synchronizations even after full-score transfer disappears. Measure those costs in the bounded 1M comparison before projecting 11,000-query references. A later batched interval implementation can hold a query-batch-by-source-block endpoint matrix and update one float64 kth-upper state per query with exact top-k along the row axis. It must use the same inclusive mask, preserve uncapped ties, and pass the existing endpoint/history/oracle tests. Its memory estimate must scale endpoint and selection workspace with the query batch; it cannot reuse the current one-query endpoint estimate. No such batched optimization is claimed as implemented or measured.
