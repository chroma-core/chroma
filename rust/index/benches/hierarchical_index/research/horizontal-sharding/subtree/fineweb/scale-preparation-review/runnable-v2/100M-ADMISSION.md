# A bounded 100M preparation attempt

A 100M attempt should first use the verified two-file ingestion path with added stage measurements, on one dedicated storage node with a six-hour ceiling. Launch waits for the matched 10M publication, read-capacity decision and the concrete checks below. Existing sandbox authorization covers this work; this document does not start a node or download data.

## Measured basis and time budget

Fresh 10M ingestion takes 676.928 seconds, requests 14.803 GB of source bytes and writes 33.629 GB of ingestion artifacts. The complete preparation retry reuses that ingestion: model fitting takes 31.497 seconds, routing 114.163, full ID and bitwise audit 156.036, sample/UUID checks 20.746, two 100-query exact-reference scans 199.953 together, and three independent whole-corpus checks 56.134. The retry's 998,336 KiB peak RSS is measured for that process; it is not a prediction for every concurrent child at 100M. The guard must sample the entire owned process group.

Archiving and restoring the measured 10M preparation bundle moves 64.64 GB of unique artifacts and takes 566 seconds. A simple tenfold arithmetic projection is about 94 minutes for that stage alone. Summing tenfold data stages with model fitting once gives approximately 204 minutes for fresh ingestion, routing, audits and the 200-query reference gate, before archive and restore. Adding archive/restore gives approximately 299 minutes. Bootstrap and preservation reserve bring the planning allowance above five hours. This is a screening estimate, not a throughput guarantee; a four-hour node does not fit it without measured improvements.

Use a six-hour absolute instance deadline, with the final 30 minutes reserved for failure-proof preservation and terminal reconciliation. The preparation runner gets at most 19,800 seconds from the node's original start time, including bootstrap and metadata planning. Recompute remaining time after every stage. Stop starting new work when a conservative projection of all unfinished stages plus the reserve does not fit. A timeout preserves an incomplete attempt and never emits a passed handoff. A future four-hour option requires measured archive parallelism or demonstrated preparation improvements first.

The first 100M reference gate remains the same 200 preserved queries plus three independent complete-corpus checks. Recompute over all 100M rows; do not concatenate 10M answers. An 11k-query publication reference set is a separate compute job and budget. It cannot silently consume the six-hour preparation allowance.

## Node and compute budget

The default candidate is one dedicated `i4i.4xlarge` in the sandbox account and region already used for the preparation pilot. It has 16 logical CPUs, 128 GiB RAM and one 3,750 GB local NVMe device. It repeats the measured machine class and leaves substantial disk headroom for two complete data copies plus a bounded failed attempt. The alternative `i4i.8xlarge` has 32 logical CPUs, 256 GiB RAM and two 3,750 GB NVMe devices; its extra resources do not prove that a two-file path or serial UUID coordinator becomes faster. Require a measured reason before choosing it. [AWS instance specifications](https://docs.aws.amazon.com/ec2/latest/instancetypes/so.html)

The preserved AWS Price List receipt prices the default Linux shared-tenancy instance at $1.373 per hour, effective October 1, 2026. Six hours is a compute ceiling of $8.238 at that receipt's rate. A 40 GiB root volume at the preserved $0.08/GiB-month rate adds about $0.026 for six hours using 730 hours/month. Refresh the official account/region price before admission and record the actual instance ID, specification and absolute stop. Object storage, requests and retained root-volume time are additional budget items (`fleet/prep10m/compute-official-pricing.json`, `root-gp3-official-pricing.json`).

The node uses only its declared sandbox role, private artifact bucket and benchmark security group. Verify account, region, instance identity and role before work. Root storage holds only bootstrap and small preservation proofs. Source chunks, temporary files, package cache, model, owner outputs, reference workspace, archive staging and restored copies belong on the owned NVMe roots. No production resource is part of this plan.

## Storage and memory admission

The source vectors require exactly 307,200,000,000 bytes at 100M × 768 × float32. Owner-routed vectors require another 307.2 GB if retained separately. Explicit ID maps require 800 MB. Linear arithmetic from the 10M ingestion bundle is about 336.3 GB, including UUID records and the reconstructible database; actual UUID lengths and database shape determine the result. A complete restored preparation bundle is approximately 646.4 GB by the observed tenfold bundle arithmetic. One retained failed full vector output adds up to another 307.2 GB. These components already approach 1.60 TB before temporary database/journal files, package caches and metadata.

Set a 2 TiB owned logical-byte cap with a 256 GiB stop margin, so the guard aborts at 1.75 TiB. Set a 512 GiB filesystem free-space floor with a 128 GiB stop margin, so the guard aborts at 640 GiB available. Set aggregate owned-process RSS to 32 GiB with a 4 GiB margin, so it aborts at 28 GiB. Sample once per second. These are proposed concrete limits, not a capacity proof: the final metadata plan, actual free space, maximum owner sizes and attempted-output retention must fit them. Repeated failures may exhaust the scope budget and must fail closed rather than delete old attempts automatically.

Declare one parent attempt root containing all ingestion attempts, UUID partial databases, model/sample outputs, routed owner files, audits/references, logs/control/lease files, package caches, archive staging and full restore output. Include any reused immutable input root separately; it still consumes filesystem space. Record logical bytes, inode-deduplicated logical bytes, allocated bytes and filesystem free space separately. Sparse files do not make the logical cap smaller. Reflink-shared extents can make allocated sums conservative. No hidden scratch directory or root-volume vector copy is allowed.

The index footprint is a separate later admission decision. The actual 10M periodic-checkpoint stores contain 33.612 GB of current objects and 44.397 GB of physical objects, a 1.320883 ratio. Objects not referenced by enumerated public manifests occupy 10.785 GB. These figures demonstrate private-checkpoint amplification and do not justify deleting those objects. A future 100M index plan must account for taller trees, maximum owner load, periodic checkpoint count, logs and retained generations; this preparation cap does not include index construction (`pilot/results/fineweb10m-storage-independent-review.json`).

## Source and metadata preflight

Freeze the same publisher revision and canonical lexical source order before planning the 100M prefix. The 10M metadata cap of 32 files is insufficient as a default for the next size. Run a separate metadata-only plan with at most 512 files, a 128 MiB charged metadata-request budget and a five-minute deadline. Fail closed if those bounds do not reach exactly 100M rows. Preserve actual per-file row counts, schema, footer/range hashes, source identities, selected column sizes and the truncated final-file interval. Change the bounds only through a new recorded plan; never guess row offsets from average rows/file.

The actual bounded footer preflight passes in 56.255 seconds. It selects 101 files and exactly 100M rows while requesting 6,619,136 metadata bytes. Selected dense/UUID columns project to 148,001,848,798 compressed bytes; the complete Parquet files total 461,577,865,542 bytes and are not fetched by this preflight. The last selected file contributes 1,078,232 of its 1,110,470 rows. Evidence is `100m-footer-v1.json`, SHA-256 `ad8ba10dfa007db63f06f415de649c55d929a4f4e54a0ef06a3d25f9b2cb1357`.

Derive the dense-column request projection from that plan. Proposed full-ingestion charged request cap is 384 GiB with at most one file retry. Every requested byte, including failed requests and metadata requests, remains charged before dispatch. Admit only if twice the projected requested data plus five percent request amplification and the metadata allowance fits the cap; otherwise revise the resource plan before downloading. Keep the verified 2-file concurrency, 2,048-row decode batches and 100,000-row output chunks initially. A requested-byte cap does not cap raw publisher file sizes because only selected column ranges are fetched.

Two-file concurrency and a serial global UUID audit remain the measured code shape. Add timers around source request waits, Parquet decode, primitive conversion, UUID JSON serialization, vector writes, chunk hashing, UUID JSON parsing, SQLite inserts/commits, final database hashing and receipt publication. Measure process-group CPU/RSS, disk reads/writes and requested bytes with complete sample windows. Do not replace SQLite based on the metadata-only fixture. Compare any alternative using real UUID metadata and equivalent lookup/output requirements in a separate bounded epoch.

## Archive, large objects and restoration

Version-pin every unique artifact and verify its size and SHA-256 on complete restore. The current artifact-store implementation switches to multipart transport above 64 MiB, uses full-object CRC32 for multipart server validation and retains local SHA-256 as content identity. A projected 5.2 GB largest owner vector file therefore uses multipart transport; it is not a single-PUT blocker. Preserve the exact deployed source and test epoch. Before 100M, run a bounded actual large-object upload/restore proof with a file exceeding 5 GB, interruption/abort evidence, version pinning and complete restored SHA. Do not copy that fixture onto the Mac.

A multipart upload permits at most 10,000 parts, with part sizes between 5 MiB and 5 GiB except the final part. Preflight the maximum file size and part count; a fixed 64 MiB configuration must reject a file needing more than 10,000 parts or explicitly choose a larger bounded part size. Bound aggregate in-flight parts across archive workers, and include their buffers and failed multipart retention in resource accounting. The existing serial archive path remains the baseline until a bounded parallel implementation passes checksum, failure and restore tests. [AWS multipart limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html)

Archive and full restore are completion gates, not optional work after the node deadline. Preserve the small catalog, source/runtime hashes, complete receipts, failed-attempt journals and version-bound object descriptors independently of the large artifacts. If the remaining deadline cannot accommodate full restoration, retain a failed/incomplete attempt; never claim a restorable handoff from upload-only evidence.

## Launch checklist

1. Complete the matched 10M publication/read-capacity decision and preserve the independent recovery and physical-store review.
2. Freeze a separately instrumented exporter epoch with tests preserving source order, exact UUID equality and verified retry behavior. Coordinate file ownership before editing the existing exporter.
3. Run and admit the bounded metadata plan, including maximum owner/input sizes, request projection, expected archive size and maximum multipart count.
4. Install the independent six-hour node stop before bulk work. Verify concrete source hashes, role/account, scopes, filesystem headroom and aggregate-process cleanup tests.
5. Execute fresh ingestion, whole-prefix model/routing, full ID/value audits, 200-query references and three independent full-corpus checks. Keep every stage outcome and actual resource measurement.
6. Complete version-pinned archive and full restore within the original deadline. Publish a handoff only when every required stage reports passed. Use the measured 100M outcome to decide a separate multi-node 1B plan.
