# Exact references at larger scale

Each corpus prefix needs an independent full-prefix exact reference. The existing CPU producer scores float32 source and query values with float64 accumulation, then orders by distance and global ID. Its chunked interface merges each chunk's exact top-k without copying the complete corpus into another file. This is mathematically equivalent to scoring the contiguous prefix, including ties, and has a tiny chunk-versus-dense parity test.

The next measured run uses the existing disjoint 100 calibration and 100 test embeddings over one million preserved FineWeb vectors. Record wall time, CPU time, resident memory, source bytes, BLAS thread count, output hashes, and errors. These measurements determine whether the larger frozen query pools are affordable on CPU. They do not justify a linear runtime promise at 100M or 1B.

A separate future study freezes 1,000 calibration and 10,000 test query identities before tuning. These pools exclude every current pilot query. Pinned text, model, tokenizer, remote implementation, runtime, batch size, and generated embeddings remain distinct provenance artifacts. Freezing texts does not imply embedding or exact-reference generation has completed.

An accelerated reference engine must scan every vector in the measured prefix and keep exact candidate selection across all blocks and devices. Partition by immutable global-ID ranges, compute block-local top-k, and merge by distance then global ID. Never filter published full-corpus answers into a subset reference. Failed partitions invalidate the output; an atomic completion manifest must bind all input and output hashes.

Numerical conformance is an explicit gate. Start with float32 input values, disable TensorFloat32 and mixed-precision matrix multiplication, and record the actual device and numerical runtime settings. Compare the engine against float64 blocked CPU output over a moderate complete subset, including duplicate vectors, equal scores, near ties, nonunit source norms, and signed values. Compare IDs, score errors, and ordering at the kth boundary. Float32 scoring alone must not be labelled equivalent to the float64 oracle when close scores reorder results. Either use float64 scoring or implement a proven conservative score-error bound that includes every potentially competitive candidate, then rerank those candidates in float64. A fixed oversampling factor is not a proof of exactness.

Measure throughput, memory, disk reads, and transfer cost before choosing sandbox GPU resources. The initial candidate is a bounded sandbox GPU evaluation after the one-million-vector CPU profile and numerical design review. No GPU is provisioned by this document. At 100M/1B, retain complete partition coverage receipts and record whether references meet float64 exact ordering or a separately named approximate numerical convention.

The measured 1M CPU run completes 100 calibration queries in 9.241 seconds and 100 test queries in 9.235 seconds with eight BLAS threads. A separate full-prefix float64 elementwise-reduction scorer checks three complete top-100 results in 7.932 seconds; all IDs match, with maximum distance difference 1.11e-16. The preparation plus both references uses 369.54 seconds overall, 491.64 process CPU seconds and peak resident memory 741,804 KiB. The independent validation process separately peaks at 1,566,540 KiB. These are measured results for the 200-query integration pool, not the frozen 11,000-query publication pool.

A conservative interval helper is implemented for CPU conformance experiments. Under IEEE float32 multiply/accumulate without underflow, overflow, TensorFloat32 or lower precision, it bounds dot-product error using gamma(2d) times the query/vector norm product, includes distance-subtraction rounding, and retains every candidate whose lower distance bound is at most the global kth upper bound. All boundary ties survive; a float64 rerank then orders by distance and global ID. Three tests cover nonunit values, close scores, duplicate-vector ties and invalid inputs. This helper does not implement GPU execution, certify a particular accelerator runtime, or promise a small retained-candidate fraction. A real moderate-prefix retention measurement and independent runtime conformance remain required before provisioning an accelerated reference run.

Independent numerical review identifies and closes concrete input gaps in the helper. It now rejects mismatched score counts, fractional or negative global IDs, nonzero subnormal source/query values, nonfinite computed bounds, and norm products that cannot conservatively exclude FP32 overflow. Dimension-scaled float64 norm inflation and outward rounding protect the interval calculation. The future engine must apply these gates before each kernel and reject nonfinite kernel results. Passing random tests does not certify a GPU arithmetic implementation.

The proposed accelerated prototype streams a bounded vector block and query block into one GPU, computes ordinary FP32 scores with TensorFloat32 and autocast disabled, and keeps the smallest global kth upper-distance bound seen so far. For each block, every lower bound at or below that threshold is retained for float64 reranking and a global distance/ID merge. The threshold only decreases as more corpus blocks arrive, so retaining extra earlier candidates is safe. Candidate counts, rerank time and retained bytes must be measured; duplicate or near-tied corpora can make retention large. A two-pass scan with a fixed final threshold is a simpler fallback if streaming candidate handling is difficult. Neither path may silently cap retained candidates.

A bounded sandbox prototype can use one g5.2xlarge or g6.2xlarge, subject to live regional availability and price checks. AWS lists each with eight virtual CPUs, 32 GiB host memory, one 24 GB GPU and 450 GB local NVMe storage. This fits the 1M reference validation, not a demonstrated 100M/1B pipeline. For a 100M corpus, 307.2 GB of vectors already consumes most of that scratch disk; use separately budgeted storage with measured headroom, and avoid retaining a second complete corpus copy. Current specifications are documented by [AWS accelerated instance specifications](https://docs.aws.amazon.com/ec2/latest/instancetypes/ac.html) and [AWS accelerated instances](https://aws.amazon.com/ec2/instance-types/accelerated-computing/).

Pin the machine image ID, NVIDIA driver, CUDA runtime, Python interpreter, package versions and hashes, source revision, and all model/query artifacts before execution. A candidate runtime is Python 3.12 with PyTorch 2.5.1 plus the CUDA 12.4 build; resolve and preserve actual wheel hashes and compatible driver details before launching it. Disable both matrix and convolution TensorFloat32, disable autocast, use highest float32 matmul precision, preserve the cuBLAS workspace configuration, and record every effective setting. Record CUDA-synchronized kernel time separately from full transfer, CPU rerank and end-to-end wall time.

The first resource gate is capped at 30 minutes of one sandbox GPU, at most 10 GB input transfer and 50 GB scratch, using the existing 1M corpus and frozen integration queries. Read the actual on-demand hourly rate before provisioning; the compute ceiling is half that hourly rate plus declared storage and transfer. Start with 200 queries, compare complete IDs and distances against the preserved float64 references, then use a larger frozen query sample only after embedding and numerical conformance pass. Measure throughput at several query-block sizes, maximum candidate retention, CPU rerank share and warm versus first-pass I/O. Provisioning remains deferred until the ingestion/capacity and numerical gates complete. No GPU measurement or price is claimed here.

## Completed bounded GPU measurement

The verified NVIDIA L4 pilot passes all 200 existing 1M-reference results. Both outputs have SHA-256 `4e12a502bccceed7a573c603f4a3b541c9929e7d81dfa6f4bf3ccfadfca37dcc`; maximum float64 rerank distance difference is 2.22e-16. Three complete check queries validate 3,000,000 score-error bounds, including rows outside the final answer, and four adversarial arithmetic cases pass. Candidate retention ranges from 357 to 450 per query, without a cap. The runtime disables TensorFloat32 and reduced precision and records its exact settings and wheel hashes.

The warm scan takes 12.742 seconds. A separate OS-cache-cleared scan takes 13.786 seconds, including input reads, transfers, score filtering and reranking, but excluding runtime installation, input hashing, initialization, pathology checks and cache clearing. The latter records 0.188 seconds of synchronized scoring, 0.292 seconds of host-to-device transfer, 0.131 seconds of device-to-host transfer and 0.265 seconds of CPU reranking. Its process-accounted disk reads are 3,075,481,600 bytes; raw vector bytes are 3,072,000,000. Clearing OS caches does not control device caches. The preserved archive is `gpu-final-small-evidence.tar.gz`, independently hash-checked against source inputs and both outputs.

The existing CPU reference takes 18.476 seconds for the same 200 queries, but runs on a different host with different precision stages and timing exclusions. These measurements do not establish a general GPU speedup. A direct work-ratio projection of the GPU scan to 100M and 11,000 queries is about 21 hours, and to 1B about 211 hours; these are deliberately crude work projections, not runtime forecasts. They expose the need to measure batching, input rereads and candidate processing separately. The current full-score transfer path would move 4.4 TB of FP32 scores at 100M and 44 TB at 1B for 11,000 queries. The separate device-filter proposal reduces that traffic while retaining certified candidates, but requires a new numerical and performance gate.

The GPU instance is terminated after evidence is checksum-restored from the private archive. No GPU remains allocated for these results. The frozen 11,000-query pool contains text identities only; its embeddings and references are separate outstanding work.
