# Bounded ingestion across source files

The real 1M serial preparation completes in 348.23 seconds and fetches 1,479,720,257 bytes through 191 distinct byte-range requests. No range repeats. The saved requests lack individual durations, so they cannot separate network waiting from decoding and serialization. File timestamps place the final chunk publication about 27.41 seconds before the prepared manifest: approximately 15.64 seconds cover the final UUID audit, sample and model work, and 11.77 seconds cover routing and output hashing. These combined, timestamp-derived boundaries suggest ingestion dominates; they are not a measured HTTP timing breakdown. Subsequent runs record request wall time and explicit ingestion, UUID audit, sample/model, and routing/hash timers.

The parallel ingester assigns one source file to one writer and preserves the canonical source order independently of completion order. It first reads actual parquet metadata, binds the observed row count, schema, object identity and ETag, and computes each file's global-ID offset. It crosschecks the row count and schema again when reading vectors. A pinned dataset revision, declared publisher digest, exact byte ranges and stable ETag bind the source; a projected read does not claim to recompute the whole-file publisher digest.

The coordinator limits concurrent files and speculative metadata reads to a bounded window. Each file writes disjoint chunk paths and a completion receipt. A coordinator lock prevents simultaneous runs from writing the same output. Resume verifies completed file receipts and chunk bytes, while incomplete attempts remain inspectable and are restarted. The implementation retains at most three attempts per file. Transient network errors have bounded retries; row-count, schema, hash, ownership and budget failures stop publication.

All workers share the source-request, output-byte and wall-time limits. Requested payload is charged before issuing a request, including failed requests, so retries cannot evade the source cap. Prepared vector and UUID writes reserve their exact bytes through one lock. The final disk-backed UUID audit has a SQLite page limit; completion also checks total owned output bytes. Small control manifests and receipts are included in the final output check. An external process timeout remains necessary for a hard wall boundary. This is a worker-storage tool, and it retains verified prepared data rather than accumulating a full source cache.

The completed ingest manifest lists chunks in canonical global-ID order, regardless of scheduling. The existing whole-prefix sampler can consume those chunks and produce the same model as serial ingestion. Four tiny tests verify exact values and UUIDs, original global-ID ordering, uniform sample/model equivalence, retained complete-file recovery, duplicate rejection and output-cap failure. Real parallel throughput is still unmeasured.

A genuine multi-file prefix must cross the first source file's 1,090,356 rows. The next bounded validation can therefore use approximately 1.1M rows from the first two pinned files, two concurrent file workers, a 3 GiB requested-payload cap, a 12 GiB output cap, and a 900-second deadline plus hard process timeout. Validate values and UUIDs against the serial first-file prefix where already available, crosscheck actual file row counts, and independently compare the complete global-ID coverage and whole-prefix sample. Schedule it after timed build/read work releases an isolated worker. Do not describe disconnected tiny slices from several source files as a canonical dense corpus prefix.

Before 100M ingestion, measure that multi-file point, disk expansion and index capacity. Use the measured per-file completion times and byte volumes to estimate the longest source job and the bounded parallel task graph. Keep a fixed concurrency limit, measure aggregate disk and network use, and preserve skew rather than scaling a single serial time by file count. The proposed 100M run remains behind these engineering gates.
