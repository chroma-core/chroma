# Real-data progression after the mechanics gate

The required real-data progression is 1M → 10M → 100M before larger prefixes. The 10M gate uses a representative sample from its entire prefix, 128 frozen logical subtrees, repeated private checkpoints, and measured peak memory and disk use. It must pass complete ID coverage, publication, read consistency, and storage-capacity checks before 100M preparation begins. Each dataset size fits its own model; placement comparisons within that size retain the same model and owner graph.

The next integration point uses the existing million-vector MS MARCO source, then the blog study uses real FineWeb subsets. Sandbox provisioning is authorized. Progression waits on measured correctness, convergence, reference cost, and capacity rather than additional permission.

## Complete the current tree mechanics gate

The two-child 10k input checks explicit IDs, one frozen root, mixed lower-tree heights, publication, and identical local versus HTTP traversal. It is too small to establish capacity, and two ownership slots cannot demonstrate eight-host distribution. Retain its observed 8,593/1,407 ownership skew and the slowest owner's time. Verify exhaustive tiny answers, unique returned global IDs, global beam traces, and append pinning before scaling.

## Integrate one million real vectors

Prepare the existing normalized million-vector MS MARCO source with a fresh frozen construction epoch and at least eight owned subtrees. Start with 16 slots if preparation overhead and smallest-child population permit it. Record the sampled model, complete ownership counts, maps, and hashes. Keep those exact slots and snapshots fixed while placing them on one, two, four, and eight physical workers. A separate experiment can compare 16 with 32 slots; changing slot count is not a host-scaling result.

Serving comparisons reuse the same committed content tree. Full-build comparisons use the same fixed task graph: the same prepared ownership inputs, writer parameters, per-job threads, publication boundary, and reopen checks. Run the jobs sequentially on one worker and concurrently across more workers with a declared per-host thread limit. Full-build elapsed time follows the last required owner and publication; CPU seconds and bytes sum across owners. Rebuilding with a different partition count changes the task graph and does not demonstrate speedup of the same work.

The million-vector source is already prepared and its complete corpus takes 4.096 GB. The independent float64 reference for 100 queries takes approximately 10.5 seconds with eight BLAS threads on the current worker. These measurements support a practical integration-sized run. The independent forest's real build reaches a balance-round limit on one worker, so its elapsed time cannot establish completed balancing or predict shared-tree compaction throughput. Require a clean completion gate and record stragglers rather than projecting that timing.

## Add an exporter that preserves FineWeb values

The existing MS MARCO exporter is unsuitable because it assumes another schema, dimension, and normalization policy. The separate `fineweb_prepare` utility is implemented and its bounded real 100k validation passes independent value/UUID checks. Use it for subsequent prefixes after the shared-tree gate. Its input is the pinned dataset manifest plus a requested prefix length. Its output is row-major float32 vectors and a row-to-document-UUID sidecar with immutable source ordering and hashes. Read `dense_embedding` and `id`; require 768 float16 values and finite entries, convert exactly to float32, and perform no normalization. Choose one-minus-inner-product provisionally, then verify numerical agreement with the publisher's reference conventions before reporting recall.

The exporter should read only the required parquet row groups and columns using bounded batches and a seekable HTTP range reader. Record the pinned file identity, object size, publisher object digest, fetched ranges, and prepared-output hashes. If range access is unavailable, download only the necessary full source files and account for their peak storage explicitly. A publisher digest is not a locally computed whole-file hash; label that distinction. Freeze lexicographic file order and parquet row order, and reject null or malformed rows. Preserve every source UUID exactly while assigning stable integer row IDs for the worker.

The 100k-prefix exporter test compares all converted vectors and UUIDs with an independent Polars decoder and passes a deterministic cache-only retry. Existing or partial output directories are rejected without mutation; resume is unsupported and requires a separate implementation gate before long ingest runs. The required progression is 1M, then 10M, then 100M, followed by the planned 250M, 500M, and 1B gates. The 100k and 1M FineWeb points are exporter/reference checks, not substitutes for the planned scale points.

## Produce separate subset references

Regenerate query embeddings with pinned model, tokenizer, query snapshot, runtime, device, and batch size. Verify query-text hashes and numerical metric parity. Freeze disjoint calibration and test pools. Recompute exact answers over each measured prefix: filtering the publisher's full-corpus top-1000 list cannot recover omitted subset neighbors.

The current blocked CPU reference handles the proposed one-minus-inner-product metric and can score an exported dense prefix in bounded working arrays. Add input hashes and UUID mapping checks to its run manifest. First measure 100 calibration and 100 test queries over the 100k and 1M FineWeb prefixes. Then measure at least 1,000 calibration and 10,000 distinct test queries for publishable curves, or budget a separate reference engine that produces equivalent exact results. Validate any faster CPU/GPU producer against the independent scalar oracle and a moderate blocked run before trusting its output.

A billion-vector corpus and 100,000 queries require 100 trillion vector comparisons. A simple work-proportional estimate from the observed 1M-by-100, 1024-dimensional run to a 768-dimensional run is about 91 days at the same eight-thread allocation. This is a planning warning, not a runtime forecast: matrix shape, numerical engine, bandwidth, and hardware change throughput. A 1B-by-10,000 reference has one tenth that arithmetic work. Full reference generation therefore needs a measured throughput/cost gate and likely separate parallel or accelerated compute before promising the complete matrix.

## Capacity bounds and additional workers

The current workers each provide approximately 3.5 TiB of scratch space and 512 GiB RAM. Raw FineWeb vectors stored as float32 require 307.2 GB at 100M, 768 GB at 250M, 1.536 TB at 500M, and 3.072 TB at 1B, before index blocks or metadata. Retaining both a dense corpus and owner input copies doubles those bytes. At 1B that alone reaches 6.144 TB across the cluster. Two current workers have approximately 7.7 TB of aggregate scratch capacity before existing data, index blocks, temporary writes, and generations; that leaves insufficient demonstrated headroom for a defensible 1B build.

Four workers reduce a perfectly balanced billion-vector raw partition to 768 GB per worker; eight reduce it to 384 GB. These are arithmetic bounds, not measured index footprints. Navigation memory, retained vectors, compaction copies, ownership skew, and storage amplification must come from the shared-tree million-vector profile and the first FineWeb prefix. The 10k root is already skewed by a factor above six between its largest and smallest child, so an equal-share capacity assumption is unsafe. Measure the largest owner and critical path, then use explicit placement to distribute slots; do not silently change the committed ownership boundary to hide skew.

Provision four or eight workers when the fixed-slot placement sweep reaches those points and the measured per-host storage/memory peaks fit with headroom. Preserve separate compute for query regeneration and exact references when it would interfere with timed workers. Source downloads, retained generations, idle provisioning, and reference cost belong in the aggregate budget. Bulk download begins only after the mechanics and exporter gates establish those boundaries.

## Fair utilization before headline scaling

The current 1M timing configuration runs one owner job per host with one balancing thread and two runtime threads on 64-vCPU workers. It checks distributed scheduling and times that setting; it is not a capacity-scaling result. Sweep owner-job concurrency and per-job thread allocation within CPU, RSS, disk, and completed-balancing limits. Freeze the resulting per-host policy for the 1/2/4/8 comparison while retaining the same ownership task graph. The fixed graph must contain enough independent work to exercise the policy; otherwise report the available parallelism limit. Parallel owner jobs on one host may erase apparent two-host gains, and that result belongs in the report.

Queries need their own saturation sweep with a fixed global search budget and explicit recall, latency, and error objectives. Record coordinator limits and actual per-host utilization. A lightly loaded baseline cannot support a capacity headline even when its two-host latency is lower.

The next construction epoch must expose enough independent work for the chosen machines. The measured 1M one-host run with 16 simultaneous owners takes 17.86 seconds, averages 18.2% of 64 virtual CPUs, and peaks at 4.47 GiB of concurrent process resident memory. This result supports testing smaller machines before adding more 64-core machines; it does not establish that larger corpus owners have the same memory demand.

Use 128 fixed logical subtrees as the first candidate for the next 1M-to-100M epoch, with a whole-prefix representative sample of at least 32,768 rows. Compare 8-vCPU and 16-vCPU memory-optimized worker sizes, subject to measured owner memory and available local disk. Eight hosts then have 16 logical jobs each; concurrency and within-owner thread counts must be selected through saturation measurements and held to the same policy across placements. A 512-subtree epoch is a separate candidate if 128 jobs leave the measured cluster idle. Measure centroid scoring, adapter process count, open files, mapping caches, owner imbalance, and per-query round trips before selecting it. Each comparison freezes one tree and its slot count across 1, 2, 4, and 8 placements.

Storage can require larger machines even when CPU measurements favor smaller ones. At 100M vectors, the projected prepared corpus, routed owner copy, UUID records, and maps consume about 644 GB before index files, temporary outputs, and safety headroom. At 1B, the same byte projection is about 6.44 TB before those additions. Size aggregate local disks from actual index expansion and largest-owner measurements; do not infer disk requirements from CPU utilization. No 4-host or 8-host fleet is needed until the next corpus gate establishes these values.

Quality selection must pass on calibration before a publishable capacity curve starts. The current tested grid reaches only 89.08% calibration recall@100 against a 90% target and therefore uses its highest-recall fallback; the 90.01% held-out result does not repair that calibration failure. Expand the search-quality grid or improve the index, freeze a setting that meets calibration quality, and then evaluate untouched test queries. Apply the same rule to the FineWeb gate.

Construction timing measures the initial committed tree. The sparse-append gate establishes atomic publication, unchanged-owner snapshot reuse, global-ID integrity, and old-reader pinning. It does not measure append throughput or distributed compaction scaling. Those require their own fixed workload, convergence checks, resource measurements, and timing experiment.

## Required 10M preparation gate

The next corpus size is a canonical 10M FineWeb prefix, followed by 100M after the 10M checks. A metadata-only preflight reads at most 16 MiB for 120 seconds across at most 32 source files. It checks actual Parquet row counts, projected column sizes and immutable source ordering. Its output determines download and retry budgets; row-proportional guesses do not determine range caps because a short suffix can require a complete compressed row group.

Run the 10M preparation on a dedicated sandbox node and download its pinned public source directly, so preparation does not use the timed workers’ network. The projected compressed columns total 14,800,596,084 bytes across 11 actual Parquet files. A 32 GiB requested-source cap covers one complete retry plus metadata. Verified complete-file reuse remains supported by immutable receipts and actual hashes, but this isolated run has no seed transfer. Partial source files restart under distinct attempt directories; one coordinator owns each output path. Two concurrent source files follow the measured 1.806 elapsed ratio from one paired observation. More concurrency needs a separate measured point.

Fit the 10M epoch from a deterministic sample across its whole prefix, with at least 65,536 sample rows and 128 fixed logical subtrees. Keep the 1M model unchanged for its append study. At 10M, vector chunks plus routed owner input consume about 61.44 GB; UUIDs, maps, SQLite validation, metadata, failed attempts and private checkpoints add storage. This is a byte projection, not measured total disk use. The final ingest cap and storage reserve follow actual metadata and current free-space checks before execution. Preserve periodic private checkpoints and complete ID audits before publishing.

Recompute the existing 200-query integration references against all 10M rows, without filtering smaller or full-10B answers. The larger 11,000-query text pool remains a separate embedding and reference task. The optional GPU filter needs device conformance and all-query reference matching against the tested 1M path before a useful combined 1M/10M bounded GPU slot. No existing GPU remains allocated.

The dedicated preparation job enforces a one-hour ingestion deadline and a two-hour whole-process deadline; model fitting, routing and references have no separate phase deadline. Its resource guard samples every second with explicit margins below 16 GiB aggregate writer RSS, 192 GiB of preparation output and a 512 GiB free-space floor. Index and checkpoint writes have separate later limits. The machine has a fixed three-hour stop deadline. A routing completion record certifies routing only; index admission also requires the final immutable attempt report to pass references and independent checks. All attempts remain preserved, and an atomic pointer identifies the latest report.
