# Storage measurement scope

The diagnostic measures file bytes reachable from the current committed blockfile roots and the union of every retained immutable generation. These are storage objects, not a count of live logical rows: an object can contain stale entries. The diagnostic separately inventories the complete owned checkpoint directory and flags objects outside the enumerated retained roots without claiming that deletion is safe.

The diagnostic compiles with Rust 1.92 and passes four release tests. The tests cover shared objects across retained generations, hard-link accounting, corrupt or absent objects, map identity, immutable head identity, writer exclusion, resource limits, and symlink handling. Data-block payloads are intentionally invalid in the fixture, which confirms that the diagnostic does not decode them. The separate executable SHA-256 is `a6827c10288e54cc994b34d8ff644b1d85b0e3d5f0b9675e7bd3434a443c9174`; the source archive SHA-256 is `34d7ebfdc05b97428e96fd467132ac5c712463690d7862e27caac91c8b4582f2`.

Each internal construction checkpoint balances, commits, flushes, and reopens the writer. Only the final checkpoint receives the complete reachable-ID audit and becomes a published immutable generation. An interrupted invocation resumes from the prior published head and rebuilds the incomplete suffix. Intermediate flushes can therefore increase physical storage without increasing the set of published generations.

All eight preserved one-million-row allocation cases use one final checkpoint per owner. Their measured file ratios cannot establish a repeated-checkpoint storage bound for a ten-million-row run. That gate needs an inventory after several private checkpoints, after final publication, and after a deliberately failed invocation whose old published snapshot remains readable. Staging copies and peak scratch need separate measurements; the object inventory does not measure them.

A capacity gate must use the largest observed owner and actual placement sums. It must reserve space for retained committed generations, unpublished checkpoint objects, staging copies, and peak scratch separately. The current review sets no numeric ten-million-row storage cap because these inventories have not yet been measured. No cleanup is authorized by this diagnostic.

The independent inventory binds all 128 owner reports to the published one-million-row tree. Current, retained-generation union, and total physical data objects each contain 3,351,329,366 logical bytes in 3,047 files. The total owned checkpoint directory files contain 3,359,959,458 logical bytes. There are no unknown paths or objects outside the enumerated retained roots. The measured physical/current ratio is 1.0 for one generation with one flush per owner. The reproducible aggregation and input archive hashes are recorded in `independent-inventory-review.json`.

A 250 GB allowance for ten million rows is an operational stop budget, not a proven storage bound. Before admitting that run, compute each owner checkpoint count as the ceiling of its appended rows divided by its checkpoint interval, using the actual largest owner and placement sums. Count original snapshots, arm clones, prepared input/map copies, and every retained generation separately. The current measurements establish neither an upper bound for new block bytes per checkpoint nor the effect of increased tree height. Measure a periodic-checkpoint case and enforce a free-space stop margin before treating any numeric allowance as adequate.
