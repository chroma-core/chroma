# Connect restoration, binding, matched work and bounded evidence retrieval

A single work process restores the admitted input, binds the verified result into existing stage specifications, runs the matched experiment, and collects evidence on return. It never creates approval, starts or stops a machine, installs a watchdog, or extends a deadline. All actual resource and execution admission remains external.

## The pieces

- The external admission pins the exact code, base template, query cohort, configuration, build provenance, restore plan and resource evidence (`orchestration-admission.template.json`). Its null values deliberately make the template nonexecutable.
- The workflow worker calls the existing materializer, binder, matched driver and collector in that order (`orchestrate-restored.py`). The existing files remain unchanged; the new worker replaces the old wrapper as the complete entry point rather than running restore twice through nested wrappers.
- The metadata helper verifies descriptors and the existing reviewed implementation verifier before restoration (`orchestration_contract.py`). It copies only the exact build-source manifest, accepted restore plan and materializer source into the evidence closure; it never copies a compiler, native binary, corpus or saved index into that closure.
- The retrieval worker validates an exact-file byte stream supplied by the parent's authenticated transport (`retrieve-evidence.py`). It opens no connection and starts no transfer process. The inner evidence archive stays opaque and is never extracted by this worker.

## The work flow

1. **Require an externally approved envelope.** Invoke `python orchestrate-restored.py --spec FILLED-SPEC.json` only in a separately admitted task. The spec pins an external admission whose decision and epoch match this experiment. All required descriptors must exist and hash correctly. The admission pins the existing setup, runner, implementation and build-provenance closures; the reviewed implementation verifier checks those before restore. The production entry point fixes the two-million-row, 768-dimensional IP cohort and its source identity. The tiny test override exists only as a core-function argument and has no CLI flag.
2. **Check the resource and query evidence.** The admission supplies exact resource approval, start-attempt, matching watchdog READY, mount verification, normalized remote guard and raw guard receipts. The worker checks account, instance/type, dedicated volume identity/size/encryption, mount capacity, timer identity and matching absolute stop. These are checks on pinned evidence, not new live AWS/systemd observations or proof that an arbitrary JSON file is genuine approval. The parent must obtain and independently admit the actual evidence. The frozen query file's hash and ordered sixteen IDs must match both the matched-input record and the admission. Both construction modes require explicit FP navigation and FP NPA.
3. **Restore and bind the successful result.** Restore uses the existing exact spec and work deadline. A nonzero restore exit skips binding and matched work. On success the worker hashes the actual receipt and runtime-provenance paths under `EXPERIMENT/restore`, then invokes the existing binder. It verifies exactly the three generated bound files, the canonical extent/path, cohort/configuration, owner and structural settings, query binding and budgets. It writes `orchestration/generated-base.json` by filling only the externally authorized `bound_inputs` field; every other base field is preserved. No generated document changes its status to approved.
4. **Run matched work and collect on return.** The existing matched driver receives that generated base. Restore, binder, matched-driver and collection stdout/stderr are captured separately. A work exception or nonzero exit still leads to `pre-collection.json` and the existing metadata-only collector while time remains. Successful work requires the matched-complete receipt and all mandatory scientific/resource metadata in the archive. Failure archives can intentionally list missing future-stage files. The final result and outside collector receipt remain separate because the archive precedes its own completion. A collection failure still produces terminal sidecars for retrieval; an unverified partial archive is not advertised as eligible.

The work deadline is identical in the base, admission and restore spec. Collection must have at least 120 seconds beyond work, and at least 60 seconds must remain before the fixed stop. Each subprocess timeout uses the remaining absolute interval. The worker neither resets the interval nor restarts a failed stage. Killing a direct child does not prove detached descendants terminate; existing stage supervision and the separately verified machine stop remain required. Forced process death can interrupt final receipt creation. A missing or invalid admission runs no child and therefore cannot invoke an unadmitted collector as a fallback.

## Exact metadata and resource interfaces

The admission contains `artifacts`, `evidence`, `budgets`, `expected`, `generated_fields`, `retrieval_limits`, `experiment_root` and `machine_stop_unix`. The template lists every required key and descriptor. The base template has `bound_inputs: null`, the exact runner/implementation/build bindings, and `integration_output: EXPERIMENT/integration`. Only the value of `bound_inputs` can be filled after the binder emits its manifest. The restore spec has `attempt_dir: EXPERIMENT/restore` and the same work deadline/disk reserve. The orchestration output is exactly `EXPERIMENT/orchestration` and must be new.

The resource approval must provide `decision: approved`, matching `epoch`, `account`, `instance_id`, `instance_type`, `volume_id`, `required_free_bytes` and `machine_stop_unix`. The start-attempt and watchdog READY receipts retain their existing lifecycle schema. Mount verification retains the existing verifier's `volume_id`, `mount` and `free_bytes`. The normalized remote guard record contains `active: true`, `timer`, `deadline_unix`, `instance_id` and `raw`, where `raw` is the exact raw-guard descriptor also supplied by the admission. Use a collector-approved `.log` or `.json` filename for that raw record. This package does not produce or normalize actual guard evidence for the parent.

The collection spec must include the admission/base/restore/config/query/implementation/resource proofs, all 21 per-object restore proofs, generated binding/base/phase records, all scientific stage outputs, both original saved manifests, and the exact prepared reference JSONL. The new worker checks this closure before restore. It also includes `orchestration/closure/{build-source-artifacts.json,restore-plan.json,restore-materializer.py,copies.json}` so original externally located metadata remains available without rewriting its contents. The existing collector still imposes its 8 MiB per-file and 64 MiB payload cap, explicit safe paths, and two exact store-manifest/reference exceptions. Raw maps and index objects stay on the retained volume.

## Bounded retrieval interface

The worker emits `orchestration/retrieval-manifest.json` and prints its exact descriptor with the terminal result. First obtain only that small descriptor-pinned manifest through an already admitted authenticated metadata channel; its fixed six-record shape fits a 64 KiB metadata request. Keep the original external admission locally as `admission_copy` with identical bytes/hash. Neither receipt grants transport authority.

The parent's transport then streams only the manifest's listed flat regular files as an uncompressed USTAR stream into `python retrieve-evidence.py --spec FILLED-RETRIEVAL.json`. The maximum six names are `evidence.tar`, `evidence.tar.receipt.json`, `result.json`, `pre-collection.json`, `collection.stdout`, and `collection.stderr`. Failure can omit the archive pair. Do not recurse over a directory or request a store/canonical/map file. The stream parser rejects unknown/duplicate/missing names, links, directories, prefixes, PAX headers, wrong sizes/hashes, nonzero trailing bytes and excess actual wire bytes before publishing the verified local files. No inner-archive path is extracted.

All three retrieval limits must be supplied externally. Hard implementation maxima are 72 MiB total wire, 68 MiB archive and 1 MiB per sidecar; these are rejection ceilings, not granted allowances. The admitted wire limit must cover the declared archive plus five sidecar maxima and 32 KiB for framing, and the sidecar limit must be at least 64 KiB. Thus the parent must choose coherent values within its actual approved budget. A file above its admitted cap remains remote and is explicitly omitted rather than silently downloaded. A valid archive/receipt pair is retained even when work fails. The outside receipt's archive hash and extent are verified during retrieval. The client validates a locally retained copy of the same external admission and never creates approval.

The retrieval deadline is fixed and no later than the admitted machine stop. The client checks before and after bounded reads but cannot interrupt a blocked stdin transport read itself. The parent must enforce the authenticated channel's absolute timeout and retain its terminal status. Actual transfer bandwidth and completion within the reserved interval are not measured by the tiny tests. There is no SSH/S3 transport, cloud action, watchdog, or automatic retry in these new files.

## Local evidence and non-executable prerequisites

The completed source has six tests across orchestration and retrieval. Local subprocess integration uses fake restore/binder/driver programs with a tiny three-row contract, the actual existing implementation verifier and collector, and the actual new retrieval CLI. It covers success, restore exit 9, driver exit 7, bad generated configuration, collection exit 5, missing admission, mismatched guard, changed query order and incomplete metadata closure. Retrieval tests reject ten malformed/oversized streams plus expired or changed admission/limits. The initial fixture-only `/var` versus `/private/var` path failure remains preserved; it starts no work phase. Retained fixture copies are marked FAKE and contain no real corpus or resource approval.

Actual resource approval and evidence, a filled admitted base/spec and complete remote source/runtime environment, the real restore, matched computation, Linux execution of this orchestration, authenticated transfer channel, transfer timing and final stopped-state collection remain unexecuted. The existing whole-tree diagnostic cap of 4,096 report leaves still applies regardless of actor count. A successful fake workflow is not a two-million-row quality, latency, memory, resource-admission or execution claim. All old windows remain closed. Parent-owned lifecycle, runner, collector, binder, Rust implementation, state, journal and staged index remain unchanged.

Successful collection requires the preparation supervision receipts and the construction and diagnosis per-arm process receipts. Construction and diagnosis execute directly through the stage runner and do not create outer supervision directories. The local fake driver enumerates this accepted output layout independently of the orchestrator requirements; its successful test explicitly asserts that those two outer directories are absent.
