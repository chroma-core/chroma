# Epoch10 corrected-runtime CPU observation

This preparation runs one explicit `100k-profile` arm against the exact corrected epoch9 binary and observes owner1's first balance. It uses the same retained 100K vectors, 32 workers, thresholds and 80K capacity as the before/after workload. It starts no build, larger run, sweep or automatic retry. The previous timing difference does not establish a causal speedup because logical work differs.

The new spec generator is `make-owner-local-spec-epoch10.py`, and the runner is `run-one-arm-epoch10.py`. They reuse unchanged generic `remote-job.py` and the existing lifecycle. The workload remains bounded to 600 seconds and a fixed absolute job deadline 590 seconds after preparation, with 660 seconds required in a fresh independently guarded epoch10 host window. Specs, outputs, run IDs and receipts use epoch10. Binaries and hash bindings come from `runtime-binaries-epoch9.json`; the collector additionally requires the known performance binary SHA256 `57f6baa4b09749dfede42247a3bf728748151c2df1a3b9ae5754877541f27de1` at `/home/ubuntu/spann-two-machine-v1/epoch9/build/two_machine_spann`. Input and token paths remain retained references, with no copies of corpus or credentials.

The runner prepares both owner specs, starts the idle peer, then starts `remote-profile-epoch10.py` before the owner1 workload. The collector checks installed perf/timeout paths, perf version and help support for PID selection, frequency/event, clock, frame-pointer stacks and thread inheritance. It refuses unprivileged sampling when `perf_event_paranoid` exceeds 2. It changes no permissions, sysctl or dependencies and invokes no sudo. The runner requires an atomic matching ready receipt before launching owner1. Preflight support is not proof that the later attachment succeeds: permission/kernel/tool failure retains a failed result and never triggers a retry.

The collector binds the reviewed spec hash and its own source hash, the fixed workload, and the supervisor's actual `running.json`. Before attaching it verifies PID, process-group ID, start ticks, boot ID, instance/job identity, exact `/proc/PID/exe`, binary hash and the inherited owned-job marker. It waits for the flushed first `balance_started` event with 100K rows. It never selects a process by name or samples system-wide. Partial trailing JSONL writes are ignored until complete.

Sampling uses 99 Hz userspace `cpu-clock:u`, `CLOCK_REALTIME` and frame-pointer stacks with process threads selected by `--pid`. The normal recording ends with SIGINT after nine seconds; a one-second forced-kill grace makes the recording's hard bound ten seconds. An observed balance completion, process exit, profile-byte cap or earlier absolute deadline stops it sooner. The recording has a 256 MiB hard file-size limit. The separate collector has a 115-second internal deadline including report generation, capped by the job, actual supervisor and host deadlines, and an outer timeout at 118 seconds plus two seconds forced termination. It does not extend or signal the workload. It only signals a separately created profiler group whose members carry the exact collector marker; cleanup verifies that no collector-group members survive.

`perf.data` remains remote. A bounded `perf report --stdio --no-children` produces at most 1 MiB of small text. The runner collects that text and small JSON/stderr receipts, then validates the collector result. A completed workload with a failed profile remains a profiling failure. Ordinary peer/process cleanup stays in the existing runner's finally path. The collector's independent timeout remains active even if the runner loses contact.

The result records realtime and monotonic event-observation and collection boundaries, exact attachment identity/argv, stop reason, file size, tool evidence, exit status and cleanup confirmation. Only the recorded interval is attributed. The leading and trailing balance intervals may be uncovered, and polling or event publication may overlap another phase. The runtime's original elapsed timer remains authoritative for total balance time. CPU samples do not measure blocked time; overlapping inclusive stack percentages must not be added. No claim of entire-phase coverage or causal performance improvement follows from this one observation.

The root operator must review the coherent scripts, freshly verify profiler availability/permissions and both instance identities, and install both shutdown guards before any upload or execution. If current permissions block sampling, stop at preflight. A separately reviewed bounded privileged sampler could be proposed later; this preparation neither enables one nor changes kernel permissions. The only runner arm is `python3 operations/run-one-arm-epoch10.py 100k-profile`, which is an operational command requiring root admission rather than authorization supplied by this note.
