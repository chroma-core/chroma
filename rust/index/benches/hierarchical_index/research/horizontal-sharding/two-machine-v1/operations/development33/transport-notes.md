# Connection reuse and bounded transport workers

The transport reuses successful connections and runs request processing on fixed worker pools. Each call exclusively borrows one cached socket, sends one authenticated framed request and reads one framed reply before returning that socket. Cloned clients share the cache, while data and control connections stay separate. The client caches at most the configured handler count per class and discards sockets after half the ordinary operation timeout. It probes a cached socket before sending and reconnects only when that probe shows the socket is closed or unusable. A write or reply failure returns an error without replaying the request, because a mutation may already have applied.

Each listener has a readiness reactor that accepts connections and assembles bounded frames with nonblocking reads. Idle sockets and partial requests consume bounded socket capacity rather than execution workers. Each pass accepts at most 32 sockets and reads at most eight chunks of 16 KiB per pending socket. Request deadlines begin with the first request byte; idle connection expiry has its own start time. Completed frames go to a bounded decoder stage with at most eight workers per listener. Decoders authenticate and decode once, release the raw frame buffer, and return typed requests without waiting for execution capacity. The reactor performs no JSON decoding.

Data requests use three independent execution lanes. Primary work includes construction jobs and handoff coordination. A second lane handles structure edits, centroid publication and owner export. A third lane handles destination chunks. This allows a primary handler to wait for an export while that export waits for a chunk without consuming the dependent execution capacity. Control calls have a separate execution pool. A reciprocal two-server test fills both primary lanes, sends export requests back across the connection and sends chunk requests back again; both chains finish successfully with one worker per lane.

The server preserves explicit overload failure: it closes a received request when the applicable execution lane or decoder queue is full. It never blocks a decoder or reactor waiting for handler capacity. It does not promise that arbitrary recursively saturated control handlers succeed. Existing engine deadlines still bound synchronous computation and dependency waits. The actual benchmark has 32 balancing workers per owner, 64 workers in each data lane and 128 control workers. Placement runs after construction drains. The fixed pools also include eight data and eight control decoder workers, so each benchmark server spawns 336 processing threads once, plus its two reactors. This is a fixed upper bound rather than a new thread for each request; idle execution workers sleep while waiting for requests.

Accepted sockets are bounded by twice the sum of execution lane capacities: 384 data sockets and 256 control sockets in the benchmark configuration. This bound includes partial frames, decoder inputs, decoded outputs and executing requests. Decoder completion queues use channels without explicit queue lengths, but every element remains charged to this admission bound. Individual encoded frames retain the configured byte limit. Multiple clients or malformed peers can exhaust admission and cause explicit failure; the transport does not provide denial-of-service isolation for an untrusted network. Authentication and encryption remain the fixture's existing shared-token and private-network model.

Shutdown stops admission, drops idle and partial sockets, joins bounded decoders, closes handler queues and joins admitted mutations. Worker completion notifications use nonblocking wake sockets so shutdown cannot hang on a full wake buffer. Readiness notification remains the default listener mode; the polling option remains available for existing comparisons.

Lightweight counters expose client connections opened and reused, server connections accepted and fixed processing workers spawned. The serializable capacity helper reports execution lane sizes, decoder sizes, socket bounds and frame bounds. Detailed request counters still attribute wire bytes and codec/handler scopes after each completed request, rather than waiting for a persistent connection to close. The existing thread-start-wait scope now measures execution queue dispatch delay; the thread-spawn scope is no longer a per-request measurement.

Validation covers connection and worker reuse, idle sockets not consuming execution slots, bounded socket admission, control progress while data is saturated, reciprocal nested export/chunk callbacks, malformed and fragmented frames, absolute deadlines, shutdown, stale cached sockets and lost replies without mutation replay. The final additional test checks that an idle connection does not consume the next request's budget and that 200 concurrent distinct replies remain isolated. Ordinary and detailed test logs are retained beside this note. Parent validation covers the combined native suite, native construction smoke and the cloud construction smoke; no separate repeated transport performance study is required.
