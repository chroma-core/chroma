# Construction failure after balancing

The retained `33-nav-on-3` run completes balancing and then exits before the cycle-complete event with `transport frame exceeds configured limit`. The preceding event successfully collects both owners' counts. The next operations collect placement statistics and redistribute ownership. The error can originate from a request whose JSON encoding exceeds the frame bound, or from a received reply prefix that advertises an oversized frame. The original error text does not distinguish these cases.

The diagnostic source at `/private/tmp/spann-research33fix` preserves the frozen source33 implementation and its 16,777,216-byte frame bound. It adds bounded stderr diagnostics that distinguish request encoding from reply-prefix rejection and identify the request kind. Placement export, chunk and shared-view installation receive separate labels. The diagnostics contain no token or payload. No functional change or larger frame bound is introduced.

A focused persistent-connection test verifies that an oversized outgoing request sends no partial frame and does not dispatch. A later valid request reconnects and succeeds. This excludes the simple claim that a local serialization-size failure inherently poisons the cached connection. It does not prove that all possible framing failures are absent. The test passes; its output is retained in `transport-size-regression.log`.

A second test constructs a complete shared routing view with 32 internal branches and 2,131 ownership leaves, matching the scale of the failed run, and 768-dimensional centroids. Every centroid component is the exactly representable value `-0.123046875f32`. Its actual `Placement.InstallView` envelope encodes to 22,550,510 JSON bytes, exceeding the unchanged 16,777,216-byte transport frame bound. The real client rejects it before the handler runs and emits the diagnostic `stage=request_encode kind=Placement.InstallView`. The test passes; its output is retained in `transport-shared-view-bound.log`.

This establishes a concrete size limitation in monolithic shared-view installation. It does not yet establish that this is the cause of the retained cloud failure: the synthetic centroids are not the failed run's exact values, and the failed run's final shared view is not retained. The diagnostic cloud run must identify the actual failing request before selecting a functional fix. A larger frame cap is not applied. The handoff chunk path also uses a binary-size bound with JSON transport encoding; no test or retained evidence currently identifies that path as the actual failure.
