# Navigation work and completion-time investigation

The selected candidate caches the most recent parent lookup while processing consecutive child rows. It removes repeated hashing during reply validation and canonical candidate ordering while preserving all per-child checks and the exact reference sort input. The candidate is implemented in `rust/index/benches/hierarchical_index/distributed/routing.rs`; `SPANN_NAVIGATION_PARENT_CACHE=0` selects the retained per-row lookup control in the same executable. The switch is read once per process, outside the row loops; the default enables the candidate.

## Evidence for the candidate

The coordinated epoch32 detailed run records 288.675 CPU-seconds inside navigation, including 70.778 CPU-seconds in reply validation and 39.015 CPU-seconds in canonical ordering. These are inclusive scopes, so they must not be summed as exclusive costs. Both loops look up each child's 128-bit parent identifier in a hash map. The owner expansion implementation emits all children of one parent consecutively before advancing to the next parent. This grouping follows directly from the emitting loop; the retained counters do not measure the frequency of grouped parent runs in the production workload.

The phase-filtered CPU profiles support investigating hashing. On owner 1, `DefaultHasher::write` accounts for 6.45% of samples and `BuildHasher::hash_one` for 2.71%; on owner 2, the corresponding shares are 6.29% and 2.70%. Owner 1's `hash_one` call tree explicitly contains canonical candidate ordering at 0.88% of samples. Aggregate hashing also includes codec metadata and other callers, so the total hashing share is not a navigation-only estimate. Euclidean distance computation remains substantial at 13.91% and 13.27% on the two owners. No lost samples are reported in these retained profiles.

The cache stores only the previous parent identifier and its validated map index. A parent change falls back to the existing map lookup, including when a previously seen parent appears again. Every row still checks finite distance, ordinal range and uniqueness, and parent revision consistency. Parent identity, completeness, duplicates and global canonical ordering checks remain intact. Shuffled replies retain the same behavior, and equal-score selection still uses the unchanged reference ordering and sort.

## Longest jobs do not identify the final jobs

The epoch32 diagnostic retains the 32 longest jobs per owner. It does not retain every job or a separate set of the last jobs to finish. The latest-finishing retained job in the coordinated detailed run ends at Unix time 1792703025.7929666, approximately 2.607 seconds before the coordinator's balance-complete event at 1792703028.3999120. Therefore these traces cannot establish the actual last-finishing job or the complete dependency chain that determines completion time. Cross-owner clock skew is another limit when comparing timestamps.

That retained job takes 2.637 seconds, including 0.538 seconds in navigation, 0.265 seconds in the expansion backend and 2.317 seconds in engine requests. These scopes overlap. Its long engine-request duration is not evidence that remote navigation dominates the job. Other retained jobs spend more time navigating, but neither a long job nor large aggregate CPU proves that a specific optimization shortens balancing. A separate bounded set of recently finished job records is being added by the parent task to resolve this gap in the next diagnostic run.

## Validation

The candidate passes 31 focused routing tests, including mixed local/remote 64-query reference replay, full-width identities, reordered and duplicate replies, malformed completeness/ordinal/revision checks, finite scores, and exact equal-score ordering. New differential coverage exercises grouped and interleaved parents with both cache settings. All malformed reply mutations are rejected under both settings. The original loopback test attempt encountered sandbox socket permission denials; the authorized rerun passes.

A fixed grouped replay processes 409,600 candidate rows. The control performs 409,600 parent lookups; the cache performs 4,096. In a native unoptimized test build, the two control samples take 0.140779 and 0.121937 seconds, and the two candidate samples take 0.036505 and 0.036085 seconds. These timings include cloning and are mechanism evidence, not a production speedup estimate. The mixed-owner reference replay reconstructs 21,376 rows with 668 lookups while retaining identical output. Production insertion and balancing effects require the parent's same-binary cloud comparison after the transport improvement is enabled.

Test evidence is in `navigation-tests.log`. The separate process control validation (`SPANN_NAVIGATION_PARENT_CACHE=0`) also passes all 31 focused routing tests and is recorded in `navigation-control-tests.log`.

## Placement frame-size investigation

The third navigation-enabled run completes balancing but fails before its cycle-complete event with a frame-limit error. This does not establish which placement request failed. The frozen implementation sends an entire published routing view in one ordinary JSON `InstallView` request after promoting internal nodes into shared routing. No chunking or maximum encoded view size protects that request. The failed run has 2,131 leaves and 32 owned internal nodes immediately before placement. The five successful runs promote 14–19 internal nodes and finish placement with 1,087–1,179 ownership units.

A deterministic wire-shape model demonstrates a reachable frame-size risk with that tree size. A view containing 32 internal parents and 2,131 leaf-child routing entries, each with a 768-dimensional centroid whose entries equal the exactly representable float `-0.123046875`, produces 22,638,861 bytes of JSON for the engine placement request. This excludes transport-envelope overhead and exceeds the 16,777,216-byte frame limit by 5,861,645 bytes. The child centroid arrays alone occupy 21,278,035 bytes. This model is not the captured failed view and therefore does not identify the incident's failing request. The size receipt is `install-view-size-model.json`; the transport investigation must identify the actual request and reproduce it with the Rust serializer before selecting a repair.

If view growth causes the failure, a general repair stages bounded chunks of the serialized view, checks the declared total size and content hash, and installs the complete validated view atomically. A compact exact-float representation reduces wire size, but it also needs an explicit growth bound or chunking for larger indexes. Raising the frame limit alone postpones the failure. Any repair must preserve publication sequence and attempt identity, reject conflicting retries, and expose no partial view.
