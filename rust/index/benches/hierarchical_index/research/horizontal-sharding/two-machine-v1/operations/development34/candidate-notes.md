# Bounded concurrent expansion groups

The candidate overlaps two groups of queries sent to the same remote owner. It targets balancing calls with more than 64 queries; ordinary insertion calls with a single group remain inline. The process reads `SPANN_EXPANSION_GROUP_CONCURRENCY` once: `2` enables the candidate and `1`, an absent value, or any other value selects the serial control. The default remains serial pending the cloud comparison.

Each multi-group invocation starts at most one scoped child thread and processes the other lane on its caller. Even-numbered initial groups run on the caller and odd-numbered groups run on the child. Each lane processes its groups sequentially, so there are at most two active subcalls per owner invocation without a thread per group. All requests use the original absolute deadline and at most 64 queries. Explicit request/reply size failures retain the existing sequential bisection within each original group. Arbitrary errors are never retried. An error cancels admission of additional initial groups, both lanes join, and no successful prefix reaches the caller. Results are assembled by original group index, retaining the original order of size subdivisions. Child panic becomes an error after the join.

The spawned child installs the initiating job context before doing work. A detailed endpoint test verifies all four calls across both lanes appear in the initiating balance job's request attribution. The existing `ExpansionSequentialGroups` telemetry name is retained for comparison, but its duration now covers the whole possibly overlapping invocation. Its initial-group, subcall and subdivision counters retain their meanings. Its thread CPU describes the initiating thread, not aggregate CPU from both lanes; process CPU remains the aggregate comparison metric.

The barrier-style test uses condition variables to require overlapping handlers and reverse the completion order of adjacent groups, then verifies exact output and a peak of two active handlers. The five-second condition-variable timeout bounds failures and is not a performance assertion. Additional tests cover a peer rejection without retries or prefix return, an expired common deadline with no sent requests, and explicit size subdivisions in both concurrency settings. The existing common-deadline test uses three initial groups so both serial and two-lane execution must respect the same total budget.

Validation: all 11 initial bounded tests pass in serial ordinary, concurrent ordinary, and concurrent detailed modes. The final additional subdivision test brings the detailed focused suite to 12 passing tests. The full ordinary concurrent suite passes 319 tests, with 3 ignored and the previously identified concurrent-parent/leaf test excluded; this full run precedes the final test-only addition. Native `cargo check -p chroma-index --locked --bench two_machine_spann` passes, with existing warnings retained in `candidate-bench-check.log`. An initial unprivileged test invocation failed at loopback bind because of sandbox permissions; the authorized loopback reruns pass.

Only `engine.rs` and `engine_endpoint_tests.rs` change. Routing completeness, finite-value checks, canonical ordering, transport framing, worker pools, and checkpoints remain unchanged.
