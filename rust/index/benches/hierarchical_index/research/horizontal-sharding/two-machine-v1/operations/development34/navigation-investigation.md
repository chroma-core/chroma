# Navigation latency investigation

The existing implementation already overlaps expansion requests to different remote owners. The narrower serialization worth measuring is within one remote owner's batch: requests are divided into groups of at most 64 queries and each group waits for its complete response before the next group starts. A second possible overlap is local scoring with remote scoring, because all local/shared images are scored before any remote request is submitted. Neither observation establishes which change shortens the measured late jobs; the request-attributed diagnostic should choose between them and non-navigation dependencies.

## What the source establishes

Navigation builds each level's candidates by scoring resident routing images and grouping the remaining nodes by owner. When multiple remote owner groups exist, scoped threads issue all groups concurrently and the driver joins all replies before validation and selection. With two owners, direct local scoring generally leaves only one remote owner group, so parallelizing owner fanout adds no new concurrency. The source is `routing.rs`, `navigate_batch_with_assembly`, around lines 328–394.

One owner's expansion can still require many sequential calls. The implementation partitions queries into groups of at most 64, submits each synchronously, and accumulates complete replies. Explicit frame-size failures bisect a query group or a single query's parent set; those subdivisions are also processed sequentially. All calls retain a common absolute deadline, and failures never expose a successful prefix. This code is `engine.rs`, `expand_remote_until`, around lines 2531–2604. Insertion normally supplies 64 queries, so concurrency across ordinary initial groups principally targets large balancing batches. Size-induced subdivisions could also affect insertion; measure their occurrence rather than assuming they are common.

Server capacity is bounded, but capacity alone does not establish spare runnable CPU. Expansion requests use the control listener (`RequestClass::Control`), whose benchmark pool has 128 handlers and eight decoders. The data listener has three execution lanes with 64 handlers each plus eight decoders. The control listener has one execution lane; decoded requests at its active limit are rejected rather than accumulating an unbounded execution queue. The detailed smoke's zero admission rejections does not measure queue delay, decoder delay, or scheduler contention. These definitions are in `transport.rs`, `TransportConfig::capacity`, `execution_lane`, and the listener loop; the explicit control request choice is in `expand_remote_until`.

## Repeated work that remains

A remote child reply passes through base64 decoding, fixed-width child materialization and finite-value checks in `expansion_codec.rs`. Routing then verifies the reply identity, full parent coverage, ordinal bounds and uniqueness, finite values and consistent revisions. Finally it reconstructs the reference parent/ordinal order before distance sorting. The parent cache already removes repeated hashing for consecutive rows but does not remove these passes or allocations.

Canonical ordering scans child rows to count each parent's children, records parent positions, creates offsets, scans rows to construct source indices, checks completeness, constructs an inverse permutation, and swaps rows into place. This is a real CPU candidate, but its 21.712 inclusive CPU-seconds in the final detailed run are smaller than reply validation's 66.945 and total navigation's 264.680. Reply validation and canonicalization also enforce different contracts: a fusion must preserve conflicting duplicate detection across replies, remote completeness and canonical ordering across local plus remote rows. Simply removing checks is not justified.

The retained profiles show distance computation near 13% of earlier owner samples, but they do not attribute this specifically to late jobs. Earlier aggregate hashing shares include unrelated callers. The epoch33 cache improves insertion by 0.528 seconds on average while balancing duration remains inconclusive. Thus broad CPU savings are useful evidence for insertion, but they do not identify the balancing completion dependency.

## Candidate selection after the diagnostic

If long jobs spend most remote time in Expand and those calls appear as several sequential groups with little server queue delay, test bounded same-owner group concurrency first. A same-binary switch such as `SPANN_EXPANSION_GROUP_CONCURRENCY=1|2` can preserve the current path at one and enable two in the candidate. Retain the 64-query maximum, common deadline, all-results barrier, stable original-group assembly, existing size-only bisection and no resubmission after arbitrary errors. Keep concurrency bounded per navigation and assess aggregate server contention; 32 balancing jobs each adding one active call may consume much of the control pool. This is a hypothesis until the diagnostic establishes multi-group calls on the relevant jobs.

If remote calls are mostly single groups and local scoring precedes a substantial remote wait, overlap local scoring and the one remote call instead. That change needs a separation between capturing coherent immutable images/classifying owners and actually scoring them; launching a worker before those handles exist risks changing view semantics. It also introduces scheduling overhead on small navigations, so use a same-binary control and evaluate CPU as well as latency.

If remote execution is small and local decoding/validation dominates, prefer a narrowly scoped validation/order fast path for already ordered parent runs, with fallback to the current general path. It must prove the order and all invariants rather than assume the wire order. If transfer or publication calls dominate last-finishing jobs instead, neither navigation overlap hypothesis follows from their duration.

## Test seams

Existing endpoint tests directly exercise the bounded expansion helper with a controlled server. `bounded_expansion_large_query_batch_preserves_complete_global_tie_order` covers 2,200 queries, the 64-query ceiling, exact output identities and global ties. Adjacent tests cover query bisection, parent-set bisection, unsplittable parents, explicit codec size causes, late failures with no returned prefix, ambiguous EOF with no retries, and one common absolute deadline. A concurrency candidate should parameterize an internal helper so both settings run in the same test process, add a barrier-controlled server proving two groups are in flight without timing thresholds, assert peak in-flight requests never exceed the bound, and retain exact output order even when replies complete in reverse order.

The routing assembler seam already compares candidates against the retained reference ordering before score sorting. Existing mixed local/remote 64-query replay and shuffled/interleaved parent-cache tests provide differential coverage for a validation/order candidate. No candidate behavior or cloud actions are performed in this investigation. Diagnostic-only instrumentation in `engine.rs` records remote expansion invocations, initial groups, multi-group invocations, group-count buckets (1, 2, 3–4, 5–8, and 9+), actual subcalls, and successful size-driven subdivisions. The inclusive sequential-groups scope attaches these counts and duration to the initiating job. It is created only in detailed mode. Group buckets provide a bounded distribution, not an exact maximum; parent validation owns the integrated test run.
