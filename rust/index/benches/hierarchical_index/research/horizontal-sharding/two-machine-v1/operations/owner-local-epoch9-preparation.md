# Epoch9 fixed 100K before/after preparation

The prepared runner executes one explicitly selected 100K arm in a fresh guarded window. The baseline uses retained epoch7 binaries. The comparison uses the new reservation-correction binaries after their build hashes and source review exist. This preparation launches nothing, reuses the generic supervisor and lifecycle, and preserves all original scripts and source archives.

[make-owner-local-spec-epoch9.py](make-owner-local-spec-epoch9.py) accepts only `100k-before` or `100k-after`. Both use the exact retained epoch2 100K descriptor/vector file, 32 workers, one initial owner, one 100K add interval and the existing thresholds and 80K owner capacity. The frozen workload-plan hash and input digest/byte count remain in provenance. Both use 600-second process bounds and an immutable job deadline no more than 590 seconds after spec preparation. Outputs use `/home/ubuntu/spann-two-machine-v1/epoch9/100k-before-owner{1,2}` or `100k-after-owner{1,2}`. Run IDs bind the fresh window and chosen arm; both owners in one arm share a run ID.

The before binary/reader paths and hashes come from `runtime-binaries-epoch7.json`. The after arm requires `operations/runtime-binaries-epoch9.json` containing reviewed SHA256 strings for `two_machine_spann` and `two_machine_reader`; the file must bind binaries at `/home/ubuntu/spann-two-machine-v1/epoch9/build/`. No placeholder after receipt is created. Missing or malformed hashes reject preparation. The complete hash-file digest enters each spec, and the runner rejects differing hash-file snapshots between owner specs. The source scope of the reservation-only change requires separate review; hash binding does not prove that scope.

[run-one-arm-epoch9.py](run-one-arm-epoch9.py) accepts exactly one positional arm. For example, `python3 operations/run-one-arm-epoch9.py 100k-before` selects only the baseline; it does not run the after arm. The corresponding after command replaces the final argument with `100k-after`. These commands operate remotely and are not authorized for execution by this note. There is no attempt flag, size sweep, automatic advance or retry. Existing local output directories reject a second invocation. The runner uses the unchanged generic `/home/ubuntu/spann-two-machine-v1/epoch9/remote-job.py`, uploaded and reviewed by the root operator from the existing generic supervisor, not an epoch8 extended-bound supervisor.

The root operator must create `operations/window-epoch9/start-intent.json` with a fresh `window_id` beginning `epoch9-` and fixed `deadline_unix`, plus fresh `running-readback.json` instance addresses. The existing lifecycle must establish independent local and remote absolute guards before any execution. The runner rejects a closed window or less than 660 seconds remaining and uses a 660-second SSH bound. It preserves existing process-group ownership/stop/readback behavior and collects only small receipts. Both owners are cleaned up on failure. Existing token and input paths are referenced; no credential or corpus copies are created.

The optional 10-second owner1 CPU observation is a prerequisite, not an implemented runner option. Historical evidence verifies child-launch perf recording, but current attachment options, permission and PID/thread inheritance support are not verified. No observer or `--profile` switch is invented. The root can admit a separate bounded collector only after verifying those capabilities, binding the owned PID/start ticks/executable, and recording coverage around the first `balance_started` event. See [OWNER-LOCAL-PROFILE-PLAN.md](../local-tests/OWNER-LOCAL-PROFILE-PLAN.md). An unprofiled before/after comparison still measures the reservation correction; existing logical-work counters must accompany it.

Eight pure local tests pass: fixed epoch7 baseline hashes/settings/input, explicit after hashes with identical workload, shared peer run identity, fresh output/run IDs, missing after receipt, rejected changed input/deadlines/windows/other arms, rejected retry/profile flags, and the unchanged generic supervisor's admission/process-ownership/cleanup tests. The log is [epoch9-owner-local-admission.log](../local-tests/epoch9-owner-local-admission.log). All three new Python files compile in memory. No Cargo, SSH, AWS, Git, profiler or benchmark command runs during preparation.
