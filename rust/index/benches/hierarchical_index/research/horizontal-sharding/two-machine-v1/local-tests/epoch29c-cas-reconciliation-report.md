# Conditional publication error reconciliation

The real storage diagnostic captures an S3 `ConditionalRequestConflict` response while another contender successfully publishes the latest generation. The storage library exposes that service response as a generic error, so the caller cannot classify it using the adapter's existing typed precondition mapping. The ten-round native diagnostic records this in round 4, with one success, one generic error, and the successful contender's descriptor in durable storage (`operations/native-cas-diagnostic-1792685572`). AWS documents conditional-write contention responses in [its multiple-writer guidance](https://aws.amazon.com/blogs/storage/building-multi-writer-applications-on-amazon-s3-using-native-controls/).

Publication reconciles a failed conditional write by reading the latest pointer once. Exact intended bytes acknowledge success. A structurally decoded descriptor different from the captured predecessor reports a conflict. An absent pointer, the same predecessor (including different JSON formatting), or malformed bytes preserve the original write error. An unavailable readback reports both the write and read errors. There is no additional PUT, unconditional overwrite, or automatic retry. A competing descriptor receives no success acknowledgment and does not need a complete referenced-object validation to establish that the pointer changed.

The original Linux smoke has two failed caller results and a committed generation 4, but it does not record the error values. That evidence remains unresolved in detail; the reproduced generic conditional-conflict response establishes one concrete classification defect, not a complete explanation of both original failures.

Eight deterministic cases cover exact committed bytes, a competing descriptor, unchanged state, failed readback, malformed bytes, an absent pointer, a reformatted predecessor, and a descriptor with the desired generation name but a different attempt. Each case asserts exactly one conditional PUT and two latest GETs (the initial read and one reconciliation read). The complete native suite passes 269 tests in 9.22 seconds, with two explicitly ignored S3 diagnostics and the same unrelated split test excluded. All three native CLIs build and pass help checks. Exact source and retained native artifact hashes are in `epoch29c-reuse-source-inventory.json` and `epoch29c-reuse-validation.json`.

A separate opt-in diagnostic repeats only conditional publication, avoiding repeated multipart payload uploads. It uses a fresh namespace per round, logs both outcomes and readback, continues collecting failed rounds, and defaults to ten rounds.
