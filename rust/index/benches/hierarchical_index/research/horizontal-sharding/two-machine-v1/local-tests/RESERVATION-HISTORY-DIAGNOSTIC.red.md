# Reservation history adds work without active conflicts

The actual reservation manager visits 65 records for one uncontended request after 64 completed attempts, versus one record without history. The live tree, placement, topology sequence and request are identical. Both cases have zero active grants and queued competitors before the probe, and both perform zero granted-region overlap checks. The only difference is retained Released history.

The diagnostic runs public request and release methods on a one-leaf manager. Test-only counters count the existing conflict-discovery loop. The test grants the probe, releases it, verifies that an old attempt still replays as Released, then asserts that completed history should not increase active-conflict work. This assertion fails with 65 versus one visited record. The red test and its exact command remain recorded; no optimization is implemented.

The single timing samples do not establish a speed difference. The empty-history request takes 1,052,625 nanoseconds and the history case takes 6,625 nanoseconds. First-use and allocation effects are uncontrolled, so these opposite-direction timings reinforce the choice to use deterministic work counts. They do not negate the count mechanism or attribute end-to-end latency.

Current construction permits this history to accumulate. The benchmark creates one owner service before its add/balance/redistribution loop and closes and seals the epoch only when saving after the cycles finish. Releasing a reservation retains its record. Phase close, seal and open handlers do not reclaim manager history, and the inspected production modules never call the existing manager reclamation method. Specific drained placement events replace the manager; ordinary local construction does not. History-dependent work must therefore be interpreted within each actual manager lifetime.

The smallest proposed repair separates conflict discovery from replay retention. Keep completed request/outcome records, and maintain a separate ordered set of currently granted attempt IDs under the same manager mutex. Grant inserts an ID; release removes it before pumping the queue. Root replacement updates the indexed record's roots. Duplicate outcomes, cancellation tombstones, FIFO order, placement checks and atomic region coverage remain intact. Deleting outcomes at balance boundaries is unnecessary and could break delayed replay.

This diagnostic proves avoidable bookkeeping amplification, not its share of the balancing slowdown. For H completed attempts, the inspected uncontended loop visits H+1 records; summing repeated admissions within one unchanged lifetime gives a source-derived quadratic visit count. Memory, replay lookup cost, active contention, navigation, posting transfers and clustering require separate accounting. The JSON receipt contains exact measurements, source hashes, lifetime evidence, command, budgets and the proposed repair's limits.
