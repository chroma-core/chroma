## Concurrency mechanism

The scheduler prevents two balance jobs for the same node from running together. It does not prevent a different leaf's split, neighbor reassignment or merge from selecting this node as a transfer destination. The transfer protocol protects the affected source and destination during that transfer, then releases them. A merge's navigation and expensive preparation do not reserve the entire subtree across its lifetime.

The current merge selects an initial source list, moves rows preferring its first neighbor, captures the remaining list and evacuates that captured list through global navigation. A posting transferred into the source after the latter capture is outside that batch. The subsequent unprotected assertion that the current list must be empty is therefore too strong. A correct response preserves that posting and revalidates or reschedules the remaining work. Retirement must still protect the actual current source and refuse to remove it if any posting arrived before protected validation.

The unsharded writer follows the same broad approach. It claims the source and first destination for the initial preferred-row transfer, then releases that pair before reassigning remaining rows. Its final retirement reacquires the source claim and removes only an actually empty leaf. It does not treat every nonempty result after the captured reassignment as fatal. The relevant source is the unsharded writer's `merge_leaf`, `reassign_many` and `retire_empty_leaf` methods. This comparison supports a local protected revalidation fix, without a tree-wide lock or hiding the source from navigation.

The construction author is preparing a deterministic reproduction and minimal repair. The review must establish exact membership under concurrent arrival, changed source revision and ancestry, and protection conflicts; it must not merely delete the assertion and then remove a nonempty source. The existing centroid-bound transfer correction remains in scope and must continue passing its adverse tests.
