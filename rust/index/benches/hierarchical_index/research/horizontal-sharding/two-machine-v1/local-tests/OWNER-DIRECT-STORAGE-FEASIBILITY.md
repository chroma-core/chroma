# Owner-direct durable saving: smallest reuse path

The checkout already has the storage operations needed for owner-direct full saves. The smallest useful step is to let the generation store and saved reader use the existing S3 storage abstraction, with each owner writing its immutable payloads to one durable namespace and the coordinator publishing only manifests. Incremental changed-block reuse is a separate step: the reference has a suitable blockfile mechanism, but its current record types and IDs cannot be substituted directly for the sharded implementation. This is read-only preparation, with no source, Cargo, infrastructure or cloud change.

## Existing interfaces to reuse

| Role | Existing interface | What is available and what is missing |
|---|---|---|
| Read/write durable bytes | `chroma_storage::Storage::{get,get_with_e_tag,put_bytes,put_file,put_stream}` with `StorageConfig::S3` | Existing S3 client/configuration and bounded-operation options. Select the existing bucket and AWS credential mode explicitly; the default credential mode is Minio. |
| Immutable object installation | `PutOptions::with_mode(PutMode::IfNotExist)` | The S3 backend sends conditional creation. On a precondition failure, the generation adapter must read and verify exact existing bytes for idempotent replay, rather than assume the collision is compatible. |
| Generation publication | `get_with_e_tag` and `PutMode::IfMatch(ETag)` | The S3 backend implements conditional replacement. Keep one combined descriptor/latest pointer and verify actual selected-backend behavior; the retained task probe establishes conditional creation, not every latest-pointer race. The local storage backend ignores write conditions and must retain its tested POSIX publication adapter. |
| Changed-block persistence | `BlockfileProvider::new_arrow`, `read`, `write`; `BlockfileWriterOptions::fork`; committed flusher IDs | Reuses untouched blocks and provides lazy reads through shared storage. Namespace and sharded record compatibility still need explicit integration. |
| Reference save/open pattern | `HierarchicalSpannWriter::commit(provider, fork_from)` and flusher `flush`; `HierarchicalSpannReader::open(provider, ids, …)` | Five blockfile roots cover postings, scalars, vectors, leaf metadata and internal metadata. Dirty nodes/embeddings and tombstones drive updates; postings and full vectors remain lazy on reader open. This is a behavioral/template reference, not an immediately compatible sharded writer. |

## Minimum full-save seam

1. Generalize only the generation object's byte access and publication boundary. The current `GenerationStore` is hardwired to filesystem paths, temporary files, hard links and directory sync. Give its immutable-object and manifest operations a selected storage backend while retaining the POSIX implementation for local tests. Keep the existing manifest validation, root coverage, format checks and saved payload representation.
2. Configure one stable S3 namespace for the run/index. Each sealed owner materializes its own payloads there and writes its owner manifest last. The coordinator receives its durable references and verifies coverage/identity/integrity, then writes the shared routing and combined manifest/descriptor last. Remove `ReadSavedObject` relay from this path; do not first restore the remote owner graph onto the coordinator.
3. Let `SavedReader` resolve the same durable references through the backend, retaining lazy selected-posting reads and cached routing metadata. Its current `GenerationStore::read_object` calls are the main access seam. A fresh reader uses only the descriptor, backend configuration and independently located full-vector source. It must not require owner processes or writer disks, nor download every posting as an opening prerequisite.
4. Retain a full-save failure/replay test and a real fresh-reader test. Verify owner-save failure leaves the previous generation visible, conflicting frozen attempts reject, conditional creation/publication do not overwrite incompatible bytes, and fresh reopen validates memberships/codes after live owners retire. Backend I/O completion replaces POSIX sync operations; it does not justify dropping durability acknowledgement.

Relative `ObjectRef.path` values can remain logical names if all owners/readers receive the same durable backend root. A prefix such as `sha256/<unique-task>/objects/<existing-logical-name>` can host them without changing the node/posting payload format. The existing external transfer helper instead maps logical names to content-addressed keys and exact S3 versions in a receipt. Reusing that representation directly needs a durable logical-name resolver; the Rust reader does not currently consume its mapping.

The general storage `GetOptions` has no VersionId selector, and its put/head interface does not expose the transfer helper's exact-version receipt. Choose this dependency explicitly: either use tested write-once logical keys with integrity verification, or add the small version-aware locator/access seam required to preserve pinned-version references. Do not silently label ordinary current-key reads as exact-version reads. The SDK/helper already demonstrates the latter operations, but it is not an integrated reader backend.

## Retained namespace and permission evidence

The retained task-role policy allows PutObject, GetObject, GetObjectVersion, multipart abort/list-parts and GetObjectAttributes beneath `spann-artifacts-079819354890-20261014-ecfcca4d/sha256/*`, with the resource account constrained to 079819354890. It does not authorize arbitrary top-level `objects/`, `block/`, `root/` or `sparse_index/` paths. The wildcard is a prefix restriction, not a requirement that every suffix be a SHA digest; a task-unique namespace beneath `sha256/` fits the retained policy. A nonempty blockfile prefix also keeps its generated `/block/<uuid>` and `/root/<uuid>` keys inside that namespace. The reference's empty-prefix defaults would not fit.

The retained conditional-creation probe records successful put/get plus a 412 conflict preserving the original version in that bucket. Existing transfer receipts/helper support exact-version restoration, and candidate27's fresh reader validates 3M memberships/codes without writer objects. That validation still reads a local saved namespace, so it does not prove owner-direct S3 reading. These are historical local receipts, not a fresh statement about current credentials or IAM state. A subsequent guarded execution must verify identity, exact resource configuration and permissions again. No new bucket, instance, volume, IAM grant, listing requirement or versioning-configuration query is required by this proposed first step.

## Incremental reuse is a distinct dependency

The reference commit forks each previous blockfile root, applies dirty live records and tombstones, and flushes new roots while inheriting untouched blocks. The sharded save currently snapshots all resident state and creates attempt-specific object names. Changing its storage backend removes the coordinator relay but still writes a full owner snapshot. A second checkpoint with one small mutation must therefore become a separate correctness/work-count test before claiming efficient incremental saving.

Reusing the provider needs full-width sharded records. The reference writer and typed hierarchy records use u32 node/vector IDs; the distributed design uses u128 logical nodes and u64 vector IDs. The blockfile key wrapper supports strings and u32, not native u128/u64 keys. Fixed-width string keys or explicit compatible record support are available directions; narrowing IDs is not. Parent/child fields and posting IDs need matching full-width value types, per-owner prior root IDs/prefixes must be retained, and dirty/tombstone tracking must cover splits, merges, reassignment and ownership movement. Immutable query generations must keep prior roots readable.

Do not convert the working full-vector source into duplicated per-owner mutable vector blockfiles merely to copy the reference's five-root container. Its independent immutable corpus descriptor/access adapter remains the applicable contract. Reuse the reference's lazy postings, dirty updates and blockfile forking where they fit; preserve the structural differences that full-width distributed ownership actually requires.

## Recommended order

Implement the backend-neutral generation/read seam with owner-direct immutable full saves first, using existing storage and the existing sandbox namespace. This proves the intended durable placement/publication/read path without inventing a central relay. Then integrate changed-block persistence and full-width record support, guided by the reference's provider/commit/open implementation. The acceptance test for the second step is a small second-generation mutation that retains unchanged immutable references, preserves the first reader, and writes work proportional to changes rather than the whole index. WAL processing, fleet management, recovery and garbage collection remain outside both steps.
