# Independent owner-local profile results review

The profile result accurately reports an early CPU sample and leaves whole-phase attribution unresolved. The reviewer finds no material correction needed in `OWNER-LOCAL-PROFILE-RESULT.md`. The next comparison should follow the measured clustering path while retaining the remaining hypotheses; the sample does not establish that sharding adds no other cost or that the clustering kernel is itself slower than the reference.

The raw workload result records a 15.257687601-second balance and 17.943982333-second construction-plus-save total. Subtracting phase snapshots gives 47.34 CPU-seconds on owner1 and 0.88 on the empty peer. Subtracting insertion counters gives 7,469,370 navigation child distances, 7,151,504 vector fetches and 485 completed balance jobs. The phase records 68 splits, 119,376 completed transferred rows, 69 leaves and one internal root. Its only cross-peer application traffic is 149 framed bytes. These measurements match the summary and report, including their scope as process intervals rather than exclusive function timings.

The retained fresh-reader receipt validates exact 100K membership, full-vector checksum and every posting/centroid code. Final ownership is 54,804 and 45,196 vectors. This meets the smaller-owner occupancy criterion after placement; it does not imply both machines constructed this initial interval. The report correctly relies on the earlier two-50K diagnostic for actual construction on both owners.

The observer reports a successful exact-process recording with a nine-second normal timeout, return code 124, cleanup confirmation and a 565,752-byte recording. The collection envelope is 9.637296745 seconds and includes start/flush/cleanup overhead. The text report displays `2K` samples, which is rounded rather than an exact count, and explicitly reports zero lost samples. The result uses approximately 2,000 samples and does not turn that display into an exact statistical sample size.

The top-level instruction-location rows are exclusive because the report disables child aggregation. The 49.60% Euclidean-distance row, 40.16% split-routine row and 3.55% posting-code row match the text report. The split routine’s caller context inside the distance row displays 46.90 percentage points of the whole report; it is included in that distance row, not an additional exclusive row. Adding those caller percentages to top-level rows would double-count samples. The result explicitly avoids that mistake and warns about noisy inlined intermediary frames.

The runtime does not timestamp its phase events. The collector observes the flushed balance-start event, records for its bounded interval, and ends without observing balance completion. That supports an early partial-slice interpretation without reconstructing exact leading/trailing phase coverage. CPU percentages describe recorded running instructions, not the entire 15.26-second balance or blocked time. The navigation distance counter also excludes clustering distances, so it cannot normalize the dominant split/distance sample work. A low transfer/navigation sample share does not rule out later-phase costs.

The raw receipt confirms the exact retained epoch9 binary binding, effective root only for the observer, unchanged permission setting of 4, PID-scoped userspace sampling and collector cleanup. The workload supervisor exits 0 with cleanup confirmed; the separate peer receipt confirms shutdown. The closed-window receipt records both authorized instances API-stopped and a single $0.35508287628173824 compute upper bound. These support the report’s lifecycle claims. The epoch10 unprivileged preflight failure remains separate evidence.

These are independently constructed, profiled timings with uncontrolled seeds and scheduling. The result appropriately makes no isolated speedup claim and assigns no exclusive share of the remaining latency gap.
