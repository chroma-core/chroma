## Fixture and interpretation

Use one fixed 100,000-vector add interval followed by one balance, with 32 workers and the existing thresholds. This is the smallest retained real-data fixture demonstrated to show the slowdown at those settings. Smaller correctness fixtures do not establish that they reproduce the leaf count, reservation history, transfer work or contention. Do not sweep sizes or workers.

The epoch6 baseline balances in 14.839610034 seconds after a 0.174966823-second add. Before placement, owner1 contains all 100K postings in 70 leaves and 71 nodes; owner2 contains zero. Owner1 records 69 splits, 111,604 transferred vectors, 8,303,863 vector fetches, 215,164 expansions and 6,565,903 navigation child distances. Its process CPU rises from 1.07 to 53.45 seconds across the phase snapshots. Peak active jobs is 22, which does not establish useful core utilization. [BALANCING-COST-SOURCE-REVIEW.md](BALANCING-COST-SOURCE-REVIEW.md) identifies the leading source differences: reservation conflict checks scan retained completed history, transfer compacts a source separately for each destination group, and local navigation constructs rich request/reply buffers. Those are mechanisms to attribute, not measured CPU shares. The reservation work-count correction is implemented and validated; its isolated end-to-end contribution remains unknown. The completed-history scan description applies to the retained baseline, not the corrected profile target.

## Reusing the actual runtime

The first 100K balance already uses one active data owner in the real distributed engine. Owner-local requests invoke the actual handler directly, including reservations, transfers and navigation. Owner2 remains an idle endpoint except for count/control requests until placement. Sample owner1 only and verify zero owner2 vectors, splits and transfers during that phase.

The frozen CLI cannot run with no peer in one process. It constructs a peer client, hardcodes counts for owner IDs 1 and 2, and redistributes with two budgets (`two_machine_spann.rs:97`, `:283`, `:329`, `:386`). There is no supported `--single-owner` or `--no-peer` flag. An unreachable or self-addressed peer is not a valid substitute. Reuse the idle peer instead of building another driver for this first observation.

The library permits an empty peer map, but that is not an existing frozen performance entry point. The earlier native wrapper `dynamic-review/consolidated-owner-construction-v1/consolidated_native.py` invokes an older `hierarchical_spann_shard reference-owner-diagnostic` writer.
