# Single-owner balancing: source attribution review

The leading avoidable differences are repeated posting-transfer work and reservation bookkeeping that grows with completed attempts. Navigation also builds substantially more temporary data than the reference. These are source-supported explanations to profile, not measured shares of the slowdown. This review makes no implementation change and runs no benchmark.

## Evidence and scope

The retained epoch7 receipt records 249.178044690 seconds of completed balance phases through 1M vectors; its 2M balance starts without a completion. At 1M, owner1 contains all 1M postings and owner2 contains zero. Owner1 reports cumulative 718 splits, 418,267 transferred vectors, 24,497,784 vector fetches, 9,907,476 internal-node expansions and 554,438,005 navigation child distances. Its peak of 32 active jobs establishes admitted concurrency, not 32 cores doing useful computation. The last completed balance takes 43.428620955 seconds and adds only 149 framed application RPC bytes between its before/after snapshots. Thus this owner-local slowdown cannot be attributed primarily to transmitting vectors between the two machines. Source: `operations/window-epoch7/3m-distributed/run-receipts.json`, embedded `events.jsonl`.

The parent reports 33.619 seconds of total balancing for the completed 3M reference. That is context, not an equal-work ratio: independent clustering, different completed sizes and missing distributed completion prevent attribution by dividing these totals. Work-normalized comparisons still need phase deltas for splits, navigation distances, transferred rows and retries.

The inspected checkout files match their SHA256 entries in `packages/source-epoch7.tar.gz.json`: distributed engine, construction, routing, reservation manager and vector source, plus the reference writer and structural reservations. ## Leading differences to investigate

| Priority | Source-supported difference | Consequence to measure |
|---|---|---|
| 1 | The reservation manager retains completed records. Every queued request scans the complete record map to find currently granted conflicts, under one mutex. Releasing a reservation marks it Released and pumps the queue without removing it. | Even an uncontended new transfer traverses completed history. Within a growing manager lifetime, repeated scans can accumulate roughly quadratic bookkeeping work in the number of attempts; overlapping queued requests add further scans and ancestry walks. Measure record count, visited records, queue length, mutex wait and pump CPU before concluding this dominates. |
| 2 | Reassignment groups vectors by destination, then executes each group through a complete transfer protocol. Source postings are checked and compacted separately for each destination group. The reference reserves available destinations together and compacts the source once across all destinations. | More destination groups multiply source scans, code-buffer copies, protocol setup and bookkeeping. Measure source entries scanned per transferred row and groups per source. |
| 3 | Local navigation uses the same rich request/reply representation as remote navigation. It copies each full query for every level/owner request and clones replies, with ordered maps/sets for validation and candidate assembly. | Allocation, memory copying and validation can add CPU per navigation distance, even with no TCP traffic. Profile allocation/copy stacks alongside scoring and sorting. |
| 4 | Local transfer stages repeatedly acquire per-node locks and the owner-wide operation mutex; structural publication also copies routing images and protects the affected ancestor region. | The necessary affected-region protection may be inexpensive or expensive depending on work overlap. Measure wait versus hold time; do not infer contention merely from the presence of locks. |

The reservation-history difference is concrete. The distributed manager owns one mutex around a topology map, attempt-record map and request queue (`distributed/protocol/reservation.rs:24`, `:132`, `:243`, `:352`). Its pump checks every record, including Released records, before filtering to granted conflicts. By contrast the reference holds only active structural reservations in a vector and removes them when their guard drops (`writer/structural.rs:14`, `:30`, `:55`). Reference membership claims similarly retain only currently claimed leaf IDs (`writer/writer.rs:28`, `:53`). Retaining duplicate-operation outcomes may be required, but scanning those outcomes to discover active conflicts is an implementation choice. This observation does not recommend deleting the duplicate-operation protections.

The transfer difference applies even when both leaves belong to the same owner. The common path makes two endpoint preparation calls and nine state-step calls per chunk, constructs a serialized digest input, clones IDs/codes/payloads, and recomputes destination codes (`distributed/engine.rs:1615`, `:1637`, `:779`, `:988`). The calls are direct local handler calls for the local owner, not network round trips (`distributed/engine.rs:1504`). Preparation checks each proposed ID with linear `posting.ids.contains`; removal repeats membership checks, builds a removal set, and copies retained IDs and codes into a fresh list. Destination checks are also linear. The reference bulk transfer builds one proposal lookup and scans the source once across all available target groups (`writer/writer.rs:1936`, `:1995`, `:2228`). The distributed reassignment loop builds a current-source ID set and copies vectors into query buffers each retry round, then calls transfer once per destination (`distributed/construction.rs:756`). Count rejected groups and rerouted rows before attributing additional cost to retries.

## What navigation and vector access actually materialize

Navigation does not load posting lists. Owner expansion clones handles to immutable routing images, scores their child-centroid rows after releasing the routing gate, and returns child metadata (`distributed/engine.rs:627`). Fetching one routing node deep-copies its centroid and child metadata but does not clone its postings (`distributed/engine.rs:522`, `:1537`). Posting IDs are copied explicitly by split and neighbor reassignment, not as a side effect of routing (`distributed/construction.rs:339`, `:843`). The reference navigates immutable cached child rows through direct node-map handles (`writer/writer.rs:763`). Therefore “navigation reads unused posting codes” is not an explanation supported by these paths.

The distributed batch navigator validates full queries, groups requests by owner, copies query vectors, and validates and clones structured replies (`distributed/routing.rs:113`, `:161`, `:228`). Single-owner navigation takes the direct expansion branch; it does not spawn a thread per level. Whole-attempt retries and root metadata refresh remain additional possible work. Their actual frequency is unknown.

The benchmark vector source preloads immutable full vectors. In this mode a vector get checks the ID range and clones an existing vector handle; it does not read or decode the file per access (`distributed/saved_reader.rs:757`). The owner adds an atomic fetch counter (`distributed/engine.rs:320`). Splits and neighbor checks revisit vectors; reassignment copies full vector coordinates into query buffers. The reference also loads or finds immutable embeddings and clones handles during splitting (`writer/writer.rs:1380`), so vector fetch counts alone cannot establish excess disk I/O or an avoidable decode cost. Verify resident mode from the run receipt, then compare copied bytes and useful vector-distance work. Both full-precision neighbor paths must be compared with matching settings; quantized reference neighbor tests answer a different question.

## Scheduling, snapshots and the next profiles

The distributed scheduler coalesces pending balance jobs by node ID but allows a follow-up to queue while that node is active. Neighbor jobs deduplicate by attempt, not by affected node/centroid proposal. All workers claim jobs through one queue mutex; each claim can rotate through the ready queue looking for an owner-local inactive node (`distributed/construction.rs:51`, `:78`, `:640`). The initial eligibility pass snapshots resident handles and reads each node; it copies neither posting codes nor full vectors (`:195`). These are secondary candidates. A peak active count cannot distinguish useful jobs from repeated no-op eligibility checks, rejected publication work or workers blocked in transfers.

Three focused profiles can separate the leading causes without changing the algorithm or sweeping dataset sizes:

1. **Attribute one already authorized owner-local balance phase.** Capture sampled CPU stacks plus off-CPU or mutex wait stacks across all workers. Separate reservation pump/ancestry, transfer membership/compaction, navigation scoring/materialization, clustering and structural publication. Pair the phase with job, split, distance and transferred-row deltas. This tests whether CPU bookkeeping or waiting explains the elapsed time.
2. **Count work amplification in that same phase.** Record reservation records visited and active counts, transfer chunks/groups, proposed and accepted rows, source entries scanned/copied, failed groups, rerouted rows and navigation attempts. Report counts against elapsed time and tree shape. History-dependent scans and repeated source compaction become distinguishable from a legitimately larger reassignment workload.
3. **Resolve allocation versus scoring only if the first profile points there.** Attribute allocated/copied bytes to full-query buffers, reply clones, source-posting rebuilds and routing-image publication. Compare reference and distributed CPU per distance and per source entry at matching precision/settings. Retain independent tree/work differences; do not treat equal vector count as equal work.

The next decision follows the profile. If reservation-history scans dominate, separate active-conflict indexing from retained replay records. If source copying dominates, design an owner-local multi-destination transfer that preserves the existing membership and ordering guarantees while compacting once. If scoring or clustering dominates with more logical work, first explain work-count differences. None of these changes is admitted or implemented by this review.
