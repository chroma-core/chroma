# Saving the index: source audit and next measurement

The [epoch18 result](QUEUE-SAVE-500K-RESULT.md) validates direct local immutable-object reuse. The coordinator records zero local copied bytes, verifies 182 existing objects in 0.045 seconds and retains remote copying and durability guarantees. Save elapsed falls from 7.413 to 6.470 seconds. The tiny fixture isolates the write-count reduction and preserves replay, corruption rejection and prior-generation readability. Remote representation, sequential owner staging and posting-object packing remain untested optimization candidates.

Saving performs avoidable copying and repeated durable writes, but the current measurements do not show how much of the 7.884-second save they explain. The next step is to measure the save phases on the fixed 500K workload after the navigation-only comparison. This audit changes no implementation, benchmark settings, or persistence guarantees.

## Measured evidence and source identity

The distributed 500K run saves in **7.884278976 seconds** and validates through a fresh reader in a separate **4.203951150 seconds**. Its 500,000 vectors occupy 344 leaves across two physical machines: 265,479 vectors and 180 leaves on owner 1; 234,521 vectors and 164 leaves on owner 2. The retained reference spends **1.135658886 seconds** in commit and **1.704624183 seconds** in flush, totaling **2.840283069 seconds**; its separate validation takes **1.342278033 seconds**. These are single measurements, and the save contracts differ.

The save interval transfers **103,190,688 framed application bytes** across the network: 103,104,088 received and 86,600 sent, with 171 remote requests. These are differences between the recorded before-save and after-save counters, not whole-build traffic. The remote owner's posting payload contains approximately 28,142,520 raw ID/code bytes. JSON encodes code bytes as integer arrays, so the observed traffic includes substantial representation overhead plus routing, manifests, requests, and framing. No save-phase CPU or filesystem timing currently separates these costs.

The measured reference binary has SHA256 `8566a052e2fe0908188862c5ede2b98215664236198f6ab40a43193248016fb6`. The epoch 14 run preflight, epoch 12b binary registry, and epoch 12 compiler-artifact receipt agree on this binary. The inspected reference persistence writer, benchmark, local storage backend, and blockfile flusher match the epoch 12 reference source manifest byte for byte. The inspected candidate save runtime, saved reader, and generation store match the epoch 15 distributed source manifest. This comparison uses the measured reference checkout, not the sibling candidate's local unsharded writer.

Evidence is retained in `operations/window-epoch15/500k-distributed/{result.json,run-receipts.json}`, `operations/window-epoch14/500k-reference/{result.json,run-receipts.json}`, `operations/window-epoch12/linux-build.json`, `operations/runtime-binaries-epoch12b.json`, and the corresponding `operations/build-manifest-epoch12-reference.json` and `operations/build-manifest-epoch15-distributed.json`.

## What saving actually does

The coordinator first closes and seals every owner, which prevents new mutations and requires accepted work to finish. Each owner then clones its current routing records and posting lists, validates membership, serializes one posting object per leaf, and writes its immutable objects and owner manifest. The coordinator processes owners sequentially. It reads every saved object in bounded chunks and writes it into the combined generation store. It then validates and writes the combined manifest, and publishes the latest-generation pointer last.

The local owner takes this same copy path. It writes objects beneath `saved-generation/owner-1`, reads them back through a local handler, and writes identical objects beneath `saved-generation/objects`. The local copy consumes no network traffic, but it repeats file creation, byte copying, checksum calculation, and durability barriers on the same filesystem. The remote copy is necessary for the current reader's single-store layout; it is not inherently necessary for all possible distributed snapshot layouts.

Each new immutable object write calls file synchronization and directory synchronization. Every posting therefore receives two durable writes, one on its owner and one in the combined store. For 344 posting objects, the source predicts **688 posting-file writes and 1,376 file/directory synchronization calls**, before metadata objects and manifests. This is a source-derived work count, not measured syscall attribution. Object reads and checksums repeat during owner-manifest validation, copying, coordinator owner-manifest validation, generation validation, and final reopen before publication. Those checks protect the current publication contract; removing them requires a replacement proof, not simply skipping validation.

Saving does not fetch full-vector rows or regenerate their one-bit posting codes. It preserves the existing codes. It packs four-bit centroids for the roughly 350 tree nodes and writes a descriptor for the existing immutable full-vector file. The saved generation depends on retaining that file; the fresh reader verifies its SHA256. At 768 dimensions, each one-bit code occupies 112 bytes, and the candidate adds an eight-byte vector ID, totaling about 60 MB of raw posting IDs/codes for 500K vectors. There are no per-vector filesystem writes in this path. The per-vector uniqueness check uses a sorted set and remains a possible CPU cost, pending timing.

## Why the reference timing is not an equal durability comparison

The reference writes ordered blockfiles for postings, node records, and full vectors, then flushes blocks with bounded concurrent writes. Its fresh commit includes all 500K full-precision vectors, approximately 1.536 GB before file-format overhead. The candidate instead references the retained corpus file. Conversely, the reference's measured local storage backend uses ordinary filesystem writes without matching file and directory synchronization barriers. Its block packing also avoids one filesystem object per posting list.

The explicit durability decision should remain separate from an optimization result. Preserving the candidate's immutable objects and manifest-last publication is the default for the next measurement. Adopting the reference backend's ordinary-write behavior could be a deliberate research-mode contract, but would change what successful save guarantees; it should be labeled and evaluated separately. A comparison that changes these barriers cannot attribute the entire improvement to removing unnecessary distributed work.

## The smallest next experiment

Add coarse, operation-local save counters without changing the work, then record them during one fixed 500K run. Record owner snapshot/validation time, posting serialization time, immutable-write time, object count and raw bytes, coordinator copy time split between local and remote objects, manifest/generation validation time, and final publication time. Add file-sync and directory-sync counts and elapsed time at the generation-store helper, plus verified-read counts and bytes. Aggregate per object and phase; avoid per-vector logs or per-byte atomics. Record process CPU immediately around the timed save and owner thread CPU where supported. Nested intervals must be labeled and must not be summed as independent latency.

A small native test can establish that these counters describe the real save path: save two leaves with a few vectors, reopen the generation, and verify every ID and code. Assert object/byte and synchronization-call counts, not elapsed-time thresholds. Retain the existing failure test that preserves the previous latest generation and reopens it without writer memory. This fixture tests counting and persistence, not 500K performance.

The first implementation candidate is **reusing local owner's already durable objects**. Writing its owner snapshot directly into the combined store, or safely linking immutable files into that store, can remove the same-filesystem duplicate write while preserving checksums, retained objects, and manifest-last publication. Direct saving is simpler than adding cross-root references to the reader. A hard-link implementation must handle incompatible filesystems and synchronize the destination directory. Neither option should overwrite an immutable object or publish latest before all owners validate. The mechanism test must also verify that a failed later save leaves the previous generation readable.

Remote binary transport, concurrent owner staging, and packed posting objects are subsequent candidates if the phase measurements justify them. The current audit establishes repeated work and unequal persistence contracts; it does not establish an end-to-end speedup or identify the dominant save cost.

## Native counting check

Coarse save profiles are implemented without changing saving behavior. The actual two-leaf/four-vector fixture verifies duplicate local writes, exact immutable-object and file/directory synchronization counts, replay behavior and fresh-reader membership/code validation after writer objects are dropped. The first run passes the counting assertions but fails a reader assertion that expects two routing nodes instead of the root plus two leaves. Correcting that expectation yields one passing test in 0.22 seconds (`save-observability-02.log`); retain `save-observability-01.log`. The next fixed workload will expose these profiles in the benchmark result. Nested synchronization time remains inside its save phase, and byte counters describe application writes rather than physical device traffic.

## Concrete local-reuse implementation path

The local owner can save directly into the combined generation-store root. The coordinator then verifies its existing owner manifest and referenced objects, and reuses the manifest reference instead of copying and rewriting them. Remote owners keep their separate roots and copy path. Final generation validation, strict reader reopen, checksums, synchronization and latest-pointer publication remain unchanged. This needs no hard links or reader-format change. In the two-leaf fixture, the predicted coordinator immutable writes fall from eight to three while the local owner still writes five; assert those counts and independent reopen before measuring latency. Preserve same-attempt replay, conflicting-request rejection, missing/corrupt object rejection and a failed later save that leaves the previous latest readable. The failure injection must target the actual new local-owner save path rather than the removed staging directory. This is a read-only implementation plan, not an implemented or measured improvement.
