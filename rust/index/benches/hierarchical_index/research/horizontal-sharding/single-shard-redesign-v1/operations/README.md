## Prepared execution controls

These scripts are prepared and syntax-checked only. No archive is packaged until the root owner freezes and reviews both source trees. No script has started an instance or executed a benchmark.

- `lifecycle.py start` requires a new window directory plus a root admission JSON containing `root_authorized_execution: true`, `combined_review_passed: true` and `local_artifacts` with absolute paths and exact SHA256 hashes. It verifies fresh sandbox identity, the stopped approved worker and its existing volume, starts an independent local API-stop watchdog, then starts the instance with a fixed 2,700-second absolute deadline. Its `stop` action waits for API-proven stopped state and records a compute upper bound. The root operator must call `stop` in its collection/failure finalizer; the watchdog remains independent.
- `remote-guard.sh` requires `SPANN_DEADLINE_UNIX` and `SPANN_WINDOW_ID`. It verifies instance identity through metadata, rejects competing jobs, and installs an independent absolute systemd machine shutdown timer before any upload or build. Existing closed timers are listed for explicit retirement only after the new guard is active.
- `remote-run.sh` holds one nonblocking benchmark lock across both builds and all four processes. `remote-run.py` verifies the exact retained input, 32 physical cores, source-file hashes, free space and active remote timer. It builds with shared dependency settings and preserves separate executable copies before the candidate build can replace the reference executable. The benchmark order is reference, candidate, candidate, reference. Every process receives 100K vectors, 768 dimensions and 32 workers, and is capped at 180 seconds. `/usr/bin/time -v`, command arrays, host state, environment, input/source/binary hashes and separate logs are retained. Each run uses a fresh process and output directory, preceded by one bounded read of the same retained input; no OS cache flush occurs.

The remote manifest requires `combined_review_passed`, `source_closure_complete: true`, `source_files` containing every extracted source file’s absolute remote path and SHA256 hash (excluding only `.git` and `target` directories), `reference_source`, `candidate_source`, and `cargo_target_dir`. Optional bounds are `required_free_bytes` (default 30 GiB) and `build_timeout_seconds` (default 900 seconds). These fields must be frozen after implementation acceptance. Use `rust_toolchain: "1.92.0"`; the runner sets `RUSTUP_TOOLCHAIN` and verifies the selected compiler reports exactly Rust 1.92.0. Use the same allocator and Cargo profile in both source trees. The candidate flag is applied only to its bench crate through `cargo rustc -p chroma-index --release --locked --bench single_shard_matched --message-format=json -- --cfg single_shard_owner`; both arms share `RUSTFLAGS=-C target-cpu=native` for dependencies.

No timing proceeds after a build/process failure, mismatch or insufficient remaining time. There is no automatic retry, workload change or deadline extension. Preserve logs and output, collect small evidence, run the API stop finalizer, reconcile the ledger once, then stop work. A closed window is never reused. The nominal 45-minute compute bound is $3.024 at $4.032/hour, leaving $0.076 within the $3.10 cap for bounded shutdown observation.

The runner accepts a binary only from Cargo’s successful `compiler-artifact` message for the exact `chroma-index` bench target and that arm’s source file. It records that message and copies the identified executable before the next build. There is no directory scan, newest-file selection or stale-binary fallback. Extracted source manifests must match the complete enumerated source closure; unexpected source files, missing entries or source symlinks stop admission.

Before every timing process, memory admission requires at least 16 GiB of `MemAvailable` and records the exact observed bytes. This covers approximately 1 GiB of fixed input/state plus 32 workers × 256 MiB conservative per-worker headroom with margin. Insufficient memory rejects the fixed 100K run; it never changes workload size. This diagnostic admission does not implement or demonstrate a general bounded cache or scalable construction memory budget. No disk resize is performed by these scripts.
