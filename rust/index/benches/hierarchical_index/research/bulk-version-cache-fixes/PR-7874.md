## Why this helps

Balancing moves vectors between groups of vectors at the leaves of the tree. Before moving a vector, the writer checks its current version so an older posting cannot replace a newer update or deletion.

Persisted scalar metadata stores many versions together in each storage block. A cold version lookup fetches a whole block but copies only the requested version into the compact cache. The writer releases decoded blocks after each batch of 64 requests. Scattered vector IDs repeatedly fetch the same blocks when the shared cache cannot retain them, making other balancing workers wait for serialized version loading.

## What this PR does

A cold lookup copies every version from the requested vector's metadata block into the compact cache. Later lookups for any vector in that block use the compact values. Writer opening remains lazy.

The scalar reader returns owned integer pairs and releases its temporary ownership of the decoded block before returning. The existing shared block cache can retain its own bounded copies; this read adds no per-reader pins. This keeps transient decoding memory bounded by one block and avoids keeping borrowed rows alive after their storage is released. The compact cache still stores two bytes per touched vector slot, with pages allocated only for the ID ranges it touches.

The mutable version map remains authoritative for updates and deletions during the writer session. Copying checkpoint values cannot overwrite that map. Current-version lookup checks the mutable map again after loading. Missing IDs retain negative cache entries; sparse IDs and checkpoints without maximum-ID metadata retain their existing behavior.

The reader change is in `rust/blockstore/src/arrow/blockfile.rs` and `rust/blockstore/src/types/reader.rs`. The writer uses it in `rust/index/benches/hierarchical_index/writer/persistence.rs`.

The amount of reassignment work remains similar while destination loading gets much faster. The two fixes have similar overall performance in this sample count. Bulk scan has a lower mean balancing time, while block fill preserves faster opening. Parallel work ordering changes the number of balance rounds and tree shape; two samples do not establish a small performance difference between the fixes or recall equivalence. ## Alternative considered

[The bulk-scan alternative (#7875)](https://github.com/chroma-core/chroma/pull/7875) fills all checkpoint versions during writer opening. It produces similar balancing and 40M component results but adds about half a second to opening and reopening 9M versions and about 2.3 seconds to opening 40M versions in the reproduction. Demand-driven metadata-block fill is the recommended default because it preserves fast opening and avoids scanning unused versions.
