# Destination reassignment deltas: ready for EC2 measurement

Suggestion #12 is implemented on local branch `codex/reassignment-destination-deltas`, commit `000ac1eb6`. Its control is branch `codex/reassignment-checkpoint-version-fix`, commit `39626fb14`. Both are based on the prior profiled writer at `85d41e1de`.

The destination registration appends a replacement to the resident delta without materializing the persisted posting list. It increments the complete leaf length, which includes persisted rows, and retains the existing leaf/version lock order. The new version remains invisible to readers until the replacement is appended and the version guard is released.

A regression test confirms an existing correctness defect: the earlier writer cannot complete first reassignment for an unchanged reopened vector whose version is present only in the checkpoint cache. Both control and candidate promote that checkpoint value into the writable version map when registering a replacement. This shared correction is necessary for a performance comparison that executes equivalent valid work. Performance against the earlier, incorrect baseline must be reported separately and cannot establish the benefit of lazy loading alone.

The candidate passes 37 test executions across the posting-delta and policy/navigation test harnesses. The control passes the new persisted-version regression. The regression covers an absent destination retaining the old version, two workers competing for the same old version, exactly one new posting/version publication, complete leaf lengths, later materialization, and persisted posting/code/version contents. The candidate additionally asserts that destination registration performs no posting load. Formatting, diff checks, and commit hooks pass.

The EC2 experiment is complete. All eight timing runs, both separate posting-verification runs, and the read-only source audit are saved locally. The repeated replay comparison does not establish a speedup; loading work moves into the subsequent cleanup. The source snapshot already lacks 2,076 reachable valid IDs, and both versions preserve matching counts while adding 200,000 valid IDs. See `REPORT.md`, `summary.json`, and `validation-summary.json` for results and limitations.

The saved bundle contains both branches and can be fetched on the node, whose base repository already contains prerequisite commit `2b547c4f2`. The prepared `run-ec2.sh` compiles both revisions, preserves separate binaries, and runs four interleaved MS MARCO 800k→1M replays using independent checkpoint copies, followed by one fresh 1M build of each revision for each dataset. Settings match the earlier profiling runs; `--write-level-min-pcts` is absent. All jobs run sequentially. The script passes `bash -n`.

One remaining mechanism to measure is the subsequent recursive balance call: it scrubs and can load the same destination immediately after registration. Removing the registration load alone may shift work to that later scrub. The benchmark must assess complete balancing and checkpoint times, posting loads, and memory, rather than interpreting a zero registration-load timer as an overall improvement. No change to when recursive balancing or scrubbing runs is included.
